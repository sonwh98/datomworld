## Findings

**P2-1. No recursion-depth limit in the decode reader (unsafe-reader hardening, not a wrong-acceptance).**
`src/cljc/dao/jing/cbor.cljc:911-991` (`read-item`) and `:1088-1139` (`item->value`) recurse per nesting level with no cap (same for `wire_of` `:812-829` on encode). An adversarial payload of ~10⁵ nested `81`-arrays or `d81b` frames overflows the host stack: JVM throws `StackOverflowError` — an `Error`, which the test's `refusal-of` (`cbor_test.cljc:70`, catches `Exception`) and any future ingress wrapper's `refusal` classification both miss — Node throws `RangeError`. Neither is an ex-info with `::refusal`. Plan sentence: decode sits at "each ingress of bytes Jing did not encode itself" (plan, *Layering*, lines 117-125), i.e. untrusted remote/DHT bytes by step 3/4; RFC 8949 §10 recommends nesting limits. Memory itself is input-bounded (every item consumes ≥1 byte; `length-of` `:877-885` refuses >2⁵³-1 heads as truncation; `need` checks before every copy), so this is stack-only. Smallest fix: thread a depth integer through `read-item`/`item->value` and refuse past a fixed cap (64-256; no corpus payload nests beyond ~4). The refusal class for it (frozen 16 have no depth class) is an architect choice — `:malformed-cbor` is defensible since no conforming producer emits such payloads. Must land before step 3; not a J1 byte blocker.

**P2-2. Host-asymmetric decimal-exponent acceptance: identical canonical bytes accepted on Node, refused on JVM.**
`cbor.cljc:441-453`: JVM `decimal` refuses unless −exponent fits `[Integer/MIN_VALUE, Integer/MAX_VALUE]` (lines 446-449); the CLJS branch only requires `js/Number.isSafeInteger` (451-452). A canonical tag-4 payload with exponent ~10¹⁵ (< 2⁵³): Node decodes it, re-encodes identically, accepts; JVM refuses `:malformed-number` at `:1119`. That is the accepting host determining the boundary — against the plan's "Do not let the accepting host determine this boundary" (*Encoding contract*, line 163) — and it will trip J3's cross-host acceptance parity. The corpus pins no exponent window (A12 rules only bignum exponents out), so this is codec policy, not a corpus conflict. Smallest fix: mirror the JVM window exactly in the CLJS branch of `decimal` (refuse unless −exponent ∈ int32 range, same formula), and record the window for J2/Dart.

**P3-1. Public carrier constructors bypass invariants; `num=` can disagree with `num-compare` for hand-built carriers.**
`cbor.cljc:319-365`: `(->Rational 2 4)` is publicly constructible. `num-compare` stays correct (cross-multiplication `:599-601` works on unreduced fractions), but `exact-key` `:556-563` keys on unreduced strings, so `num=` says false and `num-hash` differs for mathematically equal values — violating "equal values compare zero and hash alike" for that input. Decode and the `ratio` constructor (`:469-486`) always reduce, so nothing in the corpus or codec produces one; `Decimal.`/`Float64.` direct construction is benign (fields are the identity). Smallest fix: reduce in `exact`'s ratio arm (one `bgcd`), or make the deftype constructors private/validating.

**P3-2. JVM `big` silently truncates non-integer Numbers.**
`cbor.cljc:101-109`: `(BigInteger/valueOf (long x))` — `(cbor/decimal 0 2.5)` or `(cbor/ratio 1.5 2)` computes garbage instead of refusing, against the plan's "reject … loudly rather than computing garbage" spirit (*Numeric identity*). CLJS `js/BigInt` throws natively. Fix: refuse non-integral `Number` input in the JVM arm of `big`.

**P3-3. CLJS `num=`/`num-hash`/`num-compare` silently accept unsafe integral numbers.**
`cbor.cljc:380-381`: `host-integer?` admits any `Number.isInteger` number; `exact` then rounds it through `js/BigInt`, so `(num= 9007199254740992 9007199254740993)` is vacuously true on a value JS already rounded — while `encode` refuses the same input (`:745-747`, `:unsupported-value`). Plan: "Reject unsafe integral JavaScript Number inputs". Fix: in the CLJS arm of `exact` (not `host-integer?`, which feeds wire dispatch), throw "not a portable number" for integral numbers failing `isSafeInteger`.

**P3-4. `exact-key` docstring overstates portability.**

The key is host-independent, but its `hash` is not: JVM hashes strings with Murmur3, CLJS with the 31-based scheme, so `num-hash`/`equiv-hash` values differ cross-host for equal values. Fine for every J1/J3 requirement (hashes are only used within one host — `collapse?` grouping, host buckets), but if hash values ever cross hosts (published-index partitioning), a specified digest is needed. Fix the comment; record the limitation for the architect.

## Recommendation 3a — decoding without Boring: RATIFY

The Jing-owned reader is not a workaround; at Boring 0.1.30 it is the only implementation that can accept the frozen corpus. Decisive concrete case: Boring's decoder maps tag-30 `3/1` to `3N`, so canonical `num/ratio/3-1` (`d81e820301`) could never round-trip through a Boring decode — re-encoding `3N` yields `03`, and the corpus requires acceptance with rational kind retained (A11). The architect's own work package already declared the plan's "read as `boring.data/UnknownRecord`" sentence stale and prescribed closed dispatch; the implementer's probe results (stringref/date/UUID acceptance, with-meta mapping, `decode-seq` dropping a trailing index frame, JS float/int conflation) show the sentinel variant fails the same way, because Boring's lossy native mappings happen before any unknown-record callback. The design honors the plan's actual invariant — "Validate tag/name/payload shapes before any lossy host conversion" — literally: the generic reader holds only bytes/BigInt/text items and refuses `:float` items (`:1093`) without ever converting their bits; Boring remains the sole byte writer; the re-encode identity check (`:1154`) enforces shortest heads, ordering, reduced ratios, canonical NaN, and metadata omission by construction, all pinned by 132 decode-refusal + 209 canonical fixtures, so a Boring writer behavior change fails tests rather than silently altering bytes. Hidden risks of hand-parsing: stack depth (P2-1, fix before step 3) and per-item allocation overhead (each item is a map; ~constant×input amplification — bounded, but worth an ingress sizing note for remote/DHT). Conditions: ratify with the depth-limit fix, a formal plan correction of the decode-path sentence, and the allocation note.

## Recommendation 3b — `:host-collapse` on Node: KEEP THE REFUSAL, RATIFY A NEW CLASS

Refusing is unambiguously right: the two keywords are *not* equal under Jing's portable equality (`equiv` compares `[kind namespace name]` fields, `:605-607`), the bytes are canonical and distinct, and "losing an entry is never acceptable". No frozen class fits honestly — `:equality-collapse` would assert portable equality that does not exist; `:duplicate-key`, `:non-canonical`, `:malformed-cbor` are all false about these bytes. So: a 17th class, ratified by architect ruling as a README erratum (the frozen file stays unedited; the implementer correctly did not touch it). This does not contradict "do not let the accepting host determine this boundary": that sentence governs Jing's *acceptance rules*, which are host-independent here (raw-duplicate and portable-collapse checks run identically everywhere, and the decode-side twins `mal/collapse-*` enforce on every host); CLJS keyword interning (`-equiv` on the joined `fqn`) is a host data-model limit no acceptance rule can cure — Node cannot hold the value at all. Scope of the limit: CLJS **map keys and set elements** with colliding joined names only (`(keyword nil "a/b")`/`(keyword "a" "b")`, and analogously `(keyword "a" "b/c")`/`(keyword "a/b" "c")`/`(keyword nil "a/b/c")`); CLJS symbols are unaffected (`Symbol -equiv` is field-based), keyword *values* in vectors/lists are unaffected (no merging), JVM and — to verify in J2 — Dart are unaffected. Consequence to record for J3: `coll/map-both-slash-keywords` cannot round-trip on Node; the by-id skip plus the evidence test (`cbor_test.cljc:170-178`) is the right pin. If cross-host fidelity for this identifier class ever becomes a requirement, the fix is a CLJS keyword carrier in a future contract version — not a v1 change.
