5. **Low-severity record for S3/S7: under sub-54-bit profiles, float-key refusal is sign-asymmetric.** For a negative float with e < 0 the `neg` at prelude.cljc:1470 can breach (m up to 53 bits) and raises MemoryError, while the positive twin passes m into radix-16 `format`, which checks neither bits nor digits for power-of-two radices, and keys successfully. Each path follows the module contract (the limit governs module results; `format` never bit-checks), the outcome is deterministic and host-independent per value, and such profiles violate the documented "limits must admit at least 1075 bits" floor for float keys — but S7's resource-limit fixtures should either avoid or pin this window deliberately. The parity suite (60 bits) cannot reach the 1470 breach; an optional hardening row would run a <54-bit composition with a negative 53-bit-mantissa key.

## Rulings on the engineer's four questions

(a) **Unknown-reason fail-closed — accept with a documented limit; it does not block.** The module is the only producer of these keywords, its contract enumerates exactly what v2 may return, and any new reason is a contract change (version 3) that lands with its prelude translation in the same change — the window is empty in practice, and the seam already fails closed on everything the module can return today. Do not add `data/keyword?` now: it touches a frozen S0 contract for a speculative need. If the vocabulary ever grows, prefer a per-shape translator (prelude-local) or a predicate exported by the `integer` module itself, which owns the vocabulary — both smaller than reopening `data`. Take finding 2's one docstring sentence now.

(b) **MemoryError message: bare, args `()` — accept.** CPython-faithful; the e2e test pins `e.args == ()` and the uncaught snapshot `{:type "MemoryError", :args []}`. A descriptive message would be a profile invention with no CPython anchor.

(c) **ValueError text without N — accept.** `::max-digits` is per-composition data the prelude cannot know, and v2 deliberately carries no payload so results stay untagged; both architects' baseline correction already demotes the digit limit to a support-profile restriction rather than a 3.9.6/3.11 message match. The text "Exceeds the limit for integer string conversion" is a prefix of CPython's and honest. If N is ever wanted it is a new ruling (a limit echo through the seam), not an S3a change.

(d) **No `data/number?` fast path — keep the nine `=` checks.** Nine keyword compares with no allocation and no hashing are cheaper than one module-boundary crossing on every host, and the `=`-chain is the JS-BigInt-safe form (a map lookup would hash the carrier). Revisit only if S3 operator benchmarks put the translator on a measured hot path.
