### Cause 1: the helper's token coordinates (round-1 divergence (1): CONFIRMED HARMFUL)

The generated `Python3LexerBase.cpp` (grammars-v4 upstream, pinned) differs from the Java helper in two ways.

- **`commonToken`**, used for INDENT and the helper's EOF:
  - C++ takes line and column from `lastToken`, and uses `0 0` when there is no last token.
  - Java's `new CommonToken(_tokenFactorySourcePair, …)` takes them from the lexer.
- **`createDedent`:**
  - Java sets `dedent.setLine(lastToken.getLine())`.
  - C++ does not.

These coordinates reach the packet only through syntax-error records: the listener's line and column come from the offending token.

**Attribution experiment (thrown away).**
1. I edited the generated `build/antlr/python3/cpp/Python3LexerBase.cpp` to the Java behaviour. The diff is `r2-exp-helper.diff`, 2 lines: `getLine(), getCharPositionInLine()` in `commonToken`, and `dedent->setLine(lastToken->getLine())`.
2. I rebuilt (`r2-exp-build.log`, exit 0, dylib `24a0bf70…`) and re-ran parity (`r2-exp-parity.log`). Result: **48/51**. Entries 1 and 2 pass, and entry 3 keeps only its message diff.
3. I then restored the pinned output with `clojure -M:antlr-gen --target cpp`. That exit 0 is digest-checked against the manifest's `:cpp :generated`, and `cmp` with the saved copy also matched.
4. I rebuilt. The dylib is back to `1e465456…`, byte-identical to before the experiment.
5. All final results above come from the restored build.

**No helper patch was kept.** Whether to add a manifest helper patch (the Java semantics) is an owner/Architect decision. Note that the existing pinned tests (`cst_export_test.cljc` `error-coordinates-are-independent-test`, `helper-token-error-coordinates-test`) already accept host-specific helper-token coordinates for Node and Dart, while this brief asks for equality with the JVM.

### Cause 2: the ANTLR4 C++ 4.13.2 `DefaultErrorStrategy` differs from Java 4.13.2

Both points are verified in source.
- **`getTokenErrorDisplay`:**
  - C++ (`runtime/src/DefaultErrorStrategy.cpp:272-285`) replaces an **empty** token text with `<type>`.
  - Java tests for **null**. The Java DEDENT's text is `""`, read back from the input, so Java prints `''`.
  - This explains entry 3's message.
  - A related latent difference: C++ writes `"<no Token>"` and Java `"<no token>"` (from `javap -c` of the 4.13.2 runtime jar).
- **`sync`/`recoverInline`:**
  - Java 4.13.2 records `nextTokensContext`/`nextTokensState` in `sync()` and builds `InputMismatchException` from them in `recoverInline`. I confirmed this with `javap -p`/`-c`: the fields and the `putfield`s in `sync`.
  - C++ `recoverInline` (`:194-211`) throws `InputMismatchException(recognizer)` from the current state, and its `sync` (`:92-134`) records nothing.
  - So Java reports the expected set of the earlier loop state (30 tokens) where C++ reports `']'`. This explains entry 4.
- **Entry 5** (a missing third error under recovery) is the same strategy class. I did **not** isolate which branch causes it, so it is attributed to the C++ runtime's recovery only provisionally.

Making these equal means changing error reporting below the grammar: for example, a wrapper-installed `ANTLRErrorStrategy` that ports the Java 4.13.2 behaviour, or a runtime patch. **I did not do either.** It goes to the owner/Architect per Q3.

### Round-1 divergence (2): indentation counted over UTF-8 bytes (SHOWN HARMLESS)

- The NEWLINE token's text, which `getIndentationCount` reads, can only be newline characters plus `SPACES: [ \t]+`. The pinned `Python3Lexer.g4:101,274` define `NEWLINE: (... SPACES | ('\r'? '\n' | '\r' | '\f') SPACES?)`.
- Both counted strings are therefore ASCII, so bytes equal code points.
- The INDENT start index (`stop - text.size() + 1`) is the same.
- **Tested:** `indent-tab`, `indent-mixed-tab`, `indent-formfeed` and `indent-nbsp` (U+00A0 is not SPACES: it gives the same syntax error on both hosts), plus `indent-nonascii-first-token` and `nonascii-under-indent`. All PASS.
