# Task: P1d-r3 — cold-launch bridge compile: cache + progress + watchdog

Role: VM Runtime Engineer (fix round; owner hit a "freeze" launching bb yin-repl --backend jolt-gambit)

## Defect (owner report + orchestrator reproduction, live timings)

First-ever `bb yin-repl --backend jolt-gambit` on a machine appears FROZEN at
`gsc -dynamic -keep-temp joltffi-bridge.scm`: the cold bridge compile is a
silent multi-stage build (gsc scm->C, cc, link per module) taking 5-8 MINUTES
total (measured live: cumulative gsc CPU 3:35+ across stages, all at ~95%
CPU — working, not hung), with zero per-stage output, and each stage under a
120s watchdog. A slow machine could exceed a stage budget and get SIGKILLed.
Warm runs (cached boot + built bridge) are fast — the defect is the cold path.

## Fix (three parts)

1. **Cache the compiled bridge across boot builds.** The bridge artifacts do
   not depend on the Yin boot (they depend on host/gambit/ffi inputs, already
   digest-pinned). build-yin-boot.py creates a fresh runtime-* dir per build;
   instead of recompiling the bridge inside each new dir, copy the
   digest-verified compiled artifacts (bridge object + dylibs) from the
   existing build/gambit-ffi/ cache into the new runtime dir (cmp/digest
   verified before reuse, rebuilt only when the ffi input digests change).
   Cold MACHINE = one compile ever; new boot build = copy.
2. **Per-stage progress lines** on the cold path: echo each compile stage
   before it runs (stage name + expected duration scale), so silence never
   reads as a freeze. Progress goes to stderr or stdout consistently with the
   launcher's other output.
3. **Bridge-stage watchdog raised to 600s** (per stage) on the cold path.
