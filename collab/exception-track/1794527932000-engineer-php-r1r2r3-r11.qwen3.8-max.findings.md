## 2. The ruling, accepted

sol ruled against the disposition I argued for in r10 §7 question 1, and the reproduction is
decisive: a near-max handle is admitted and returned as the original `Exception`, its count is
left AT the native maximum *by php's own repaired arithmetic*, and the next ordinary reception
then excludes that endpoint and hands back a `ForeignException`. An ordinary catch retaining one
more reference cannot make an unchanged local exception foreign. My r10 framing — "not a count
php's machinery could have produced" — is falsified by the first call itself, which is php's
machinery producing it. Accepted without reservation; the bounds are gone.

I also accept both corrections to r10's supporting argument:

1. **Raw `clojure.core/*` on two Long operands does not auto-promote** — it throws
   `ArithmeticException: long overflow`; only `*'` promotes. My "square the long maximum a dozen
   times" construction was wrong as written. (The r11 construction in §5 avoids it: the seed is
   `integer/shift-left`, which the module demotes to a `clojure.lang.BigInt`, and raw `+` on two
   BigInts goes through `Numbers$BigIntOps.add` and does not throw.)
2. **An initial 63-bit bound does not prove all later ownership results stay 64-bit** — counts
   grow by one per acquisition, so any admission-time bound is a snapshot, not an invariant.
   Correct, and it is the reason the r11 replacement proves *headroom* rather than a bound (§3).

Neither correction negated the `::bit-limit` hazard, which sol confirms is real; §3 is the
limit-aware replacement the dispatch and re-check5 both require.

## 3. The limit-aware replacement: probe the arithmetic, don't bound the carrier

`php/obj-val?`'s count admission is now three total calls, no comparison against any endpoint:

```clojure
(if (integer/integer? rc)
  (if (integer/integer? (integer/add rc 1))
    (integer/integer? (integer/add rc rc))
    false)
  false)
```

- `integer/integer?` — the exact-integer domain predicate (r10, unchanged; residual 2's repair).
- `(integer/add rc 1)` — **addref's own operation**, so admission establishes r7's
  "INCREMENTABLE" property against the composition's actual arithmetic domain instead of against
  the native carrier. `int-add` runs `out`, and `out` answers the `::bit-limit` keyword once the
  result's magnitude-bit-length exceeds `::integer/max-bits`; a keyword fails `integer/integer?`,
  so such a count is FOREIGN and the keyword is never installed as `:rc` where the next ownership
  operation would refuse as a host failure.
- `(integer/add rc rc)` — **headroom**. This is the direct answer to correction 2: an
  admission-time increment is a snapshot, because counts move by one per acquisition. A
  successful doubling proves `bits(rc) + 1 <= max-bits`, i.e. `|rc| < 2^(max-bits - 1)`, so
  reaching the limit afterwards takes at least `2^(max-bits - 1)` acquisitions — 2^99999 in these
  lanes, 2^4095 at the profile floor. `integer/sub rc 1` is covered by the same headroom, so r7's
  decrementability holds without a second probe. (Probe 1 is mathematically implied by probe 2 and
  is kept because it *is* the operation being licensed; it costs one fast-path call.)

Why this satisfies "distinguish genuinely unsupported state from the local results ordinary
ownership now produces", and is not the bare revert sol forbade:

| count | bits | disposition | why |
| --- | --- | --- | --- |
| 1, small | ≤ 63 | LOCAL | ordinary |
| MAX-1, MAX, MIN, 2^53, 2^63, 2^64 | ≤ 65 | **LOCAL** | sol's ruling: the repaired arithmetic produces these itself; 65 ≪ 4096 ≤ max-bits, both probes answer integers |
| any beyond-native big carrier under the limit | < max-bits | LOCAL | same |
| `(/ 1 2)`, `(data/float64 1)`, `"bad"`, absent | — | FOREIGN | `integer/integer?` refuses (residual 2, unchanged) |
| 2^100000 in a 100000-bit lane | 100001 | FOREIGN | probe 1 answers `::bit-limit` — genuinely unsupported state |
| 2^99999 in a 100000-bit lane | 100000 | FOREIGN | probe 2 answers `::bit-limit` — no headroom |

No hardcoded carrier bound, no broad host catch, nothing caught after the fact, no new export or
mint surface. The thresholds come from the composition's own `::integer/max-bits`, so a lane that
installs different limits gets a correspondingly different admitted domain with no source change.
`host-names` is untouched: `integer/integer?` and `integer/add` were both already declared.

The two `php.rt/int-max` / `php.rt/int-min` reads are gone from `php/obj-val?`; both cells remain
