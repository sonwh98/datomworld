## 3. The defect I found in the handover that neither r9 nor re-check4 identified

The handover's admission was `(integer/integer? rc)` and nothing else, on the stated reasoning
that "counts at or beyond the native carriers are inside php's own integer model …
(min-integer-bits is far beyond the native carriers) … the arithmetic itself cannot overflow".
`integer/add` is exact, but it is **not total**: it is *limited*.

```clojure
;; yin.vm.integer
(defn- out [limits b] (if (> (bits b) (::max-bits limits)) ::bit-limit (host/demote b)))
(defn- int-add [limits a b] (out limits (host/add (big! 'add 0 a) (big! 'add 1 b))))
(defn- big! [op arg x] (if (host/exact-integer? x) (host/promote x) (wrong-type! op arg :integer)))
```

and `::integer/max-bits` is finite for every PHP composition: the profile's floor
`yang.php.antlr.prelude/min-integer-bits` is **4096** (`register-integer-module` refuses
anything less), and the compositions these tests build install **100000** —
`test/yang/php/antlr/portable_harness.cljc:78`, `{::integer/max-bits 100000,
::integer/max-digits 4300}`. Whichever number applies, it is the point past which `integer/add`
stops answering an integer and answers the keyword `:yin.vm.integer/bit-limit` instead. Meanwhile
the VM's arithmetic primitives are raw host references (`yin.vm/primitives`: `(pure '+ + …)`,
`(pure '- - …)`, `(pure '* * …)`), which no `::max-bits` bounds and which auto-promote on the
JVM — the same fact that let sol build a Ratio with `(/ 1 2)`. So a guest can build an
arbitrarily wide exact-integer count in a handful of operations (`(* x x)` from the long maximum:
63 → 126 → 252 → … bits, i.e. past the 4096 floor in six squarings and past 100000 bits in
eleven), and then:

1. `integer/integer?` admits it (a `clojure.lang.BigInt` *is* an exact-integer carrier);
2. reception's `php/addref` calls `integer/add`, which answers `::bit-limit`;
3. that **keyword is `assoc`'d into the cell as `:rc`** and the payload is raised as a local
   Throwable — no refusal, nothing observable yet;
4. the next ownership operation on that count (`php/delref`'s `integer/sub`, or any
   `integer/compare`) reaches `big!` with a keyword and throws `ex-info` `"integer primitive
   refused"` `{:yin.vm.integer/reason :wrong-type, :op sub, :arg 0, :expected :integer}` — a
   **host failure escaping the boundary**, which is precisely the class this whole round exists
   to eliminate ("a caller checks for them before the call, so reaching one is a defect of the
   caller, and it stays a host failure, never a guest exception").

Restoring the strict bounds closes this by construction: every admitted count is < 2^63 in
magnitude, so it is at most 63 bits and every acquisition result at most ~64 bits — 64 is below
any `::max-bits` this profile can be registered under, so `integer/add`/`integer/sub` can never
reach `out`'s limit branch on the ownership path, and `big!` can never see a non-integer because
admission already proved the carrier. The admitted domain is then a strict subset of the domain
the arithmetic is total over, which is what "match admitted count carriers and all ordinary
ownership operations to one safe arithmetic domain" has to mean; the unbounded version matched
them to a domain where the arithmetic is only *conditionally* total.

**This is reasoning from source, not a reproduction.** I could not run it. It is falsifiable in
one command by the next seat (§6, step 1): set `:rc` to an exact integer wider than the
composition's `::integer/max-bits` (100000 in these lanes, 4096 at the profile floor) at the
handover's admission and watch the second ownership operation refuse.

## 4. Why the bounds also settle the rule-1 / rule-3 question (and the dispatch's fourth bullet)

`docs/design/yang.antlr.md` :3868-3876:

> 1. A payload valid as an exception in its own runtime retains that runtime's ordinary
>    catching and identity behavior.
> 3. A runtime requiring exception objects, such as Python or PHP, represents an otherwise
>    foreign payload with its own `ForeignException`, retaining the complete condition and
>    original payload.

r9 read rule 1 as making the endpoints local ("a handle whose count is the native maximum … is
VALID local state"). The dispatch reads the other way, and so does the code: it requires
MAX-1 and 2^53 to be pinned *safe through an ordinary catch/return* and separately requires
"the r7 boundary controls stay green" — and r7's boundary controls assert that the two
endpoints are foreign. Those two requirements are only simultaneously satisfiable with the
bounds kept, because reception's acquisition is what moves MAX-1 *onto* MAX: the endpoint is
excluded at admission, the count just below it is admitted and then leaves the range safely
under exact arithmetic. That is also the honest reading of rule 1/rule 3 — a count at the exact
endpoint of php's own int encoding is not state php's machinery could have produced and still
operate on inside that encoding, so it is "otherwise foreign" and is retained whole (rule 3),
while every count php *could* have produced keeps its identity through unlimited acquisitions
(rule 1). No broad host catch was added; nothing is caught after the fact.
