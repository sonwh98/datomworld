## 1. Attack-list verification

**(1) float-digits — correct.** The floor/ceiling bracketing in `int-float-digits` (`src/cljc/yin/vm/integer.cljc`, new "Float text (version 4)" section) is sound: a rounding interval is convex and contains `|v|·10^k`, so any n-digit decimal outside `[floor, ceil]` in the interval would force floor or ceil in too — checking both is sufficient, and nearest-only is genuinely insufficient below powers of two (asymmetric interval), exactly as designed. The `hi?` guard when `r = 0` is safe (an exact `lo` always reads back). Tie-break `2r vs den`, half to even on `lo`'s parity, is right (hi = lo+1 flips parity). The `10^n` ceiling bump (`exp10 = e + (count text) − n`) is correct, and a trailing-zero first-survivor is impossible (the same real number would have survived at a shorter n), so post-strip exponents are right. `float-ratio` is exact for subnormals (×2^64 below 2^11 keeps intermediates < 2^53; powers of two always representable). `decimal-exponent` corrects the bit-length estimate exactly and terminates. Pinned: `5e-324 → ["5" -324]`, max double `→ ["17976931348623157" 308]`, and both power-of-two asymmetry cases (`0060000000000000`, `4580000000000000`), whose fixture rows I confirmed (float-text-v1.txt:262-264, 3578-3580). Zero/NaN/±inf → `:wrong-type` `:finite-nonzero-float`, and non-float arg 0, all pinned. No host float parse/print anywhere on the path (`pow2`, host big ops, `host/to-radix-string` only). See nit 3 on the 17-digit cap.

**(2) decimal->float — correct.** One exact `ratio->float` per input; the sticky tail is never re-rounded. Truncation keeps 800 + sticky 1; since trailing zeros are stripped first, the dropped tail always contains the final nonzero digit, so an unconditional sticky 1 is exact. The thresholds agree with the exact path at both boundaries: s = 310 implies value ≥ 10^309 > max double, so both paths give `+inf` (and `ratio->float`'s `::float-overflow` keyword → `##Inf`, the only keyword it can return — underflow returns `0.0`, not a keyword); s = −326 implies value < 10^−325 < 2^-1075·(midpoint), so both paths give `0.0`. After truncation `e ∈ [−1127, 309]`, so `host/to-native` and `pow10` (table + squaring, exercised up to ~10^1075 by the padded-midpoint rows) are safe. Never a limit reason: no `out` call, no `::max-digits` read — proven by the 5001-digit fast pin (`1` + 5000 zeros at −5000 → 1.0) and the `0e99999999999999999999` fixture row (→ +0.0, so the all-zeros path short-circuits before the exponent is used). Malformed refusals pinned: empty / non-digit (`"1.5"`, `"-1"`) → `:syntax`; non-string digits, non-integer exponent → `:wrong-type`. ## 2. Findings

1. **Comment states 767; the true bound is 768.** `src/cljc/yin/vm/integer.cljc`, `max-significant-digits` docstring ("a double's midpoint has at most 767 significant digits"); same figure repeated in the engineer report. The midpoint between the smallest normal and the largest subnormal, (2^53−1)·2^−1075 = (2^53−1)·5^1075·10^−1075, has **768** significant decimal digits (log10 = 15.9546 + 751.3934 = 767.35; odd×odd, no trailing zeros); so does (2^53+1)·2^−1075. The architect's design §1 has the same off-by-one. **No soundness impact**: 800 kept + sticky = 801 > 768 with margin. Severity: nit (doc), but it is the justification for a load-bearing constant — someone shrinking 800 toward the stated bound would create a real bug. Exact fix: change the docstring to "at most 768 significant digits" (and optionally note the design figure was off by one, per the fixture-wins/errata convention).
2. **`yin.vm.integer-test` carries no v4 semantics.** Version 3 has `float-fixture-test`, `float-named-cases-test`, `float-refusals-test` (`test/yin/vm/integer_test.cljc:501-599`); version 4 adds only the version pin and export-set names, leaving all v4 behavior in the yang tree beside the fixture. Severity: nit. Exact fix: add one small `float-text-named-cases-test` (~10 lines) — the two power-of-two asymmetry pins, one sticky-truncation pin, one `:finite-nonzero-float` refusal pin, and the `max-digits` pin — mirroring `float-named-cases-test` style.
3. **No explicit 17-digit cap in the search loop.** `int-float-digits` recurs `(inc n)` unbounded; design §1 says "for n = 1 to 17". Behaviorally identical (17 significant digits always round-trip a binary64, so the loop provably stops ≤ 17), but the invariant is only implicit while the report describes a bounded loop. Severity: nano-nit; fix optional (a `:when`/assert at 18, or a comment).
4. **`:special` float_str rows are bits-unchecked in M4.** `float_text_test.cljc:319` skips inf/nan splits, so the fixture's `inf`/`-inf`/`nan`/`-nan` bit expectations (e.g. line 9868, `-nan` → `fff8000000000000`) bind nothing yet. Correct for M4's scope — the kernel has no word-form path — but it must not be inherited silently. Severity: nit (forwarding note). Exact fix: S4's guest `float()` test must check bits on those rows; see Q2.

## 4. Rulings on the open questions

- **Q1 — should `integer_test` get v4 pins: yes** (finding 2). The v3 convention is exactly that, and version 4 otherwise leaves the module's own namespace blind to its bump.
- **Q2 — `float('-nan')` sign bit: S4 must match the bits** (`fff8000000000000`, fixture line 9868). Repr hides the sign, but content identity, dict keys, and any later signbit/copysign observe it, and the bit pattern is host-observable today. Build the sign by pinned bit manipulation (or a pinned host op), never `(* -1.0 nan)`, whose sign bit is host-dependent.
- **Q3 — `int(str)` whitespace: measure it in `int-conv-v1`; do not share `float`'s set by assumption.** The float measurement already proves CPython 3.9.6 does not strip by `str.isspace` for `float` (28–31 refused while `isspace` is true), so the two builtins demonstrably differ in at least one direction; `int`'s set must be measured before S4 hard-codes anything. Also fold disagreement 2 into S4's message work: whitespace-only strings quote `''`, everything else quotes the unstripped original.
