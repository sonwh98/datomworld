## A. Critique of slices 1–5

1. **Fragmentation: necessary, but the proposed slice crosses a protocol boundary.** The current DHT refuses requests above 1200 bytes and drops oversized replies, so large index nodes cannot reliably leave the local store ([node.cljc](/Users/sto/workspace/datomworld/src/cljc/dao/jing/dht/node.cljc:74), [node.cljc](/Users/sto/workspace/datomworld/src/cljc/dao/jing/dht/node.cljc:186)). The existing `dao.stream.udp` framing is defined for remote-stream request IDs and directions, with a 64 KiB default message limit ([udp.cljc](/Users/sto/workspace/datomworld/src/cljc/dao/stream/udp.cljc:151), [udp.cljc](/Users/sto/workspace/datomworld/src/cljc/dao/stream/udp.cljc:230)). **I disagree** that the DHT node can simply reuse that private envelope or that moving its Transit-JSON wire to CBOR is required. Either run DHT messages over a specified stream channel, or extract a transport-neutral fragmenter with its own message identity and bounds. Preserve the current wire during an independent framing change unless a versioned migration is justified. Whole-content hash checking already protects accepted bytes ([dht.cljc](/Users/sto/workspace/datomworld/src/cljc/dao/jing/dht.cljc:167)); per-fragment hashes are optional, but reassembly limits, source scoping, expiry or eviction, and retries are required.

2. **Replication: the blocking put is real; the proposed acknowledgement is unsound.** A put waits for peer attempts after its local write ([dht.cljc](/Users/sto/workspace/datomworld/src/cljc/dao/jing/dht.cljc:203)); each request can take three 500 ms attempts ([node.cljc](/Users/sto/workspace/datomworld/src/cljc/dao/jing/dht/node.cljc:231)). **I disagree** with “durably stored locally and queued” when the queue is `dao.stream.memory-log`: that log explicitly lasts only for the process ([memory_log.cljc](/Users/sto/workspace/datomworld/src/cljc/dao/stream/memory_log.cljc:1)). Choose one honest contract before coding: local durability with *volatile, best-effort* replication, or local durability plus a separately durable replication intent recorded before acknowledgement. An empty bootstrap must retain pending intent for later peer discovery under the latter contract; silently dropping it contradicts “queued.” Define bounded backlog, retry, shutdown, and recovery behavior. The local backend must be `dao.jing.file` for a durable claim; the DHT constructor currently accepts memory as local storage ([dht.cljc](/Users/sto/workspace/datomworld/src/cljc/dao/jing/dht.cljc:285)).

3. **Non-JVM support: transport choice precedes host ports.** The author’s separate CLJD and Node UDP implementations are possible, but **I disagree** that they are the preferred architectural slice. The owner’s invariant makes any stream exposable through WebSocket or UDP, with NAT traversal and no privileged server role ([dao.stream.remote.md](/Users/sto/workspace/datomworld/docs/design/dao.stream.remote.md:13)). A DHT `IDhtNet` adapter over symmetric `dao.stream.remote` channels fits that boundary better than three independent socket protocol stacks. Reuse the existing UDP channel where applicable; use WebSocket or relay paths where raw UDP is unavailable. A browser cannot listen or use raw UDP ([dao.stream.remote.md](/Users/sto/workspace/datomworld/docs/design/dao.stream.remote.md:32)). Preserve `IDhtNet` as a useful seam ([dht.cljc](/Users/sto/workspace/datomworld/src/cljc/dao/jing/dht.cljc:53)), but specify peer identity, reply correlation, deadlines, and channel loss through stream events, consistent with the six invariants ([datom.world.md](/Users/sto/workspace/datomworld/docs/design/datom.world.md:24)).

4. **Hardening: correct concern, incomplete mechanism.** The receiver learns claimed `:from` peers before validating returnability and processes requests on its receiving thread ([node.cljc](/Users/sto/workspace/datomworld/src/cljc/dao/jing/dht/node.cljc:144)). A cookie must bind the observed source address and port, a short validity period, and a server-held secret; issue it in a small challenge reply and require it before expensive lookup responses, content reads, or store processing. Check reply size against request size until validation; cap bytes, work, fragments, pending RPCs, and storage per source and globally. A per-peer token bucket keyed only by claimed `:from` is spoofable. Also match replies to the expected source, not merely the RPC number ([node.cljc](/Users/sto/workspace/datomworld/src/cljc/dao/jing/dht/node.cljc:176)). This is an architectural threat-model decision followed by implementation work.

5. **REPL integration: premature as slice 5.** The DHT has no roots by design ([dao.jing.dht.md](/Users/sto/workspace/datomworld/docs/design/dao.jing.dht.md:9)), while the durable REPL design needs a validated published HEAD and recovery path ([durable-store findings](/Users/sto/workspace/datomworld/collab/1790709703000-architect-repl-durable-index-store-startup.gpt-6-sol.findings.md:15)). **I disagree** that a `:dht` startup spec and content fetch alone produce a usable cross-process index. A reader needs a trusted current manifest address, bootstrap reachability, and a complete fetchable index. The proposed plan also omits a slice for root discovery, availability repair, and storage limits. The existing lookup can strand live peers behind dead closest peers ([dht.cljc](/Users/sto/workspace/datomworld/src/cljc/dao/jing/dht.cljc:107)); best-effort replication plus unbounded storage does not establish persistent network availability ([dao.jing.dht.md](/Users/sto/workspace/datomworld/docs/design/dao.jing.dht.md:169)).

The DHT document’s “sha256 only” statement is stale: the implemented store accepts registered segment algorithms ([dao.jing.dht.md](/Users/sto/workspace/datomworld/docs/design/dao.jing.dht.md:17), [dht.cljc](/Users/sto/workspace/datomworld/src/cljc/dao/jing/dht.cljc:299)); Jing’s registry includes BLAKE3 and SHA-256, with BLAKE3 the default ([jing.cljc](/Users/sto/workspace/datomworld/src/cljc/dao/jing.cljc:207)).

## B. Owner-policy recommendations

1. **Keep `mem` as the default; require explicit `dht:`.** That preserves the agreed startup contract and prevents a change in latency, durability, network exposure, and failure modes merely by upgrading the REPL ([durable-store findings](/Users/sto/workspace/datomworld/collab/1790709703000-architect-repl-durable-index-store-startup.gpt-6-sol.findings.md:7)). A `dht:` choice must name a durable local directory if it promises persistence.

2. **Keep networking off until explicitly configured.** Empty bootstrap alone is insufficient: the current UDP constructor still binds a socket and starts a receiver ([node.cljc](/Users/sto/workspace/datomworld/src/cljc/dao/jing/dht/node.cljc:307)). Define local-only as *no listener, outbound dial, or replication worker*; enabling networking requires an explicit peer or meeting configuration. Once enabled, bootstrap addresses are ordinary peers, never authorities. NAT failure remains an observable connectivity state, not silent success ([dao.stream.remote.md](/Users/sto/workspace/datomworld/docs/design/dao.stream.remote.md:32)).

3. **Do not publish sensitive REPL content to an open DHT before authorization exists.** “Sensitive” means anything the REPL intake can contain that the user has not explicitly marked public: source text, literals and secrets, AST or code rows, execution state, metadata, and index nodes or manifests that reveal those facts. Jing is deliberately payload-agnostic, so it cannot infer sensitivity ([dao.jing.md](/Users/sto/workspace/datomworld/docs/design/dao.jing.md:30)). Enforce the policy at REPL composition: reject network-enabled `dht:` publication by default; allow only an explicit public-data opt-in for that index, with a clear statement that peers can retain and redistribute every published segment. A warning alone does not enforce it. Encryption without key and access policy would still expose addresses and traffic metadata ([dao.stream.remote.md](/Users/sto/workspace/datomworld/docs/design/dao.stream.remote.md:45)).

## C. Decisions before implementation

Decide now: the acknowledgement and outbox durability contract; whether DHT traffic uses `dao.stream.remote` or a standalone versioned wire; maximum segment and reassembly size; the security boundary and public opt-in; what “local-only” opens; root-fact authority and conflict rule; and the availability promise (including what a peer acknowledgement proves). These shape interfaces and acceptance tests.

Per slice, choose concrete codec, fragment sizing, retry timings, token-bucket values, host adapters, and CLI syntax. Root discovery can remain outside the DHT without a privileged node: a writer appends signed `{writer-id, sequence, previous-root, manifest-address}` facts to an explicitly configured durable `dao.stream`; peers expose or relay that stream via `dao.stream.remote`. A reader obtains a descriptor through configured peers or a meeting stream, verifies the trusted writer key and monotonic chain, then fetches the manifest by address. The stream’s location is bootstrap information; competing writers require an explicit application policy, not DHT consensus.
