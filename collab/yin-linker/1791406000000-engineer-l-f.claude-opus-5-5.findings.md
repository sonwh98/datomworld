### 1.3 R4 and R5: the tree scanners are one walk

R4's free-name walk was implemented first. The section 3.4 measurement then
showed the two other tree scanners far above R5's one-second line
(section 3 below), so R5 was applied to both. The result is one private
walk, `tree-places`, over the occurrence relation:

- worklist `[path id bound in-body? conditional?]` from `[[] root #{} false false]`;
  children from `vm/semantic-bytecode-grammar` exactly as
  `vm/occurrence-child-places` enumerates them (`tree-child-places`, a local
  copy since the vm one is private and `yin.vm` may not change);
- entering a `:lambda`'s slot 3 adds its params to `bound` and sets both
  `in-body?` and `conditional?`; entering an `:if`'s slot 3 or 4 sets
  `conditional?`; nothing else changes the context;
- `loop` with a vector frontier and a transient accumulator, no `for`, no
  multi-key `assoc` (section 3.2's portability rules).

The three scanners filter its places and sort by `path-order`:

- `tree-free-name-occurrences`: a `:variable` whose name is not in `bound`
  and not reserved, `{:name :at [root path] :in-body?}`.
- `tree-definition-occurrences`: `tree-binding` recognises a
  `:vm/store-put` row (own path) and a definition form (`yin/def` operator
  row, two operands, first a `:literal`; path extended by `[3 2]`), carrying
  `conditional?`.
- `tree-application-sites`: an `:application` row at `(conj path [3 n])`.

Deleted from the linker: `tree-occurrence-query`, `tree-definition-query`,
`tree-application-query`, `tree-row-at`, `tree-enclosure`, `tree-rows`, and
the `dao.space.query` require. The walk is occurrence-scoped (per place,
never per row; no visited set), so the shared-row hazard cannot arise.
`vm/free-names`, `vm/occurrence-rules`, `vm/occurrences`,
`vm/ast-requirements` and `dao.space.query` are untouched.

Section 5.5 permitted "whether the walk carries `in-body?` or recomputes it
with `tree-enclosure`"; carrying it was chosen, and carrying `conditional?`
the same way follows from R5's conversion.

## 4. Findings: what in the ruling was found wrong or incomplete

### 4.1 The synthetic module cannot link `:ok` on `:yin.ast/code` (section 3.3)

Section 3.3 asks the slow test to publish `:ok` on all four formats with
only declared primitives retained. In the wide layout every definition form
is itself an application site, and step 5a discharges a body occurrence only
by a definition that strictly precedes every application site, so a sibling
read inside a lambda body is retained on the tree format and refused
`:undeclared-free` (here `f1`). This is the same gap section 6 already
expects for P2 ("`:refused :undeclared-free` on `:yin.ast/code` naming
`float?` or another sibling (L-b)"). It is independent of L-f (no bound, no
scanner cost; the walk equals the rules on this shape). The test asserts
the refusal and that the name is a sibling, with a comment naming L-b, so
L-b flips it deliberately. Architect: confirm, or amend section 3.3.

### 4.2 A `:verifying` serve of a prelude-sized module over `yin.repl.link` never completes

Measured: a `yin.repl.link` composition serving `(wide-module 1000)` by name
for `:yin.debruijn.code`: `:verifying` (the default) stays `:pending` on
every round (0.5 s per round, nothing appended); `:trusted` answers `:ok`
`:trust :composition` in 3.1 s.

Cause: `attempt` caps one attempt at `attempt-budget` = 64 drive rounds, and
the linker issues one content request per link per `step`, so a 6006-part
tree fetch needs about 6000 rounds; an exhausted attempt restarts from
nothing on the next serve. Section 1.3's "after R3, a `:verifying` serve
fetches the tree (5688 parts over the content pair)" is therefore true of
`link-manifest` over `local-runtime` (as `publish-module!` uses) but not of
the REPL composition. Consequences for P2: the corpus legs on `:trusted`
work; section 6's `a-verifying-serve-links-py` and any default `(require
'py)` over `yin.repl.link` would stay pending. Not fixed here: L-f may
touch only the `local-runtime` ring capacity, and neither the budget nor
one-in-flight is within it. Options for the Architect: an attempt budget
scaled to the walk (or a budget of no-progress rounds instead of rounds),
pipelined content requests per link (section 7's deferred "streaming
multi-part fetch"), or `:trusted` for a self-publishing composition only.

### 4.3 `:trust` in the registry entry (section 6's P2 amendment)

Section 1.3 says the serving outcome arrives as `(:derivation response)`
(`engine.cljc` 1383). Before L-f the response carried no `:derivation` at
all, so the registry entry's `:derivation` was nil. After R6 the response
carries `:derivation` (the record) and `:trust` as two keys, mirroring
`link-manifest`'s outcome; the engine (untouched, as ruled) stores only the
record under the entry's `:derivation`. P2's "`:trust :verified` in the
registry entry" therefore has no slot to read without an engine change; P2
can assert it on the response instead. Note also that this means the
default composition's responses and registry entries now carry the
derivation record and `:trust`, which section 5.2's "composition without
`:derivation` behaves exactly as today" does not strictly allow; it is
unavoidable if a `:verifying` serve is to report `:verified` (section 5.3's
own test). All lanes stay green with it.

### 4.4 The request key set is in the design text

Section 3.1 allows an extra request key; section 6.3 of the linker design
lists the closed key set, so the key is documented there (an edit section
5.4 did not list).

### 4.5 The prelude-sized oracle comparison

R4 says the conformance test holds the walk to the rules "on every linker
fixture and on a synthetic module of the prelude's size". The oracle is the
quadratic query itself (8 to 15 minutes on the prelude, by the ruling's own
figure), so the conformance tests use `(wide-module 12)` (under 100 rows, same
shape) in the fast lane, and the prelude-sized module is covered by the
publish test only. Running the oracle at 6006 rows was not attempted.
