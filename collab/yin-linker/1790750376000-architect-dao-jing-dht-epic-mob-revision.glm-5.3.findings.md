## R1. The raw datagram layer

**Namespace: `dao.stream.datagram`** (agree with gemini over gpt's `dao.stream.udp.raw`): the owner framed the concept as "not all networking code is stream base but datagram base" — the abstraction is *datagram*, and UDP is its one carrier today; a sub-namespace of `udp` would invert that (the value/fragment layer is the udp-specific part, `dao.stream.remote.md` §3.2, and stays `dao.stream.udp`). Either name works; the load-bearing point is that it is a sibling transport with its own key namespace, not a rewrite of the value layer.

**Surface.** A bound port is created (`create!`-style, like the memory-log — there is no remote descriptor to attach to) and exposes exactly: one **writer handle** whose `append!` value is `{:dao.stream.datagram/destination {:host h :port p} :dao.stream.datagram/bytes b64}`, and a **traffic deposit** of `{:dao.stream.datagram/source {:host h :port p} :dao.stream.datagram/bytes b64}` events onto a caller-supplied stream. The socket itself has no reader surface (it retains nothing — the existing deposit model, `udp.cljc:364-370`); consumers hold cursors on the traffic stream; a bounded ring's `gap` is datagram loss by definition and each interpreter treats it as such. Sending is destination-in-value (connectionless); per-destination writer handles are sugar composable above it (the `UdpHandle` shape, `udp.cljc:460-476`), not part of the layer.

**Bytes as Base64 text in the public values** (agree with gpt, differ from gemini's "canonical byte arrays"). Three grounds: the host-boundary rule — "Host types are classified into plain data in the transform… no host type crosses onto the stream" (`datom.world.md`, Host Boundaries) — and `byte[]`/`Uint8Array`/`Uint8List` are host types; the repo's settled convention for bytes in stream-visible application values is padded standard Base64 (`content.cljc:11-13`; `dao.jing.cbor.md:464-471`); and the Transit codec carries no byte strings (`dao.jing.md`, open items), so gemini's choice would fence a datagram traffic stream off from ever being served through half the remote surface. Real bytes stay below the boundary at the host seam, exactly where they live today (`send!` takes bytes, `receive!` takes bytes, `udp.cljc:202,373`). The encode/decode cost per datagram is trivial beside the syscalls.

**Outcomes and bounds.** `append!` answers `:dao.stream/ok` (local send acceptance — never delivery, per `dao.stream.md:588-599` Writing and `dao.stream.remote.md` §2.4's identical rule), `:dao.stream/invalid-value` (malformed address/Base64, or decoded length over the enforced 1200 B `max-datagram`, `udp.cljc:58-62`), `:dao.stream/closed`, `:dao.stream/transport-error` (host send fault). Here I **differ from gemini**: their "`append!` returns `:dao.stream/blocked` if the host's socket buffer is full" is a contract error — `blocked` is a reader outcome (`dao.stream.md:574`); a writer under back pressure answers `full` (`dao.stream.md:161-162,595`), and only if a bounded outbound queue is composed (host policy), otherwise `transport-error`. gpt's outcome list is correct as written.

**Migration.** The host seams move under the raw layer unchanged in shape (`jvm.clj`/`node.cljs`/`dart.cljd` already return exactly this `send!`/deposit seam); `dao.stream.udp`'s value layer becomes an interpreter *over* the raw port: `make-port`'s `:send!` host seam and the direct `receive!` call become composition internals, the fragment/reassembly machinery (`udp.cljc:151-195,316-361`), descriptor, projection, `step!`, and `send-to!` are unchanged publicly, and `dao.stream.remote`'s §3.2 channel is untouched. Acceptance is both positions' criterion combined: existing `dao.stream.udp` and `dao.stream.remote` tests pass unchanged (gemini's S0 AC), plus new per-host and cross-host raw round-trip tests of exact bytes and observed source addresses (gpt's S1 AC). Host callbacks only deposit and return (`datom.world.md:69`), as today.

## R2. The DHT on raw datagrams

**Codec: canonical CBOR now, with a `:ver` field on every message.** Here I **differ from gpt** (keep Transit, version later) and **agree with gemini's conclusion while adding the evidence neither gave**: with k=20, a `find-node` reply carrying 20 `{id host port}` peer maps is ~2 KB in Transit-JSON — *already over the 1200 B budget today*, and therefore silently dropped at `node.cljc:190-195` whenever a table is deep enough to answer with a full bucket. The datagram budget is not a cosmetic constraint on this wire; it is binding on the most common message. CBOR byte-string ids bring a peer record to ~60–70 B, and a **capped peers-per-reply** (nearest 8, with shortlist iteration compensating — `dht.cljc:107-131` already iterates) fits comfortably. Add to that codec-family uniformity (content is canonical CBOR; `dao.jing.cbor.md:469` describes the Transit envelope as current state, not a commitment) and one codec story for the non-JVM hosts, and CBOR wins on raw-layer grounds my consensus position never needed. I adopt gpt's version-field discipline, which gemini lacks: `:ver 1` on every message now, so the chunk messages of the next revision need no fleet flag day. No negotiation machinery; the clean break is free while there is no fleet.

**Chunking: DHT-owned, rules borrowed, fields its own.** Forced by the owner's decision (the DHT may not consume the value layer's envelope). Each DHT message is one CBOR value; ≤1200 B encoded → one datagram; larger → `{ver, rpc, dir, part, parts, bytes}` datagrams whose `bytes` are slices of the whole encoded message, reassembled keyed by `[observed source address, dir, rpc]` — the same key shape the value layer uses (`[attachment direction id]`, `udp.cljc:328-332`) — then decoded whole, then hash-verified by the existing ingress check (`dht.cljc:167-180`), never stored or served otherwise. The reassembly *rules* are re-implemented against DHT fields but should come from one shared transport-neutral utility parameterized over key and fields (gpt explicitly allows this and bars importing `udp.cljc`'s private envelope or its `:dao.stream.remote/id` meaning — I agree; this is the surviving fragment of my consensus D1). Bounds: `max-message-bytes` (64 KiB default, composition datum), parts-count disagreement drops, duplicates ignored, accumulated-bytes bound enforced on arrival, oldest-partial eviction, per-source *and* global partials caps — the value layer's discipline (`udp.cljc:310-361`) minus its stream namespaces. Oversize is refused before the first datagram, never torn (`udp.cljc:225-233` rule).

**Hardening at this boundary.** Both positions put it in the DHT's raw processing step; agree, and the consensus D6 gate survives unchanged: the cookie/caps *design* is frozen in S0, implemented in the hardening slice, and nothing runs non-loopback before it. Adopt gpt's additions, which improve on both earlier rounds: a small `ping` obtains a time-limited cookie bound to the **observed source ip:port** (not the claimed `:from`); the cookie is required before any fragmented reply and before allocating reassembly state, and a verifiable token rides each incoming chunk so an attacker cannot force assembly before validation; unverified replies are capped at the request's size or a small fixed budget; replies are matched to the expected observed source, not the rpc number alone (`node.cljc:176-178` currently matches by `:rpc` only); and — the sharpest catch — **do not observe the claimed `:from` into the routing table before validation** (`node.cljc:171-175` does exactly that today). Amplification framing from my consensus round stands: chunking turns ~12× into ~60×, which is why the design gate belongs to S0. Rate limiting stays LRU-capped per source (bounded memory against port rotation), with per-source and global caps on work, fragments, pending RPCs, and storage.

## R3. The DHT's dao.stream-shaped API

**Two composition-supplied streams, caller-stepped interpreter — agree with both positions' shape, adopt gpt's value details.** A request writer and an outcome stream; request values carry a caller-minted id: `{:dao.jing.dht/id n :dao.jing.dht/op :put :dao.jing.dht/address a :dao.jing.dht/bytes b64}`, `{:dao.jing.dht/id n :dao.jing.dht/op :get :dao.jing.dht/address a}`, plus `:find` for shortlist queries. The interpreter is a `(step! dht)` that reads requests and raw traffic, owns explicit pending-RPC and cursor state, and appends exactly one terminal outcome per accepted id: put → the **local verdict** `{:id n :dao.jing.dht/put :inserted|:present}` emitted as soon as the local backend answers (D3 made structural), get → `{:id n :dao.jing.dht/get :found b64 | :not-found | :error …}`; replication progress is a separate informational event keyed by address and can never retroactively change a verdict. These are DHT-qualified *values* on the outcome stream, while stream operations keep the exhaustive `:dao.stream/outcome` vocabulary (`dao.stream.md:94-96` Result Convention) — gpt states this distinction exactly right. **Differ from gemini** on two specifics: their outcome values carry no correlation id (an address alone cannot correlate concurrent or repeated operations), and `spin-polls/blocks` is not an acceptable adapter mechanism — the repo's established pattern is a portable stepped core plus a **JVM blocking facade** that sleeps between steps with explicit deadlines (`dao.jing.md:436-441` records the precedent for the deleted `dao.jing.remote`; `dao.jing.content.driver` is the current instance, `content.cljc:16`), never a spin loop.

**The dao.jing adapter** (the crux, and where the two positions genuinely fork). Keep the byte-store handle contract (`:put-bytes-fn/:get-bytes-fn/:close-fn`, consumed by `dao.jing/materialize!`, `dao.jing.content`, and `yin.repl.index` at `index.cljc:148-160`) satisfied by an adapter with **three postures**: (1) `put` is always synchronous-and-local — validate (`dht.cljc:155-164`), write `:local`, enqueue the address-only volatile intent, return the verdict; this is honest on every host with no waiting at all; (2) `get` on a local hit answers immediately; (3) a local miss is *staged* on non-JVM hosts — the adapter issues the request, answers the caller per an explicit policy (an outstanding-fetch marker, never a silent `not-found`, gpt's rule), and hydration completes on later steps with the caller retrying the local read. On the JVM only, a blocking facade may drive `step!` to a deadline and return the verified fetch synchronously — preserving today's `make-get` semantics (`dht.cljc:227-252`) for callers that want them. This differs from my consensus round only in *where* the sync surface lives: previously the handle itself did network IO; now the core never blocks and blocking is a facade, which is the better factoring and the one the repo already uses everywhere else. Note what this does for the REPL round: `yin.repl.index` reads back only what it just wrote, so its publish/readback path (`index.cljc:232-252`) stays entirely on local hits — the round never waits on the network even without any facade.

**Unchanged standings:** solo mode is "no raw port composed" (D4); `mem` default, `dht:` explicit, the structural `--dht-publish` gate (D9) — with the gate now enforced at **both** ends gpt names: origin (the store refuses to enqueue replication intent for non-public content while closed) and serving (bootstrap-alone is fetch/serve of already-public content, never originating publication). D7 unchanged: local HEAD covers restart; a reader given only a peer address still needs a supplied manifest address until the root-facts epic exists.
