## Findings (severity | file:line | evidence | correction)

1. **MEDIUM (new in round 3) | `src/cljc/yin/vm/ucf/rows.cljc:351` | the search leaf's key puts the whole root row body under `:label-bytes`.** `search` computes the leaf key as `(checked-key (checked-encode (subvec (get rows id) 1)))`; the root task row body carries the inline `:D` slots (profile, status, custody slot 10, the code map slot 11, slots 14 and 16) and the `:optional-V` result literal in slot 15. These are the input's own bytes, not an intermediate label, yet they are now refused at 1 MiB whenever the task has at least one cell. Probe (both runs): `(rows/emit (task-node [[:x (cell-body :s 0)]] [:lit (vec (range 400000))]))` → `{:status :yin.k/unsupported :kind :resource-limit :path [:label-bytes]}`, while the identical task with **no** cell emits (nil), and the same literal in a `:vec` row or a `:store` row emits and decodes. Custody variant `(assoc slots 16 (vec (range 400000)))` with one cell → the same refusal. Round 2 (bb4a6558) had no byte bound on emit, so this is an accepted-domain regression; decode is affected too, because `decode*` re-runs `emit` for `:noncanonical-cells`, so a 1.5 MiB wire that the 16 MiB `:bytes` budget admits becomes undecodable when it has a cell. Correction (one line, no canonical-byte change): the leaf key is the digest preimage of the root body, bounded already by the task itself (and by `:bytes` on decode); compute it with plain `cbor/encode`/`bytes-key`, or bound it with `(:bytes budget)` instead of `(:label-bytes budget)`. Add a test: one cell plus a ~1.2 MiB inline result literal emits and decodes.

2. **MEDIUM (pre-existing, surfaced by brief question 3) | `rows.cljc:205-209, 259, 290, 326-330` | a `:work` unit costs time proportional to the current label size, so the work bound does not bound time.** Under default budgets at 256 MiB: 7 equal-body cells in one `:set` → `:resource-limit [:work]` after **44 s**; 7 equal-body cells as `:map` keys with distinct literal values → `[:work]` after **35 s**; 10 such map keys → `[:work]` after **748 s** (12.5 minutes) for a wire of a few hundred bytes; 20 and 64 map keys refuse `[:label-bytes]` in 2.4 s and 9.6 s. (The map case never refines because draft §6 step 3 gives a key the position `[kind :key CE(k)]`, which carries no information about its value, so the search must individualize; that is the design as written.) `check-label-bytes!` bounds each label, but `classes`, `refine` and `checked-sort` then compare labels via `bytes-key`, an O(label) boxed vector per comparison, charged one `:work` unit regardless of size. Not introduced in round 3 (rounds 1-2 had the same `:work` semantics), and §10.10 leaves elapsed time optional, so this is not a blocker for this slice; it should be fixed before 6b exposes `decode` to peers. Correction within §10.10's latitude (no canonical-byte change): charge `:work` in proportion to bytes keyed/compared (e.g. `(quot (alength bs) 1024)` per `checked-key`), or add a cumulative `:label-bytes-total` budget.

## Answers

**1. The four round-2 findings.** All closed. (a) Marker-shaped guest maps are refused in every literal context on encode and decode: besides the author's twenty assertions (task result, nested vector, symbol metadata, store value, custody; wire forgeries of each), my probes refuse them in a stream descriptor, nested inside a map value, inside a set literal, as a map key, in vector metadata, in `:bindings` via `frame->rows`, in a `:put` pending value via `frame->rows`, and in a code-map constant. Well-formed markers (`{:yin.k/row (node :prim …)}`) are refused regardless of payload validity (X01 killed). (b) The explicit path round-trips: `bijection` on all reference frames with the test encoder, and the well-formed guest map round-trips under the explicit encoder. (c) No previously legitimate value is refused: two-key maps `{:yin.k/row 1 :yin.k/cell 2}`, the empty map, nil-valued envelopes still round-trip; the only accepted-domain change I found is finding 1, which is the byte bound, not the marker rule. (d) Task-result literals and the `[:identity …]` false duplicate are fixed (X06 killed).

**2. Tagged equality.** Injective by construction: every guest literal is wrapped (`[:literal x]`, `[:seq …]`, `[:set …]`, `[:map …]`, recursively), cells are `[:identity id]`, opaque rows `[:row n]`; a guest value can never spell a bare `[:identity …]` or `[:row …]` because its vectors become `[:seq …]`. Probes: cell vs `[:row {:kind :prim …}]` literal, `:prim` row vs row-shaped literal, `:map` row vs `[:map {…}]`-shaped literal, `:set` row vs `#{[:identity …]}` literal all decode (nil). Genuine duplicates preserved: two equal `:map` rows, `:vec` vs `:list` rows with equal contents, and `[x [1]]` vs `[x (1)]` all refuse `:duplicate-key` (X07 killed by `schema-and-literal-canonicality`). Canonical bytes unmoved: `canonical-roots-are-pinned` passes at HEAD with the three pins (`…be82d50b…` for `(fixture :s1 :s2 :x :y)`, `…c4a7c7e6…` for `(frame->rows ft/worked-frame)`, `…8899f95d…` for the three-cell pin), and X12 shows the test does check them (killed, 2 errors). `checked-sort` keeps `sorted-bytes`' comparator; nothing on the emission path changed a byte.

**3. The `:label-bytes` bound.** The preflight precedes allocation at every intermediate site: initial labels, position encodings, signatures, individualization labels, `checked-sort` comparisons, class keys and the leaf key all go through `checked-encode`/`checked-key`, which size the Clojure value (byte payloads by native length, no copy) before `cbor/encode` or `bytes-key`. The seven-cell fixture refuses at 256 MiB inside the 11.7 s baseline run, as does the whole suite. The one path that still allocates more than the bound suggests is `bytes-key`'s boxing (finding 4), bounded but ~8× and per cell; I found no unbounded path. Realistic sizes: 10, 20 and 64 equal-body cells in a `:vec` canonicalize in ≤ 20 ms; 4-6 equal-body cells in a `:set` or as `:map` keys canonicalize (0.1-3.8 s); two mutual pairs (4 cells) canonicalize; **three mutual pairs (6 cells) refuse `[:label-bytes]`** in 0.3 s, and 7+ equal-body cells in a set or map refuse `[:work]` slowly (finding 2). The default therefore spares ordered and refinement-separable tasks of any size but refuses symmetric structures from six equal-body cells; whether six cursors on one stream at one position arranged in mutual pairs is "realistic" is the Architect's call. The refusal kind `:yin.k/unsupported :resource-limit [:label-bytes]` matches `spend!` exactly. Finding 1 is the one place the bound is applied to the wrong quantity. **Design amendment:** none is *required*. §10.10 adopts a work bound with implementation-chosen limits that must not alter canonical bytes; refusing the seven-cell case is compliant, and the fixture is not a canonicality test. Two things should be recorded before 6b: (i) §10.10's list (bytes, rows, cells, depth, refinement work, search nodes) should name label/signature bytes as a bounded resource and require `:work` to be charged in proportion to bytes processed; (ii) the open question whether the §6 labels should be hashed per round (constant size, no growth bound needed) must be decided knowing it **changes canonical bytes** (class order is bytewise by label) and re-pins all three roots, so it is an amendment, not a fix. The current refusal is the conservative choice.

**5. Scope and portability.** `git diff bb4a6558 HEAD --stat` lists exactly `rows.cljc` and `rows_test.cljc`; `frame.cljc` untouched. Every `assoc` in the diff is single-key or on a map (`(assoc (:slots …) 6 …)`, `(assoc (subvec row 1) 16 …)`, `(assoc ls id …)`); no `for`; no `#'` in source or test.
