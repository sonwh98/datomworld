## 2. Custody consequences of a running root

### 2.1 What a running root is

A machine with `:control {:segment seg :pc pc}` set, `:k` a vector or nil, `:window W`, `:env E`, `:blocked? false`, `:halted? false`, `:value` irrelevant, and `:wait-set []`. The last is an invariant of the kernel, not a choice: every arm of `vm-hot` that creates a wait entry also clears `:control` (`run-effect` `:stop` arm `semantic.cljc:96-97`; `:ffi-call` `:252-254`; `register-restore` `request-sent` arm `:110-111`), and nothing re-sets `:control` while a wait exists except a resume, which first pops the wait or the queue. A machine with `:control` set and a non-empty wait set is therefore malformed, and the lift refuses it as `:yin.k/non-portable :inconsistent-state` (§4.1 R0). The ready queue may be non-empty while `:control` is set (§2.5).

Its canonical state is the assessment's `:run` form, unchanged:

```clojure
{:yin.k/state :run
 :yin.k/segment A  :yin.k/pc n          ; the instruction about to execute
 :yin.k/env E  :yin.k/window {r V …}    ; exactly L(n); nil present as [:lit nil]
 :yin.k/k [ …return frames… ]}          ; no deliver, no pending
```

### 2.2 How the holder pauses it: cooperative preemption at an instruction boundary

Today (`driver/run-cycle` `driver.cljc:2111-2144`): `(vm/run m0)` when the gate is `:running` and the machine is not halted (`:2120-2122`); `require-tenure!` before (`:2118`) and after (`:2123`). `vm/run` is `ffi/maybe-run` over `register-run-scheduler` (`semantic.cljc:271-274`, `:333`), a `run-loop` that steps `(vm-hot % nil)` until the activation parks or halts. A pure loop of a billion instructions holds `run-cycle` for its duration; the next `require-tenure!` throws `:lease-bound`, `step-active` ends the run (`:2252-2253`), the machine is gated `:ended`, and the occurrence is regrantable from its **last checkpoint**, which is the pack this holder lowered. The computation since that checkpoint is lost. This is exactly the violation the owner names.

The change (6d-b item 1):

- `yin.vm.semantic/run-fuel [machine n]`: `(if (engine/active-continuation? machine) (vm-hot machine n) (scheduler-round machine))`, public, telemetry-free; `vm-hot` with fuel `n` already answers `put-registers` at the boundary (`:142-143`). It is **not** `n` calls of `vm/step` (each emits a telemetry snapshot and runs `ready-for-ingress?`, `:331-332`).
- `driver/run-cycle` reads a holder config key `:fuel` (positive integer or nil). With nil it runs `vm/run` as today (no behaviour change for existing compositions and tests). With `n` it runs `(run-fuel m0 n)`: the machine comes back either parked/halted (as before) or **at an instruction boundary with `:control` set**. The cycle continues (replay, emit, reader step) exactly as today; those read the machine's resources and wait set, not its control.
- `cycle-result` (`:2166-2185`) is unchanged: the phase stays `:running`; the next program tick runs another `n` instructions. `require-tenure!` between cycles is the preemption point: tenure dying between two fuel slices ends the run with the machine **at a boundary**, and the holder, instead of losing it, can arm the exit (`hand-off`) **before** the bound. The driver's renewal cadence (half the duration, `:60-65`) already gives the composition a window; the composition picks `n` so that one slice is short against that window. The driver has no clock-to-instruction mapping and should not acquire one (no clock in the VM; `dao.lease` owns liveness).
- `hand-off` (`:1118-1134`) on a machine at a boundary: `arm-exit` → `export/enter` → `prepare`/`encode` → `kind :running`. Nothing else in the exit half reads the kind except through `custody-baseline` and `kind-of`.

**Whether the driver auto-exports at the bound** is a policy knob (§5, decision 2). Recommendation: no automatic export; `hand-off` remains the composition's explicit act (UCF §7.8 "composition-driven, never automatic"), and 6d-b exposes a status detail `:yin.k/at-boundary true` on the holder state after a fuel-exhausted cycle so a composition can decide.

### 2.3 What the source does after the grant

Unchanged from a parked root. The source's driver is a candidate over its own bytes (`driver.cljc:109-112`): it never resumes its local machine on data; it resumes only through a grant to itself. After `enter`, the local machine is gated `:exporting` with `:control` still set and `:wait-set []`; the driver does not run it (`:2120`); `vm-hot` refuses to step it (6d-b item 3); a direct `:resume` is refused (`resume-continuation` `engine.cljc:2359`). `abort` (`export.cljc:578-`) returns the gate to its prior value and the machine continues from the same boundary. On a grant to another holder the source's machine is ended and released as today; the successor occurrence lowers the pack as a `:running` root and continues from `pc`.

### 2.4 Occurrence, lease, fencing, exclusive handoff for a running root

- **Custody slot**: the blocked/parked form (`{:yin.k/policy :yin.k/exclusive :yin.k/occurrence :yin.k/arbitration :yin.k/next-op-seq}` plus `:yin.k/origin` on a successor). A running root is a lease subject: it has a next observable step. `header-custody` (`rows.cljc:1704-1716`) takes the four-key arm for `:running`.
- **Operation ids**: a running root carries no retained write, so `protect!` (`:1719-1737`) checks nothing and `custody-baseline`'s `:yin.k/ops` is empty; `next-op-seq` travels and the receiver's writer continues numbering from it. `:yin.k/issue` numbering (`with-custody` `:2052-2056`) numbers zero waits. The `:op-seq-exhausted` check (`:1769`) applies to a `:running` root as to blocked/parked.
- **Grant on lower**: `check-custody!` (`:2023-2039`) runs `accept-grant!` for `:running` (today it skips only `fenced?` and `:halted`). Evidence, binding, lease, holder, arbitration, epoch, tenure and the input prefix are checked exactly as for a blocked root; the pack address is the carrier's.
- **Offer**: `ledger/offer-defect` (`:277`) and `grant/offer-decision` (`:74-75`) admit `:running`; a `:running` offer is otherwise shaped as a blocked one. The checkpoint inspector follows `custody-baseline`.
- **Gate on restore**: `with-custody` gates the tree `:running` (root not halted). The restored machine's `:control` is set, so the holder's next program tick runs it under the gate: `:stream-put` parks without observing (`handle-put` `:532-533`), `:stream-next` parks (`handle-next` `:677`), `:stream-cursor` mints an unminted cell (`:2654-2656`), `:stream-close` queues (`:754`), `:ffi-call`'s `ffi/put-request` answers `full` so the request is retained for the driver (`ffi.cljc:61-62`). The first effect the resumed computation reaches is therefore the driver's to perform, exactly as for a resumed parked root.
- **In-flight host effects**: none exist at a boundary. Each `vm-hot` arm is one pure function of the pre-state and, where it observes, one observation's outcome inside the arm (assessment §A.5, re-verified: `observe-put` `engine.cljc:495-498` is called from `handle-put` inside `run-effect` inside the step; `:ffi-call` mints the park and appends inside one arm `semantic.cljc:237-254`). An exception inside an arm leaves the loop locals behind and the caller sees the pre-state. Under the `:running` gate the observe halves do not run at all (above). The owner's monad sentence is true of the gated machine and of every retry; the restatement stands: **a step is atomic; effects are observed only inside a step or inside the sweep; every state between steps is pure data.**
- **Successor chain**: the exit mints the successor occurrence once (`exit-mint` `driver.cljc:1137-`), origin names the predecessor occurrence and lease; unchanged.
- **Recovery format 2**: `freeze` stores the pack and the holder-local state (`export.cljc:344-375`); `recovery-metadata` records per-wait issue stamps (zero for a running root) and the gate; `rehydrate-fenced` restores `:control` set, gate `:exporting`, `:yin.k/recovery-waits []`. Re-preparation must reproduce the pack byte for byte, which holds because the `:run` frame is a pure function of the restored fields.

### 2.5 The exporting phase and the quiescence rule

`export/enter` (`export.cljc:121-149`) requires, in order: not already exporting/ended; **empty ready queue in every task of the tree** (`first-refusal` `:107-114`); no hold (`refusal-at` `:83-104`: `:observe`, `:held`, `:unminted-cursor`, `:pending-close`, `:link-cursor-not-installed`). It then sets the gate, empties the wait set and the parked map into the record. For a running root nothing is detached (no waits); the parked map still moves (a running root may hold parked records reachable by `:resume`). `lift-task*` repeats the first two refusals (`:1652-1655`) and keeps them.

**The ready queue stays a refusal.** The assessment's §B.1 reasoning holds: a woken entry is a performed effect's result (a woken `:put` has appended; a woken `:next` holds the successor cursor in `:resource-updates`, `make-woken-run-queue-entries` `engine.cljc:442-463`) that no row kind carries, and the engine never leaves one at rest in its own API. One correction to the assessment's "a caller crosses it with one `vm/step`": that is true when `:control` is nil (`vm-hot` runs `scheduler-round`, which pops the first entry, `:2315-2326`). When `:control` is set, `vm/step` executes one instruction of the active activation and the queue is untouched; it drains only when the activation parks or halts and `run-loop` reaches the `(seq q)` arm (`:2216-2218`). So a running root with a non-empty ready queue lifts only once its activation has parked and the queued entry has been resumed, which is `vm/run` to the next park. Organically this needs two waiters woken in one sweep (the harness's `two-callers`, `:1069`); an organic one-control machine has at most one waiter and the queue is empty whenever `:control` is set. The holder under fuel sees this case only in multi-waiter machines; `hand-off` then answers `:yin.k/not-quiescent` and the composition retries after the next cycle, as it does today for a queue it observes. No `:ready` row kind (as before).

**Nothing about parked roots regresses**: every refusal above applies to parked roots unchanged; the only parked-root behaviour that changes is that `kind-of` and the kind tables gain a branch that parked roots never take.

### 4.4 Node and Dart considerations (all slices)

- **Determinism of the stepping driver.** A is host-independent and `vm-hot` executes one instruction per fuel unit on every host, so the step count to a park is identical across hosts; the pinned counts of item 4 are asserted on all three. ## 5. Risks, and what the owner must still decide

**Risks.**
1. **A liveness bug surfaces at a pc no park ever looked at.** If `L(p)` under-approximates anywhere, law 1 fails at that pc. That is a finding, not a slice risk; it is the main reason to run the every-pc laws. Mitigation: none wanted.
2. **Register-target refusals dominate law 5 (6e).** Mitigation: the allowlist equality assertion (§4.3).
3. **Slow-tier time.** Thousands of lift/lower/run triples on Dart. Mitigation: slow tier only; the quick sample; measure once at 6d-a landing and record the wall time in the ledger row.
4. **Fuel too small or too large.** Too small and the holder's per-tick overhead dominates; too large and preemption is late. The driver cannot know; it is a composition knob (decision 1). Mitigation: a default of nil (today's behaviour) so nothing changes until a composition opts in.
5. **The `vm-hot` gate guard** is an engine edit outside the hot loop; a reviewer must confirm it costs one map read per `run-fuel` call, not per instruction.
6. **Module-pins commit 2** lands between 6d-a and 6e and re-mints every root; 6d's own fixtures pin step counts and refusal kinds, not root ids, so the re-mint is a rebase, not a redo. Keep it so in the briefs.
7. **Row grammar choice** (decision 3): reusing slot 13 for the `:run` cref keeps every existing root id; a new slot re-mints every fixture in the tree. Recommended: reuse.

**Decisions for the owner** (none blocks 6d-a; defaults stated so work proceeds):
1. **Fuel as a holder config key**, default nil (no change for existing compositions). Recommended as stated.
2. **No automatic export at the lease bound**; `hand-off` stays the composition's explicit act; the driver only reports `:yin.k/at-boundary`. Recommended; the alternative (the driver arms the exit when tenure is below one renewal interval) is a composition policy that belongs in `compose`, not the driver, and can come later without changing the carrier.
3. **The `:run` cref lives in root slot 13** (`frames`, `[:refs :wait :run]`), kind rule "exactly one, a `:run`"; no new slot. Recommended.
4. **Q6** (continuation §11): keep edge-reachability liveness and pin the pre-branch false refusal (§4.1 item 6). Recommended; a "no" means a constant-propagation pass in `live-pcs`, which is a new static analysis and a separate slice.
