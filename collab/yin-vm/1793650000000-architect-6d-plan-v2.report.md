## 3. Plan v2

### 3.1 State model: the task-state product

**Task** (one machine of the tree, root or install child):

```
task = ( kind,                      ; :running | :blocked | :parked | :halted
         run?,                      ; the active activation ⟨A, pc, W↾L(pc), E, K⟩, iff kind = :running
         waits  = [wait …],         ; ordered pending waits (any kind but :halted)
         ready  = [ready …],        ; ordered completed wakes, scheduler outcomes (any kind but :halted)
         parked-table, result?, parked-id?,
         store, module-stores, cursor-cells, free-env, id-counter, requires, code, installs, custody )
```

**Kind rules** (replace tuples §5.5 / continuation §2.6; the machine-side predicate in the lift, §3.2):

| kind | machine | frames (waits) | run | ready | parked-id | result |
|---|---|---|---|---|---|---|
| `:running` | `:control` set | 0..n | exactly one `:run` | 0..n | none | none |
| `:parked` | control nil, `:value` a parked record the table holds | 0..n | none | 0..n | names a table key | none |
| `:blocked` | control nil, not parked, `(or (seq waits) (seq ready))` | 0..n | none | 0..n (waits+ready ≥ 1) | none | none |
| `:halted` | control nil, `halted-with-empty-queue?`, no waits | 0 | none | 0 | none | one |

A machine with `:halted? true`, a non-parked value and a non-empty queue (one activation of a multi-waiter machine halted while a wake is queued) is kind `:blocked`: `run-loop` resumes the queue before it reads the halt (`:2216` before `:2219`) and the next halt overwrites `:value`, so the halt value is dead by the kernel's own order; restore gives it `:blocked? true :halted? false`, which `run-loop` treats identically (no waits wake; the queue pops). Law 1 and law 2 hold on it and the harness pins the case (§3.9 6d-a item 6).

**Row grammar** (`rows.cljc` `row-table`; two new row kinds, two new task slots):

```
:run    [:A :N [:ref :env] [:ref :window] [:ref :k]]          ; five slots; no deliver, no pending
:ready  [[:ref :wait] :V :D [:ref :cursor-cells]]              ; the wait it completes, value, status, cursor updates
:task   [… slot 13 [:refs :wait]  14 :optional-D  15 :optional-V  16 :optional-D   ; unchanged
           17 [:refs :run]        ; 0 or 1, by kind
           18 [:refs :ready]]     ; 0..n, in queue order
```

- `:run`: `pc` is the instruction about to execute (`0 ≤ pc < count v`); the window is exactly `L(pc)` (`analysis/live`), nil present as `[:lit nil]`, sorted on the wire; `K` as for an `:act`.
- `:ready`: its `[:ref :wait]` is a `:wait` row (state `:act`/`:tail` + pending), judged in context `:wait` exactly as a pending wait; `:V` is the woken `:value` (for a `:put` the appended datom; for a `:next` the element read, or the shaped refusal map; for an FFI response the response map, the entry's `:call-id` riding the pending as today); `:D` is the `:status` keyword, carried verbatim so the receiver's `terminal-resume-outcome` raises exactly as the source would have; `[:ref :cursor-cells]` is the entry's `:resource-updates`, a pairs row of `C → cursor-cell-body` over cells of the task's census (a `:next` wake advances one cell; a `:put` wake has none: empty row). The entry's redundant `:cursor` field is not carried (resume reads `:resource-updates`, `engine.cljc:2299`, `:2307`). Reasons admitted in a ready row: `:next`, `:put` (an FFI response is a `:next` on the response cursor); any other reason in the queue refuses `:yin.k/non-portable :ready-reason` and is pinned (6d-a verifies by reading `poll-links` whether link wakes ever enter the queue; today they restore directly).
- Why two new slots rather than a mixed slot 13: every slot-13 traversal (`task-ops` `:1263-1277`, `protect!` `:1725-1727`, `check-pendings!` `:1873-1876`, `lower-defect` `:947-948`, restore's entry mapping) reads wait rows positionally; a `:run` or `:ready` row in the same list is exactly F7's silent-misread class. Separate slots leave those traversals untouched and give the new rows their own. Cost: every task row's bytes change, so every pinned root id re-mints once. Module-pins commit 2 re-mints them all anyway and is merging now; 6d-a lands right after and re-mints once more. Decision 1 (§3.10).

**Validator** (`frame.cljc`), in the existing order:

| # | Rule | Kind |
|---|---|---|

### 3.3 Custody and lifecycle of a running root

**A running root under a lease.** Full custody slot (policy, occurrence, arbitration, next-op-seq, origin on a successor); `accept-grant!` on lower; gate `:running` on restore; offerable by `ledger/offer-defect` (`ledger.cljc:277`) and `grant/offer-decision` (`authority/grant.cljc:74-75`) once both sets list `:running`; `protect!` checks its retained `:put` waits as for a blocked root (there may be some: F2). The restored machine's first effect parks under the gate (`handle-put` `engine.cljc:532-533`, `handle-next`, `ffi/put-request` answering `full`), so the driver performs it; unchanged from a parked root.

**Four outcomes, specified separately.**

1. **Preemption under live tenure** (the normal path). `run-cycle` runs `(run-fuel m0 n)` when `:fuel` is set (§3.4); the slice returns a machine parked, halted, or at a boundary. The cycle continues (replay, emit, reader step) exactly as today; `cycle-result` leaves the phase `:running` and adds `:yin.k/at-boundary true` to the status detail when `(:control m4)` is set. The composition calls `hand-off` (`driver.cljc:1118-1134`) when it wants to export: `arm-exit` → `export/enter` (its `first-refusal` queue check is deleted; holds remain) → the exit steps mint, prepare, encode (`kind :running`), journal the fence, freeze the recovery object, offer. Only a live-tenure holder reaches `exit-mint` (`:1144`). This is the path that closes the owner's invariant for the holder: a long pure computation is interruptible at every `n` instructions and exportable there.
2. **Tenure dies after a completed slice** (at `:2123`, inside replay/emit/read, or at the next entry's `binding-check`). 6d-b restructures `run-cycle` so each stage's product is assoc'd into the state **before** the next tenure check (`(-> state (assoc :machine m1) require-tenure! …)`), and `step-active`'s catch ends the run on the state it was handed, which now carries the newest completed pure stage. `end-run` gates the machine `:ended` as today; the ended state additionally carries `:yin.k/retained-boundary {:yin.k/pc … :yin.k/segment … :yin.k/steps-since-checkpoint k}` for inspection and diagnostics. **No adoption**: an ended holder holds no tenure, so `exit-mint` refuses, `abort` refuses `:tenure-ended`/`:tenure-unconfirmed`, and the retained bytes are never offered or resumed. Why retention is safe: under the `:running` gate the slice performs no external observation (effects park; FFI requests are retained for the driver), so `m1` is pure local progress; retaining it loses nothing and discloses nothing.
3. **Expiry and recovery.** The occurrence is regrantable from its **last durable checkpoint**: the pack this holder lowered, or the last successor it published. The successor relowers it (`step-validating` `:2291-2316`, awaiting-grant for a running root as for a blocked one), `accept-grant!` checks the input prefix and `next-op-seq`, and the writer replays retained writes idempotently by op-id (UCF §7.4.3). **Progress since that checkpoint is lost**: pure computation, and effects performed since (they are durable on the streams and will be re-performed only if their op-ids say they were not). Fuel does not repair this; only exporting before the bound does (outcome 1). The documents say so in those words (§3.7).
4. **Reopen** (`rebuilt-cell`, `reopen-source`): a fenced snapshot of a running root rehydrates with `:control` set and gate `:exporting` (`rows/lower-task {:fenced true}`); `rehydrate-fenced` re-prepares and must reproduce the pack byte for byte (a `:run` frame is a pure function of the restored fields; the ready list likewise). The kernel refuses to step it: `vm-hot` gains the entry guard `(when (contains? #{:exporting :ended} (vm/gate-mode machine)) (fail "Gate is closed" …))` before the loop (`semantic.cljc:137`), one map read per call, not per instruction; `run-fuel` inherits it. Today the guard is moot for parked roots (control nil → `scheduler-round`, which observes nothing under a gate); for a running root it is what makes "the exporting machine is pure data" (UCF §7.7.4) true.

**Auto-arm before the bound** (decision 3): recommendation is **not in 6d-b**. `hand-off` stays the composition's explicit act (UCF §7.8); `:yin.k/at-boundary` is the signal. A later policy "arm the exit when remaining tenure is below one renewal interval" needs only `lease/holding?` and the clock the driver already reads (`:2060-2063`), no clock-to-instruction conversion, and can live in `compose` without touching the carrier.

**Tests (6d-b)**: clock-controlled cuts (a) immediately before the slice, (b) immediately after it (the `:2123` check), (c) in replay, in emit and in the reader step, (d) between two slices at the next entry's `binding-check`, (e) during `exit-mint`/`prepare`/`offer` of a running root; in each: the source is fenced or ended, no effect was performed past the bound, and **either** a durably authorized successor exists (the offer was accepted under live tenure) **or** the recovery checkpoint is the last pack and `:yin.k/retained-boundary` reports the lost steps; byte-equality of `rehydrate-fenced` for a running root with waits and with a ready entry; two competing candidates for a `:running` offer; stale-source stepping refused by the gate guard; `abort` with uncertain offer refused; expired-grant admission refused.

### 3.4 Fuel and budget propagation

**`yin.vm.semantic/run-fuel [machine n]`**, public, `n` a positive integer:

```
(ffi/maybe-run machine
  (fn [m]
    (if (engine/active-continuation? m)
      (vm-hot m n)                       ; ≤ n instructions of the active activation
      (scheduler-round-fuel m n))))      ; one sweep, children budgeted, one resume
```

- `vm-hot m n` already materialises the boundary at exhaustion (`semantic.cljc:142-143`).
- `scheduler-round-fuel m n` = `check-wait-set` with `advance-installs` taking the budget: each install child is stepped with `(run-fuel child n)` instead of `(vm/run …)` (`engine.cljc:1475`); a child that returns with `:control` set is stored at phase `:running` (the existing `:else` arm, `:1490-1491`); a blocked child `:parked`; a halted child goes to `link-install` as today. Then `resume-from-run-queue` once. **Per-tree bound**: each task of the tree executes at most `n` instructions per program tick, so a tick is at most `n × (tasks in the tree)` instructions plus the sweep's scan plus the host seams listed below. Nested install children are tasks of the tree and get the same `n`.
- `ffi/maybe-run` (`ffi.cljc:334-348`) loops bridge steps while the machine is blocked and a handler answered; each loop costs another slice; the bridge step itself is a host seam.
- `vm/run` and `vm/step` are unchanged (`vm/step` keeps its telemetry snapshot; `run-fuel` emits none per slice, but parks and resumes inside it emit as today).

**The honest guarantee** (goes into the documents verbatim): *Fuel counts completed instructions. A holder with fuel `n` is interruptible at the boundary after at most `n` instructions of each task of its tree per program tick. No wall-clock bound is claimed for one instruction: a `:call` of a host function (`semantic.cljc:193`), a stream constructor (`engine.cljc:480`), a bridge step, one scheduler sweep, and a `:var` resolution are atomic host seams whose duration the VM does not control. The VM has no clock and converts no time to instructions; `dao.lease` owns liveness; the composition picks `n` against its renewal interval.*

**Running install children in the carrier**: a child with `:control` set lifts as a `:running` child task (same walk); wire phase `:running` ↔ child kind `:running`; `check-install!` admits it (§3.1); receiver admission per child is unchanged (`check-modules!` after module-pins); a running child restores with its control set and continues in the next sweep; the de Bruijn backends refuse installs as today. Tests (6d-a item 8): a long initializer preempted mid-body, lifted, lowered, continued to `linked`; a nested initializer (child of a child); handoff while a child is running (6d-b).

### 3.5 Stack layouts at control-flow pcs; the register side

**Static layouts** (`layout.cljc` `stack-layouts`, 6d-a): for a parse node `:if` at `b` with jump pc `j`, result register `rd(if)` (the `rd` the arms define; the emitter writes both arms to it, `derive.cljc:81-85` for H, the A linearizer for the register), define `layout(j) = layout(b) ++ [rd(if)]`; for a terminator pc (`:return r`, `:halt r`) define `layout = []`; every other pc as today. Then at every pc inside a body:

```
ordered:  region(p) = layout(p) ++ [W[u] for u in uses-in-order(p)]        ; emitter order (derive.cljc:92-97): :call operator then operands, :ffi-call operands, :stream-put target then value
set:      (set layout(p)) ∪ (set uses(p)) = L(p)   for every reachable non-tail pc
          (set uses(p)) = L(p)                     for every reachable tail-call pc
```

The ordered form is the check (duplicates `(f x x)` are two positions holding one value; the lift asserts they agree). `jump` and `branch-false` pcs: branch pc keeps the ancestors' layout (`uses` is the test, which H pops); jump pc as above. **`:push` pcs of H**: canonicalised, not refused: `stack-layout` at a `:push` is undefined because it is no A pc; the kernel state at a `:push` equals the state at its successor except pc (`stack.cljc:722-723`); `h->a` maps `hpc` to `h->a(hpc+1)` when `hpc` is a `:push` (never two pushes in a row, `correspondence` `:97-108`); the lift relabels, running nothing; laws 4/5 compare at the aligned A boundary. The design calls this a stutter of the stack backend, not a property of A.

**Dead prefix (tail residuals)**: a tail `:call` consumes `f` and its args and keeps the rest of the region (`stack.cljc:731`, `:747`) without pushing a frame (`:737-738`). Hence inside a body entered by a tail call, and transitively, the current activation's region and any later frame's slice may carry a **dead prefix** below the layout: values the ambient layout syntax pushed, never read again (every H read is top-relative: `:call` by `f-pos` from the top, `:branch-false`/`:return`/`:halt` peek; `return-transition` truncates to `stack-base`, which includes the prefix, and the prefix stays dead). Rule: `lift-stack` takes the **top** `|layout(p)| + |uses(p)|` values of the current region and the top `|layout(pc_i − 1)|` of each frame's slice and drops the rest (`slice-window`'s count equality becomes `≥`, with the excess recorded as `:yin.k/dead-prefix n` in the lift's diagnostics, never in the frame); `lower-stack` produces no prefix and recomputes bases cumulatively (`stack-k` `:635-651` already does). Unobservable: law 1 on continuing to the reference result; law 2/4 since the relift of the lowered kernel has no prefix and the canonical form never had one. **6e item 6** either exhibits a lane-fragment case with a non-empty ambient layout at a tail call (then the rule is exercised) or proves by the static check `layout(p) = [] at every tail-call pc of the fragment` that none exists (then the rule is pinned on a hand-built vector). Both are acceptance, not open design.

**Register side**: `allocation` gives distinct slots to virtuals both in `L(p) ∪ def(p)` (`derive.cljc:127-130`), freeing only when the interval end `< pc` (`:140-143`), so `virt(p, s)` over `L(p)`'s image is single-valued at every pc; `register-window` over `L(p)` for a run; `write-back`-style nil fill outside `L(p)`. Unchanged from v1; the review concurs; it is still a check (§3.9 6d-a item 7).

### 3.6 Harness order, worlds, oracle, coverage

**Order per point** (reference lane, 6d-a; backends, 6e): at boundary `S_i` of the stepping source: (1) **lift**; (2) **lower** into a fresh receiver of an **isolated world** (§ below); (3) **immediate relift** of the receiver and **law 2** (`canonical-under` root equality with the lift; no execution in between); (4) **law 6** on every lifted frame (plus the two window tampers); (5) **run the receiver to the end** in its world, **law 1** (result and effect trace equal the reference's, after `normalize`'s fresh-identity correspondence); (6) negative controls kept: cursor positions and descriptors, windows and lexical values tampered are refused or differ as today.

**Isolated worlds**: each point builds the receiver's composition and streams fresh from the case's **deterministic script** (the same scripted inputs the reference run saw, fed to the receiver's own streams); the stepping source's world is never shared with a receiver; fresh identities normalise through the existing correspondence (`normalize`, `:238`). The reference result and trace are computed once per case on a pristine world.

**"Every pc"** means every boundary of the chosen executions (the stepping driver's `S_0 … S_end` for each case and each wrapper), not every CFG-reachable pc nor every possible activation. Coverage is pinned by `(segment-address, pc, structural-class)` where the class is one of: body entry, branch taken, branch untaken, jump, non-tail call, return, tail transition, capture (`:current-continuation`), resume, park, FFI park, scheduler product (active + waits, active + ready, blocked + ready), install child running; the harness asserts each class is reached at least once on the corpus and pins the point count per case per host. The static all-pc checks (§3.5) and the dynamic pass are complementary; neither proves a universal theorem and the docs say so (§3.7 "claims that are checks").

**Refusal oracle (6e)**: for each case and point, the expected register-target refusal is computed by an **independent traversal in the test** over the decoded task: any `:prim` row reachable from the `run`'s window or lexical bindings, from any `K` frame's window or bindings, from any wait's or ready's state, or from any parked state. Assert per direction: exactly the expected points refuse `:yin.k/unsupported :continuation-registers` before any attach (attach count zero), and **every other point transfers** and continues to the reference result. The other obstructions (image collision, installs, free-env procedure, retained FFI) are asserted on their existing fixtures and stay in the documented limit list.
