# Integral-float kind preservation on JavaScript

**Decision: this is a runtime correctness defect in the source-to-VM portability claim. Fix it in the source frontend, before numeric token kind is lost. Select option (b): frontend-owned, token-aware source ingestion and lowering. Preserve Jing's existing numeric contract and representation. Old artifacts retain their recorded meaning; repairing their compilation requires new artifacts.**

The r2 acceptance of a narrowed collection-order corpus was a scope boundary, not acceptance of the numeric defect. This ruling supersedes any reading of “encoder/float-carrier territory” as a diagnosis that the encoder should infer the lost kind. It does not retroactively reopen that bounded collection-order decision or authorize work now.

## Evidence re-derived

1. `src/cljc/dao/host/integer.cljc:66` classifies safe integral JS Numbers, except negative zero, as exact integers. `src/cljc/dao/jing/cbor.cljc:201–220` also recognizes unsafe integral Numbers for refusal and distinguishes floating content. `number-bytes` at line 748 emits integer content or refuses an unsafe integral Number before its float branch. JVM `Double` is float content, even at `1.0`. `cbor/float64` at line 242 delegates to `dao.host.number/float64-of`, whose JS carrier preserves the distinction. This matches `docs/design/dao.jing.cbor.md:387–425`; the codec is conforming.
2. `src/cljc/yin/vm/data.cljc:513–536` makes float and exact-integer `data/equiv` mutually exclusive, recursively. Its `admit-key?` at line 538 refuses float content and admits exact integers. `data/content=` and Jing `content=` are kind-strict. `src/cljc/yang/clojure/core_impl.cljc:256–261` dispatches `inc`/`dec` to `float/add`/`float/sub` or integer operations according to `data/float64?`. `clj/collection-key` in `src/cljc/yang/clojure/prelude.cljc:225` applies the key admission policy. These are observable semantics, independently of hashing.
3. `yang.clojure/compile-literal` at line 766 merely puts its argument in `{:type :literal :value ...}`. `compile-quote` does the same for quoted Data. There is no lexical provenance from which either can distinguish two bare JS Numbers with value 1.
4. The explicit source entry `yang.clojure/read-forms`, at line 2135, uses **`cljs.tools.reader`**, not an in-repository Clojure lexer. JVM uses `clojure.tools.reader`. These are upstream `org.clojure/tools.reader` code; `deps.edn` declares 1.5.0. I inspected the locally available 1.5.0 and 1.5.2 jars: `cljs/tools/reader.cljs` reads a token and calls `match-number`; `cljs/tools/reader/impl/commons.cljs:79–95` selects float syntax and returns `js/parseFloat`. It knows the distinction temporarily and discards it in its result. A general tagged-literal hook does not automatically intercept ordinary numeric literals.
5. **There is another source entry.** `yin.repl/read-forms`, `src/cljc/yin/repl.cljc:1333`, uses `cljs.reader` on JS and `clojure.core/read-string` on JVM. The standard Clojure binding in `src/cljc/yin/repl/frontends.cljc:135` is `:input :forms`, with `:parse identity`. `compile-input`/`compile-source` therefore pass already-read forms. Fixing only `yang.clojure/read-forms` misses the normal REPL. `yin.repl.adapter` also reads for command detection, but forwards ordinary remote input as its original string; its command sniffing must not be confused with compilation.
6. **There is a carrier-admission gap.** `yang.clojure/literal?` and `constant-form?`, lines 270–301, recognize numeric scalars through host `number?`. Jing's JS Float64 is a `deftype` carrier, not a JS Number. Directly supplying that carrier to the normal forms compiler can reach “Cannot compile unknown form type” at line 1840. Carrier insertion therefore requires bounded compiler admission work as well. The VM Data API, raw UAST literal constructors, and the forms compiler are distinct APIs; a working carrier in the first two does not prove acceptance by the third.
7. Python already boxes float tokens in `src/cljc/yang/python/antlr/lower.cljc:350–363`; PHP does so in `src/cljc/yang/php/antlr/lower.cljc:310–315`; TypeScript boxes Number tokens in `src/cljc/yang/typescript/antlr/lower.cljc:428–440`. TypeScript BigInt is a separate case: “every numeric literal” here means Number literals, not BigInt literals. Python/PHP distinguish integer syntax from float syntax; TypeScript Number `1` is intentionally float64 content. Uniform representation does not mean uniform language rules for spelling `1`.
8. Host-compiled quoted `.cljc` prelude data can lose kind independently of the runtime reader. The JVM build reader can retain Double initially, but the emitted JS literal is still a bare Number. `yang.core.defquoted` is not a general numeric-preservation pass. TypeScript's explicit `(data/float64 1)` convention and Python's existing float-address discipline address that producer boundary; changing a runtime source reader cannot retroactively repair already-compiled quoted constants.
9. **Carrier-aware arithmetic is profile-specific.** `src/cljc/yin/vm.cljc:420–440` still binds the base `+`, `-`, `*`, comparison and equality primitives to host functions. The `inc`/`dec` evidence above is the Clojure library path, not a claim that every base primitive dispatches by Jing kind. `core-source-name` in `yang.clojure.cljc:868` is conditional on the outcome/library convention. Boxing a literal does not by itself make bare host arithmetic portable; on JS the carrier deliberately refuses numeric coercion. This is a necessary integration gate, not a reason to erase kind again.

## RULING 1 — Impact and responsibility

**Normative:** yin.vm's source portability claim MUST treat loss of intended numeric kind as a correctness defect, not merely an address or traceability defect. Identical source text MUST NOT silently acquire integer semantics on one supported compiling host and floating semantics on another. A portable VM interpreting correctly encoded Data does not absolve a frontend that supplies the wrong Data.

| Surface | Concrete impact and boundary |
| --- | --- |
| Source text and source forms | Bare `0.0`, `1.0`, `1e0`, negative integral floats, and floats rounded/underflowed to integral values can become integers on JS. Unsafe integral results can be refused instead of compiled. This affects top-level literals, arguments, definitions, quoted data, and nested collection contents. Once an external reader has supplied only Number 1, the forms API cannot know whether it originally read `1` or `1.0`. |
| Public host-Data APIs | An unboxed JS Number 1 already denotes integer content under the contract. A caller intending float content must supply `cbor/float64`/`data/float64` before crossing the boundary. Correctly boxed VM inputs are representable today. The forms compiler's additional carrier-admission gap must be fixed; do not advertise direct carrier forms as working everywhere today. |
| Runtime equality and dispatch | For intended float `f = 1.0`, `data/equiv(f, 1)` is false; after collapse it is true. The same distinction recurses through vectors and maps. `inc(f)` takes the float branch and returns float content; collapsed 1 takes the integer branch. A matching printed result, such as 2, is not a sufficient oracle. |
| Collections | Key admission can change from float refusal to integer acceptance. Lookup, membership, collision behavior, and constructor operand ordering can consequently differ. A host reader may already coalesce integer/float keys or set members before compilation. This ruling does not grant float-key support to Clojure-family collections: existing refusal policy remains. Do not assert that all maps universally support both keys merely because Jing distinguishes the scalar contents. |
| Prelude/library code | Host-quoted numeric constants, macro-generated forms, and library constructors are producers too. A runtime reader fix does not reach them automatically. Explicit float constructors remain necessary where those producers otherwise lose information. Float-producing arithmetic must rebox before a value is exposed, stored, captured, or resumed. |
| Stored artifacts and cross-host reload | A JS-produced artifact containing integer 1 reloads as integer 1 on JVM. It is not healed by the destination reader. A JVM-produced float artifact decodes to a Float64 carrier on JS and retains float kind. The defect is usually different artifacts produced from the same source, not the decoder randomly changing a fixed artifact. Existing profile/ABI compatibility requirements still apply. |
| Canonical addresses and provenance | Integer and float literal bytes differ; ancestor UAST roots, compiled-content ordering, call-site keys/C1 relations, format projections, modules, and addressed state can differ. Source-text identity can remain identical while derived forms differ. Sorting cannot repair wrong child content. |
| `content=` | `content=(float64(1), 1)` is false by contract. A collapsed source `1.0` produces true against integer 1 on JS. Canonical equality must remain kind-strict; weakening it would hide the defect and alter valid programs. |

The distinction between `data/equiv` and `content=` also remains: floating positive and negative zero are `data/equiv`, but not `content=`; NaN is not `data/equiv` to itself, while canonical NaN content has one identity. The repair MUST NOT conflate these relations.

## RULING 2 — One fix layer: frontend-owned lexical preservation (option b)

**Normative:** the Clojure source frontend MUST preserve the original numeric token's kind while source text is available and produce Jing float64 Data for every supported binary floating literal, including integral-valued ones. On JS, all such float literals MUST use the existing carrier, including non-integral values. Integer literals MUST remain exact integers under their existing supported range/carrier rules. No test of a bare Number's value can reconstruct the missing distinction.

Choose **(b), frontend-owned token-aware source ingestion**, generalized from the ANTLR frontends' producer rule. “Reconstruction” means interpreting the retained original token, not guessing from the output of an ordinary reader. It MUST occur before host maps/sets or downstream lowering can destroy occurrences. A value-keyed table, postwalk of already-read Numbers, numeric printing round-trip, or textual regex substitution over arbitrary source is insufficient.

The frontend may retain token spans/kinds in a transient parse structure and materialize carrier Data from them. It need not adopt ANTLR or replace the whole Clojure grammar. A scoped source-reading adapter can be the implementation of this frontend-owned stage, but it MUST consume the original lexical information; changing the meaning of the process-wide host reader is not the selected architecture. The engineer must demonstrate lexical coverage and occurrence preservation before selecting a minimal mechanism. The ruling does not pre-authorize a full parser rewrite.

All source compilation routes, including REPL compilation, MUST reach this stage or supply equivalent already-kind-preserving forms. Retain the original source text and source locations for provenance. Reader support and refusal behavior must be explicit for comments, strings, character literals, quote, metadata, dispatch forms, discarded forms, and any currently supported conditional syntax. No evaluation during reading and no ambient mutable reader registration. Token kind is derivable from source and need not become a new persisted UAST field or Jing tag.

Alternatives:

| Option | Ruling and reasons |
| --- | --- |
| (a) Change the upstream cljs reader/toolchain to return Float64 | Rejected as the primary repair. The readers are not ours; changing ordinary numeric results across upstream `cljs.tools.reader`, `cljs.reader`, and host compilation affects unrelated application code, host arithmetic, and macros. A change to one reader misses the others and precompiled quotes. A future upstream token-preservation API could help implement (b), but is not a dependency or authorization for global reader semantics changes. |
| (b) Frontend owns lexical preservation and emits the carrier | Selected. It acts where syntax still identifies the kind, is independently versionable, follows the existing Python/PHP/TS pattern, and leaves the codec and consumers' Data interpretation intact. It includes the source-ingestion boundary, not just `compile-literal`. |
| (c) Change canonical CBOR for integral JS Numbers | Rejected for this defect. A bare Number supplies no fact distinguishing intended integer from float. Encoding all such Numbers as float breaks legitimate integers; encoding all integral floats as integers breaks the established four-kind model and JVM/Dart meaning. A new explicit marker would merely duplicate the existing Float64 carrier. A deliberate future codec round is possible, but cannot recover absent source information and has an unnecessary consumer-wide migration radius here. |
| (d) Source discipline only | Rejected as closure of source portability. Requiring every user to rewrite `1.0` is an honest temporary restriction, not a working frontend for supported float syntax. Explicit constructors remain the permanent, correct contract for already-materialized host Data and generated/precompiled code whose original syntax is unavailable. |

**Cross-frontend uniformity:** all four frontends MUST meet the same producer invariant, while retaining their language's numeric syntax and selected semantic profile. Python's tagged native float payload must still be float64 internally; its Clojure profile can emit bare float64 content. PHP float tokens remain float64; TS Number tokens remain float64 and BigInt tokens remain integers. The new Clojure path brings its float tokens into the same representation. It does not promise that `1` means float in all languages or that unlike language profiles have identical program roots.

**Forms and prelude obligation:** the forms compiler MUST admit existing numeric carriers as literal constants, including nested/quoted positions, and preserve them. It MUST NOT reinterpret an unboxed Number 1 as a float. Library/generated forms without token provenance must use explicit constructors or a kind-preserving source/build path. Audit host-quoted prelude constants on a host that still distinguishes Double from integer; a JS-only scan after loss cannot establish absence. Fixing only the source reader is not sufficient acceptance.

**Execution obligation:** the repaired portable frontend/profile MUST route its supported floating operations through carrier-aware numeric operations/adapters, with results reboxed before becoming guest Data. The authorized round must inspect the default REPL and plain-compile bindings as well as linked/library paths. Do not feed newly boxed floats to raw host `+` and call a coercion exception a completed portability repair. Prefer the existing explicit float/integer modules and scoped frontend/runtime bindings; do not change the global legacy primitive table or Float64 coercion policy incidentally. Any raw-host profile retained unchanged must retain its explicit limitation and immutable identity. Supporting the affected floating operations under the new portable profile is part of acceptance; a broad legacy arithmetic overhaul is not implied.

## RULING 3 — Migration, legacy loading, and revisions

**Normative:** newly compiled affected JS artifacts MUST be re-minted under a new Clojure frontend revision and a revised lowering/support profile. The current `:yang/clojure` manifest is revision `"c1-2"`, lowering profile `:yang.clojure/constructed-collections-v1`, in `src/cljc/yin/repl/frontends.cljc:44–61`. Do not publish repaired semantics under those unchanged identities. The replacement profile must retain the constructed-collection ordering contract as well as add numeric-kind preservation; exact new names are for the authorized implementation round.

The revision is a portable frontend identity, not a Node-only variant. Publish the same revised frontend contract on supported hosts. Source-reader/tokenizer implementation identity belongs in the existing compilation derivation; expose accurate source-text versus forms-only capabilities. JVM/Node source reading and Dart/Jolt forms execution must not be mislabeled as four identical parser capabilities.

- **Expected one-time bytes shift:** JS compilation of affected floating source changes literal content from INTEGER to FLOAT64 and changes its dependent address closure. Unsafe-integral-number failures can become valid float compilations. Correct JVM float literal bytes and already-correct Python/PHP/TS float bytes should remain unchanged. Unaffected integer-only and already-correct scalar artifacts must stay byte-stable unless a separately explained dependency or provenance record changes.
- **JVM changes are not categorically zero:** frontend manifests/derivations change with revision. Corrected source collection preservation, or a repaired shared prelude/library, may also change JVM artifacts. Inventory these explicitly; do not justify arbitrary churn by calling it a JS fix. Original source text is unchanged; a canonical read-form input address may change when its previous kind was wrong.
- **Legacy loading:** preserve old bytes and addresses. Continue loading/executing old integer-bearing and float-bearing artifacts with their recorded meaning and compatible pinned runtimes. Do not rewrite integer rows on load, alias old addresses to corrected bytes, or claim an old JS integer artifact was always a float. Recompilation from authoritative source under the new frontend yields a new artifact and a derivation relating input, interpreter revision, and output. If source is absent, recovery of intended kind is not generally possible.
- **Other frontends/profiles:** no blanket Python/PHP/TS revision bump. Their token float constructors already meet this obligation. Their native profiles and Clojure-family profiles need new immutable revisions only if this round actually changes their emitted content, descriptor/support promise, or pinned runtime closure. In particular, a change to shared `clojure.core.impl`/`clojure.core`/`clj` artifacts requires new pins for every consuming profile whose closure changes; never mutate an existing `clojure-core-v1` publication in place. Python's `py-v1` and already-correct native JS/PHP publications are not automatically re-minted merely because the Clojure source reader changes.
- **Version boundaries:** no Jing encoding-profile, CBOR tag, universal AST grammar, VM numeric-kind/equality, C1 marker, or bytecode-format version bump is warranted by this repair. Prelude/runtime revisions change only when their artifacts/contracts change. Keeping an old frontend revision selectable requires its actual old implementation/closure; retaining a label over new behavior is not legacy support.

This migration preserves artifact portability while correcting source portability. The new compiler cannot make past wrong and new correct artifacts have the same content address.

## RULING 4 — Honest portability statement pending the fix

**Normative text for the public claim:**

> yin.vm on JS preserves the numeric kind carried by portable Data and canonically encoded artifacts, subject to the selected runtime/profile's supported operations. Its Clojure source-to-Data path does not currently preserve every floating literal: ordinary JS readers and host-compiled forms can collapse an integral-valued binary float such as `0.0`, `1.0`, or `1e0` into integer content before compilation. Therefore equal Clojure source containing those unmarked values is not currently guaranteed equal runtime behavior or canonical output across hosts. A bare integral JS Number denotes integer content; intended floating Data must use Jing's float64 carrier. The Clojure forms compiler also needs carrier-literal admission repaired before direct carrier forms are supported uniformly.

Safe **with respect to this defect**, not a blanket certification of every language feature:

- Supported exact integer forms whose values are representable exactly on the producing host; use supported exact carriers for large integers, never a rounded JS Number.
- Supported float source values that remain non-integral after reading retain initial kind today. Native negative zero and non-finite Numbers have float classification in Jing. This does not guarantee every reader/build route preserves their original spelling/sign, and does not certify subsequent bare host arithmetic: `1.5 + 0.5` can become an unboxed integral Number unless the operation reboxes it.
- Explicit executable guest construction, e.g. `(data/float64 1)` where the `data` module/profile is available, supplies float kind at runtime. It is an expression, not a substitute for a float literal inside quoted Data; changing quoted `1.0` into quoted `(data/float64 1)` changes the value into a list.
- Canonical float64 Data decoded from existing Jing artifacts, or explicitly boxed host values passed to VM/UAST interfaces that accept them, retain kind. They must continue through carrier-aware operations. Do not generalize this to `yang.clojure/compile`'s currently incomplete carrier recognition.
- Python/PHP/TS token-based float lowering already performs boxing. Its existing profile-specific tests and explicit prelude/runtime producer obligations continue to govern those paths; this Clojure defect is not evidence of a new defect in each of them.

**Placement required in the future round:**

1. Keep the authoritative numeric/producer contract in `docs/design/dao.jing.cbor.md` and add a cross-reference to the Clojure source boundary; do not redefine codec meaning to accommodate the frontend.
2. Put the Clojure source/forms limitation, selected repair, revision, migration, and capability matrix in `docs/design/yang.antlr.md` §8.8, alongside §8.5.5's existing float-producer precedent. There is no current `docs/design/yang.clojure.md`; do not cite a nonexistent document as the authority.
3. Reconcile portability assertions in `src/cljc/yang/docs/yang_implementation.md`, relevant VM/REPL public documentation, and the `read-forms`/compile API docstrings, including the forms-only boundary. `docs/design/yang.preludes.md` must retain the producer and profile obligations for shared preludes.
4. Correct `test/yang/clojure_collection_order_test.cljc`'s corpus comment/docstring: green non-integral replacement rows establish only that narrowed coverage. Identify this as a source-producer correctness dependency, link the archived failed row and this ruling, and remove the pending limitation only after the restored source and semantics gates pass. A corpus comment alone is not adequate public disclosure.

## Verification performed and limits

This is a read-only architectural investigation plus this findings file. I inspected current source, locally installed upstream reader source, the r3 raw failure log, and the r2 ruling. I ran bounded JVM expressions using the existing cached classpath, without rebuilding: `yang.clojure/read-forms` returns Long for `1`, Double for `1.0`, `0.0`, `1e0`, `-0.0`, `1.5`, and `9007199254740992.0`.
