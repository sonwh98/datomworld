## RULING 1 — one content-canonical policy, at the collection emitter

**MUST:** In `yang.clojure/compile-constructed-collection`, compile each map entry as a paired record containing its key AST and value AST, using the existing environment and macro environment and `tail? = false`. Recursively normalize any constructed collections in those children. Compute each child's canonical UAST root by the existing `vm/ast->semantic-bytecode` projection. Sort the paired records in ascending `jing/canonical-compare` order of the two-element vector `[key-root value-root]`. Flatten the sorted records as `key-AST, value-AST, ...`, after the unchanged empty-map seed operand. Emit the existing `assoc` application with its existing operator resolution and parent tail mark.

This is option (a), specified precisely as **compiled-content address order**. It is not source-text order, host-map order, evaluated-key order, or a sort of the final side table. The comparator is the unsigned bytewise lexicographic order of Jing canonical bytes, with a proper prefix first (`src/cljc/dao/jing.cljc:174–207`). The concrete key is the vector of two address values, not its printer rendering and not the hash of that vector. Key-root is primary, value-root is secondary. Do not independently sort keys and values.

For the saved named-arity example, the key roots begin `1e0366…` (`:yin.k/fn`), `81b62c…` (`:yin.vm.data/reason`), and `8930bf…` (`:yin.k/argc`). With these pinned child rows the ruled pair order is therefore `:yin.k/fn`, `:yin.vm.data/reason`, `:yin.k/argc`. Neither old host's whole operand vector is privileged as the new golden.

**MUST:** For a constructed set, use the same rule with each compiled element's canonical UAST root as the sort key; emit `conj` with the unchanged empty-set seed followed by those sorted element ASTs. For a vector, retain the supplied element order and do not sort.

Compute each child AST and its sort key once per emitter invocation; sorting must not recompile or evaluate it. Keep the original AST, including its attached frontend/source metadata, with its paired record. The projected rows used to obtain a sort key are temporary compiler data, not published roots, origins, expansion events, or a new persisted ordering table. No new canonical field is needed.

Equal sort keys mean equal executable content under the existing content-address integrity contract. Preserve every operand occurrence, including distinct source forms that compile to identical children; do not deduplicate them. A tie must not use host object identity, a counter, or printer output. Permuting truly identical compiled pairs/elements does not change canonical code or its C1 occurrence-key vector; their source metadata remains attached to the respective AST objects. Existing collision checks remain in force. This rule does not claim an ordering for arbitrary noncanonical host objects or extend the codec's supported domain.

**Pipeline location:** this normalization is part of source/form-to-UAST lowering, inside the existing collection emitter (a private helper in the same file is allowed), after recursive child lowering and before assembling this constructor application's operand vector. It therefore precedes the owning final C1 path/root projection, macro traversal over the emitted tree, instruction lowering, and publication. Later compiler-generated form maps that re-enter `compile-form` pass through this same emitter. It is not a global post-expansion AST sorter. Existing finalizers still run after wrappers, tail marking, expansion, and other tree-changing passes at their established boundaries.

Sort keys name the compiled children **at this emission boundary**. A later macro expansion or global-name rewrite may change their addresses; it must preserve the already-selected operand sequence, not re-sort an existing application by its new child addresses. Ordering assertions inspect the emitter boundary; whole-pipeline assertions inspect replay equality and execution. This distinction prevents normalization from becoming a second, effect-reordering optimization pass.

`vm/ast->semantic-bytecode` hashes grammar slots, removes symbol-slot metadata, excludes frontend node keys, and retains semantic literal payload metadata (`src/cljc/yin/vm.cljc:1156–1210`). Using that projection avoids letting irrelevant reader metadata choose executable ordering. Generated naming remains the producer's responsibility: identical replay naming inputs must already yield identical child code. Do not mask a naming divergence by stripping generated names or origins.

Alternatives considered:

| Policy | Decision and reason |
| --- | --- |
| (a) Compiled-content address order at emitter | Adopted. One existing, typed, portable content identity works for mixed keys, arbitrary key expressions, nested collections, and generated form maps. It needs no reader or VM change. |
| (b) Attach source-written order metadata | Rejected for this repair. The public form API receives maps/sets, and `arity-error-form` creates a map without a source-written sequence. Preserving order through readers, macro construction, and every rewriting producer would require a separate ordered-syntax contract. Source-position metadata cannot reconstruct order that was never retained. |
| (c) Sort by key representation | Rejected if this means `pr-str`, `str`, keyword names, host comparison, or host hash. These either omit type/content distinctions or import host behavior. Sorting raw source forms by canonical bytes also lets non-executable source metadata influence order and bypasses the compiler's existing content projection. Compiled key-root ordering is the typed version selected above, with value-root as its explicit secondary key. |
| (d) Patch only `arity-error-form`, or normalize only C1/hashes | Rejected. A hand-ordered arity constructor leaves every other dynamic map and set exposed. Ignoring operand order in hashes would identify executable programs with potentially different behavior. |

## RULING 2 — evaluation semantics and applicability

**MUST preserve:** the VM's application evaluation rule, operator lookup, seeds, key/value association, multiplicity, tail behavior, and normal exception/continuation behavior. On a successful construction every key and value is evaluated once; within a map pair the key precedes its value. Sets evaluate each retained element expression once even when evaluated values coincide. The constructor is invoked only after its operands finish, exactly as today. An exception or transfer of control during an operand prevents the later evaluations that the existing VM would not reach. Sorting is compile-time inspection of code, never evaluation of keys or values.

**The order between pairs/elements is henceforth the canonical order in RULING 1.** It is executable order: the VM consumes that operand vector left to right. The frontend MUST NOT pretend this is an observationally invisible serialization change for every possible program. Effectful operands, competing failures, continuation capture, and distinct key expressions evaluating to an equal key can observe the selected order. For equal evaluated keys, ordinary `assoc`'s later-pair replacement behavior remains; which pair is later is now determined canonically. A shadowed constructor still receives the canonically ordered operands through the existing lookup rules.

There is an unavoidable boundary to “runtime evaluation semantics unchanged”: VM transition semantics and explicitly ordered syntax remain unchanged; an accidental old host traversal is not preserved as a portable language order. No one permutation can preserve two different old hosts' observable traces while also producing identical operand bytes. If “unchanged” means preserving each old host's trace for every effectful unordered form, that stronger requirement is incompatible with universal canonical reordering and is **not** a claim of this ruling. This ruling explicitly fixes the frontend's previously host-dependent choice and requires a frontend revision change. The arity-error map's unchanged built-in computation and distinct constant keys make that particular repair value-preserving.

Programs requiring a particular sequence must express it with existing ordered forms, for example `let` bindings that compute values in order followed by collection construction, or an explicit ordered constructor application. This round introduces no implicit purity inference, effect suppression, or new ordered-map metadata protocol.

**Scope:** all dynamic/unquoted map and set forms reaching `compile-constructed-collection`, including compiler-generated maps, nested collections, and forms admitted through `compile-form`, `compile`, `compile-program` under native and argument-vector/unit options, and `lower-unit`/`library-for` consumers. The emitter branches covered are its map and set branches; the vector branch is an order-preservation control. `arity-error-form` is a covered producer, not a second ordering authority.

`compile-literal` and `compile-quote` continue to emit constant/quoted collections as literal data. Their maps/sets already use Jing's unordered value encoding; do not turn them into calls. `compile-application`, `compile-dao-stream-apply-call`, `u/app`, lambda bodies, `let`, `do`, and pre-existing UAST operand vectors remain ordered and MUST NOT be sorted, including explicit `(assoc ...)` and `(conj ...)` calls. `u/sexp->uast` treats its non-list collection values as literals and is not a dynamic collection emitter. No universal “sort every assoc/conj application” transform is authorized. Other frontends are outside this implementation round; equivalent unordered-to-ordered emitters discovered elsewhere require their own bounded repair, not silent scope expansion.

## RULING 4 — versioning, addresses, and legacy artifacts

**Yes: there is a one-time canonical shift for affected newly compiled artifacts under this new compiler revision.** Changed collection applications change ancestor roots and may change occurrence paths, C1 keys/tables, instruction vectors/provenance, macro input/output records, and containing publication addresses. Even an application elsewhere in a changed root gets a different C1 key because the root is part of that key. There is no requirement that every artifact changes.

**MUST:** advance the Clojure frontend manifest revision from the inspected `"c1-1"` to `"c1-2"` and declare its lowering profile as `:yang.clojure/constructed-collections-v1` (if the dispatch base has already advanced, choose and record a fresh nonconflicting successor before recording expectations). Keep the C1 marker value `1` and the existing C1 support claim: identity/coverage schema has not changed. Keep SPI and UAST/execution grammar versions unchanged. The shared UAST-to-instruction lowerer has not changed for a given UAST, so its own lowering-profile stamp must not be bumped merely because this frontend now supplies different input trees. Pin the compiler commit and this frontend ordering profile with the replay fixtures.

This follows the original design's §3.1 distinction between frontend/lowering revisions and execution grammar revisions, and `docs/design/yin.vm.code-as-tuples.md` §5.2.1–5.2.2: content integrity, derivation verification under an exact profile, and executable loadability are distinct obligations. The existing manifest function is at `src/cljc/yin/repl/frontends.cljc:43–54`.

**Legacy artifacts MUST continue to load at their original addresses**, subject to their already-existing content/contract/dependency checks. Loaders must not sort their operands, rehash them under the new policy, rewrite stored facts, or relabel old C1 keys as new ones. Old executable operand order remains old executable behavior. No storage rewrite or destructive migration is required. Recompilation/republishing creates new immutable artifacts and new addresses; consumers electing to upgrade update their references explicitly. Old side tables remain attached to old roots, and absent legacy provenance is not fabricated.

**Address guarantee:** identical canonical bytes retain identical content addresses regardless of compiler version. Identical source text does NOT promise identical compiled addresses across unpinned compiler/profile revisions. C1 §5.2 replay equality already pins the compiler/profile revision and all other listed inputs; it never guaranteed source-to-address stability across compiler upgrades. Reproducing an old compilation requires its old pinned compiler/profile (or loading its retained output), not silently applying this new normalization. Historical evidence remains valid evidence of its own artifacts, not a certificate for newly compiled roots.

Acceptance remains pending the new fix, independently checked re-pins, four-host regression results, legacy execution evidence, and the separate cc4 budget closure. This document rules policy and bounds; it does not claim those gates have passed.
