## The six attack points

**1. Two-codec dispatch determinism — verified, the claims hold.**

- Jing's reader refuses tag 39 outright: `src/cljc/dao/jing/cbor.cljc:1526` (`39 (refuse :identifier-tag-39)`), inside `item->value`'s tag dispatch, so it fires anywhere in the tree.
- Every handoff body necessarily carries qualified-keyword keys (`:yin.k/handoff` itself first), and under the stream codec identifiers ride Boring's native tag 39 (`src/cljc/dao/stream/cbor/boring.cljc:9-11`). So **no real v0 body can ever be accepted by jing** — the refusal is structural, not trial-and-error.
- Conversely, jing encodes every keyword through tag-27 `dao.jing/keyword` frames (`cbor.cljc:1095-1103, 1123`), and the stream codec's decode refuses them: `:tolerate-unknown-tags false` and `on-unknown-record` admits only the name `"dao.stream/list"` (`boring.cljc:57-68`), with the residue rejected by `convert` (`boring.cljc:139-148`) or `ensure-portable!`.
- Both codecs also pin canonicality by re-encode byte-compare (`cbor.cljc:1552-1560`; `boring.cljc:204-212`), so acceptance is a function of the bytes on each host.
- The genuine overlap — identifier-free scalar payloads (text-keyed maps, numbers, strings) — can decode under both. The pipeline is still deterministic: `decode-two` (`handoff.cljc:1353-1368`) takes the first accepter (jing), commits to it (`or` short-circuits; no fallback on later failure), and such bytes die at `require-tag!` (`handoff.cljc:1371-1375`) with `:yin.k/undecodable {:yin.k/kind :body}` — they can never reach the stream path, because a body passing the tag check under jing must contain tag-27 identifier frames the stream codec refuses. This matches the engineer's scalar-overlap note exactly.
- "A v1 structural failure never reinterprets as v0" is structural in the code, not just tested: once `decode-two` answers `{:codec … :body …}`, the codec is never re-consulted; every later refusal propagates through `call!`.

## Numbered findings

1. **Minor — docstring/report overclaim: an integral float *can* pass the version gate on the stream path, on ClojureScript only.** Boring on JS decodes a CBOR float64 `0.0` to a plain JS number where `js/Number.isInteger` is true, so `jing.cbor/numeric-kind` reports `:integer` (`cbor.cljc:461-468`) and `(contains? #{0} 0.0)` is true on cljs — a stream body with a float `0.0` version passes the gate (`handoff.cljc:1389-1391`) and lowers as a fork on cljs, while the JVM (Double) and Dart (double) refuse it as `:float64`. This is a host limitation inherited from the stream codec (stage-1's `(= 0 v)` merged `0.0` with `0` on cljs identically — no regression), unreachable by any real producer (the lift writes integer `emitted-version`), and the jing path — the only path a v1 can ride — is kind-strict on all three hosts. The version-gate! docstring's "one not of the integer kind is refused" (`handoff.cljc:1380-1382`) and the report's "an integral float never passes on any host" should be qualified "for jing bytes / where the host preserves the kind"; a one-word docs touch, not a code change.

2. **Minor — the reverse mixed tree is unspecified and unrefused: a version-1 child inside a version-0 root lowers `:ok`.** Checkpoint's mixed-version rule (`checkpoint.cljc:139-153`, `known-versions`) runs only for v1 roots; the v0 path skips step 4, and `validate-body`'s membership (`handoff.cljc:978-982`) accepts both versions at every recursion level, so a v1 child in a v0 root re-encodes to jing bytes (`handoff.cljc:1207-1214`) and resumes as an install child. The contract names only the v0-child-in-v1-root direction; no wire producer can emit the reverse today (stage-1 stamps every body 0; D9's lift raises whole trees), and nothing smuggles custody through it (a child carries no header keys by the child rule). If the architect wants the mixed-tree rule symmetric it is a one-line `validate-body` addition — recommend confirming at D9/D10 rather than blocking here.

3. **Minor — test-coverage gap against the D7 row "halted forbids frames."** The rule is present as shared grammar (`handoff.cljc:1001-1003`) and runs on both versions, but neither suite exercises it as a refusal: stage-1 asserts only that the lift emits no frames on a halt (`handoff_test.cljc:807`), and the new suite's halted fixtures touch only header keys and the child role (`handoff_v1_test.cljc:467-474, 482-511`). One tamper fixture (frames assoc'd onto a halted v1 body → `:yin.k/undecodable` at `[:yin.k/frames]`) closes the row; trivial to add at landing or in D9's regeneration commit.

4. **Trivia, no action needed.** The prompt's diff size "+177" vs git's "+178/−32"; the stage-1 wrong-version refusal data now carries an extra `:yin.k/supported` key (no test asserts exact data there — `handoff_test.cljc:1034-1038` checks status only); the `handoff-version` docstring change makes `docs/design/yin.vm.ucf-revisions.md`'s "`handoff-version` is still 0" lines stale, which is exactly the orchestrator's r3 §5 docs pass, deliberately out of scope.
