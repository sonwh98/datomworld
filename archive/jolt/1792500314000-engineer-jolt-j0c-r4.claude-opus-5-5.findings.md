## A. Worker isolation

### A.1 Mechanism

The design fixes this, and it matches the JVM `cst.clj:43-71`.

**Native side** (`jolt_parser.cpp`):
- `jolt_parser_worker_new` returns an opaque `Worker`. It owns fresh `std::vector<dfa::DFA>` for the lexer and the parser, built over the generated ATNs' decision states, plus two `PredictionContextCache`s.
- `jolt_parser_export(worker, …)` installs fresh simulators over the worker's caches before recognition, replacing the generated defaults that point at the static caches:
  - `lexer.setInterpreter(new LexerATNSimulator(&lexer, *atn, w->lexer_dfa, w->lexer_ctx))`;
  - the same for the parser.
- `Recognizer::setInterpreter` deletes the generated default (`runtime/src/Recognizer.cpp:88-91`), and the generated destructors delete the installed one. So the simulators live per call, and the caches live as long as the worker.
- `jolt_parser_worker_free` disposes the handle.

**Guards:**
- A tag rejects a NULL or unrecognized handle with −1.
- A per-worker atomic busy flag refuses a concurrent second call with a new status, **−5**. It is fail-closed, enforcing "a worker is used by one thread at a time" (§7.4).

**jolt side** (`cst.jolt`):
- `make-worker` holds the handle in an atom.
- New `close-worker` is idempotent: a `compare-and-set!` frees it once.
- A closed worker throws "jolt parser worker is closed".
- `export-records` now takes the worker, and `first-failure` uses it.

**The design gap to settle:** `close-worker` is jolt-only; the other hosts' workers are collected. The parser stage's close/reset (§7.4: "its parser stage owns it and disposes it at close/reset") lives in shared code (`yang.stage`, `yang.python.antlr.parser`, `repl_probe`). That is outside this track's files, so **those callers do not call it yet**. `repl_probe` makes a temporary worker per probe call, and under jolt each one keeps its native caches until the process exits. Wiring disposal into the stage and the probe is J5/integration work. The stand-in parser used by the harness has the same leak.

### A.3 Static-state audit (generated C++, helpers, runtime 4.13.2)

**Generated, mutable, per-grammar static (the caches §7.4 names):**
- `Python3Lexer.cpp:33-34` and `Python3Parser.cpp:29-30`: `decisionToDFA`, `sharedContextCache` inside `Python3{Lexer,Parser}StaticData`.
- Held in the anonymous-namespace globals `Python3Lexer.cpp:49` and `Python3Parser.cpp:43`, initialized once through `call_once` (`Python3Lexer.cpp:763`).
- Wired into the default simulators at `Python3Lexer.cpp:623` and `Python3Parser.cpp:667`.
- `ANTLR4_USE_THREAD_LOCAL_CACHE` is not defined, so these are process-wide, not thread-local.
- **Replaced per worker (above), and shown not to grow.**

**Generated, immutable after init (shared):**
- the ATN, `serializedATN`, `ruleNames`, `vocabulary`, `literalNames`, `symbolicNames`.

**Helpers:**
- `Python3LexerBase` keeps only per-instance state: `tokens`, `indents`, `opened`, `lastToken`.
- `getIndentationCount` is a static pure function.
- `onNewLine` builds its `std::regex` per call.
- `Python3ParserBase` has no state.
- **No static mutable state.**

**Runtime statics:**
- `tree/xpath/XPathLexer.cpp:46` (thread_local XPath lexer data), `tree/xpath/XPath.cpp:123`, `tree/ParseTreeWalker.cpp:18`, and `Parser.cpp:47` (`BypassAltsAtnCache`). None of them is reached by `file_input` recognition or by the wrapper; they serve XPath, tree walking and parse-tree patterns.
- `ATN::_mutex/_stateMutex/_edgeMutex` (`ATN.h:127-129`) are locks only.

**OPEN, for review:** the shared ATN's next-token memo.
- `ATN::nextTokens(ATNState*)` lazily fills `ATNState::_nextTokenWithinRule` under `ATN::_mutex` (`runtime/src/atn/ATN.cpp:40-49`). It lives in the shared, generated ATN.
- **It does grow during worker recognition:** 0 → 99 parser ATN states after the corpus. The test records this (RECORD line); it does not assert it.
- It is a deterministic memo of a pure function of the ATN alone (no input or worker state), set once per state under a lock, and never read before it is set.
- The JVM shares exactly the same memo: Java's `ATN.nextTokens(ATNState)` caches `s.nextTokenWithinRule`, and `cst.clj` shares the generated ATN across workers. The design cites `cst.clj` as the isolation reference, so I read §7.4 as accepting it and **did not stop A**.
- If the Architect reads "mutable caches may not [be shared]" literally, there are two options:
  - (a) fill the memo for every ATN state once, at library initialization (cheap, a few thousand states), which makes it immutable before any recognition;
  - (b) deserialize a private ATN per worker (memory per worker, no shared ATN state at all).
- **I chose neither.**

## B. Thread, stack, collection

**Actual thread configuration,** read on the parsing thread itself through `jolt_parser_thread_info` (`pthread_get_stacksize_np`/`pthread_get_stackaddr_np`/`pthread_main_np`):

| parsing thread | stack bytes | main thread | used at the call |
|---|---|---|---|
| jolt's script/main thread (`jolt -M:jolt file.clj`) | 10,027,008 | yes | 9,089 B |
| a thread jolt starts with `Thread.` | 536,576 | no | 241 B |

- **The `:blocking` parse runs on the calling thread:** the reported stack is the caller's own.
- **The main thread's stack is RLIMIT_STACK:** this shell's `ulimit -s` is 9792 KiB = 10,027,008 bytes. So the main-thread budget is inherited from whoever launches jolt and is **not a property of the build**.
- **A jolt `Thread.` gets the macOS default 512 KiB pthread stack:** 536,576 bytes as reported. jolt sets no thread stack size that I could see.

**Nesting budget** (`bb src/dev/jolt_j0c_stack.clj`):
- Every parse runs in a child jolt process, so a crash kills only the child.
- Per shape and per thread kind: doubling depths, then 16 steps inside the failing interval, then a FRESH child (cold caches) at the last passing depth through the full jolt path (native, decode, shared exporter).
- Native-only runs (`native` mode) crash at the same depths as full runs (parens: main passes 8,000 and dies before 16,000 in both modes; a jolt thread passes 500 and dies before 1,000), so **the overflow is the native recursion** (ANTLR's recursive descent and the wrapper's walk), not the jolt side.

Final run: `r4-stack.log`, written to `build/j0c/r4/stack-budget.edn`, exit 0. The time cap is 20 s per parse. "passes" is the last depth that passed in the 16-step refinement; a fresh child (cold caches) then passed it again through the full jolt path.

**Comparison, the JVM oracle on its default main-thread stack** (`clojure -M -e`):
- parens nesting 256 parses; **512 throws `StackOverflowError`** (catchable on the JVM).
- unary takes 328 ms / 986 ms / 6,005 ms at 128/256/512, the same super-linear growth, so it is the grammar/ALL(*) cost and not the C++ runtime's.
- So the C++ main thread nests deeper than the JVM oracle can. Parity beyond the JVM's own limit has no oracle; J5 must decide the bound.

**Failure mode at and above the bracket:**
- **Main thread:** the process dies with SIGSEGV (exit 139).
  - This holds for every crashing shape on both thread kinds; the jolt `Thread.` line below likewise.
- **jolt `Thread.`:** the process dies with SIGILL (exit 132).
- Either way nothing is reported, there is no exception, and no catch is possible, as §7.6 says. Every crash happened in a child, and the harness survived and recorded it.

**No bound is enforced in `cst.jolt`;** §7.6 assigns enforcement to J5. **Budget policy is not chosen here.** Options for J5:
- per-thread-kind budgets from the measured `passes` with a safety factor (for example 1/2);
- run parses on an owned thread created with an explicit large stack, so the budget no longer depends on RLIMIT_STACK or jolt's default;
- a pre-parse nesting count, with the §7.6 caveat that brackets alone do not bound every shape (unary, `not`, `lambda`, ternary and `**` nest without brackets; see the table);
- **and a time/resource bound, not only a stack bound.** Prefix unary nesting reaches 93.5 s at depth 1,024, long before any overflow, on the JVM as well. No asynchronous cancellation of a native call exists (§7.6), so bounding the input is the only defence against this input.

| case | policy | result |
|---|---|---|
| embedded NUL: in a string, in a comment, after a statement, alone, in indentation | parity with the JVM (E1) | 5/5 PASS, all strictly equal |
| empty, CRLF, lone CR, U+FFFD, U+10FFFF, U+FFFF, DEL | parity (E1) | 7/7 PASS, strictly equal |
| **BOM at start** `"﻿x = 1\n"` | parity (E1) | **FAILED first, then fixed**: see below. PASS, strictly equal |
| invalid UTF-8 at the C ABI: lone 0xFF, truncated sequence, overlong `/`, encoded U+D800, above U+10FFFF, 0xFF in a string literal | no JVM equivalent (a JVM String cannot hold one). Fail closed: −2, message copied out, no JPX1 buffer | 6/6 PASS |
| invalid UTF-8 from jolt | a jolt string cannot carry it: jolt decodes 0xFF to U+FFFD, as the JVM's `new String` does, and its reader refuses `"\uD800"` | observed, not reachable through `cst` |
| output over 64 MiB (one 70 MiB string token) | −4, no buffer; `cst` throws, so no packet; the same worker parses again | PASS (also in the ASan harness) |
| invalid arguments: NULL source with a length, NULL out cell, NULL worker, unrecognized worker (zeroed memory) | −1, no buffer | 4/4 PASS |

**BOM defect, found by C and fixed.**
- **Cause:** `ANTLRInputStream::load` strips a leading UTF-8 BOM (`runtime/src/ANTLRInputStream.cpp:43-48`); the JVM's `CharStreams.fromString` keeps it.
- **Effect:** jolt parsed `"﻿x = 1\n"` as **ok**, with every index one code point off the source. `validate!` refused it (`token-text-not-source`), and the JVM answers a syntax error. That is a wrong *successful* packet, which C forbids.
- **Fix:** the wrapper's `SourceStream` (a subclass of `ANTLRInputStream`) decodes with the runtime's own `antlrcpp::Utf8::strictDecode`, throwing the same "illegal byte sequence" on invalid input, and keeps U+FEFF. It is used by both entries.
- **After the fix:** strictly equal to the JVM, and the 51 E1 entries are unchanged.

**Also hardened:** the 64 MiB bound is now enforced **while the buffer grows** (an `Oversize` marker is thrown and answers −4). Before, the whole answer was built and only then compared with the bound.

**Not covered:** there is no input-size bound. Only the output is bounded; the input is limited by memory and by the B recursion limits (J5).
