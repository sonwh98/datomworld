## Checks

- (A) **Worker isolation is real in the C++**: `Worker` owns fresh DFA vectors + two `PredictionContextCache`s (:358-373); each export installs new simulators over them via `setInterpreter` (:434-439), replacing the generated static-cache defaults; RAII `Hold` (:381-391, constructed before the `try`) gives the fail-closed −5 busy refusal on every exit path, allocating nothing. The test evidence is meaningful: 51 sources parsed under isolated reference vs 2-workers-interleaved-opposite-orders vs 4-workers-on-4-gated-threads, all equal (r4-workers-final.log:2,4); the static counters are proven live by two positive controls - the worker's own caches fill (89/265, 143/254/213) and a round-1 static-cache parse grows the statics (33/64, 57/60/105) while worker parses leave them byte-identical (:6,:8). **ATN memo**: the evidence supports the author's characterization - `ATN::nextTokens` is a lock-guarded, set-once memo of a pure function of immutable ATN state, it grew 0→99 (RECORD only, :7), and Java's runtime caches the same field on the same shared generated ATN, so the JVM oracle shares it too. I do not decide whether §7.4's "mutable caches may not be shared" covers it; the author correctly flagged it, proposed two remedies, and chose neither.
- (B) **Stack/thread**: every depth ran in a child process - the harness survived 11+ recorded crashes (exit 139/132 captured per row) and wrote the full summary, which is itself proof of isolation. Every number in the report appears verbatim in r4-stack.log (parens main 10752/11264/139, thread 544/576/132, unary main time-limited 512 ok 10.3 s → 1024 at 93,547 ms, thread unary fail-exit 0 at the 20 s cap, honestly labelled time-bound). Method (doubling → 16-step refinement → fresh cold-cache child at the last pass through the full jolt path, plus native-only controls attributing the overflow to native recursion) is sound; the JVM comparison (512 throws) is honest about there being no oracle past the JVM's own limit. **GC claim credible**: r4-gc.log matches exactly (call 0.1→35,826 ms; gc 206.8→271.1; 5,237 unrelated ticks; plain control recorded not asserted); no `:blocking`-semantics claim is built on it.
- (C) **Input policy**: the 13-entry oracle is JVM-only (generator requires only JVM namespaces; parity asserts `:host :jvm` + grammar-id; fixture forbids cross-host edits), and all 13 pass **strictly** - stronger than E1. The BOM fix is correct and complete: `SourceStream` decodes via the runtime's own `strictDecode`, keeping U+FEFF, and bypasses `ANTLRInputStream::load`'s strip at both entries; invalid UTF-8 becomes −2 fail-closed. Invalid UTF-8 (6 vectors incl. overlong and encoded surrogate), oversize (−4 mid-growth via `Out::room`, then a clean re-parse), and bad args (4) all fail closed with no buffer. The pre-fix BOM behaviour (a wrong *successful* packet, caught by `validate!`) is exactly what C exists to catch, and it was disclosed.
- (D) **Leaks**: cycles log matches the report digit-for-digit (1,304,240→1,416,912; flat after ~1,000/3,000); the assertion is honestly "growth under 1 MiB", not zero. ASan+UBSan harness exit 0 "HARNESS ok", `leaks --atExit` 0 leaks; LSan-unavailable-on-macOS and no-TSan disclosed. Note the sanitizer harness is standalone C++ (never loaded into jolt) - the jolt FFI path is covered by the cycles flatness instead; that split is reasonable and described.
