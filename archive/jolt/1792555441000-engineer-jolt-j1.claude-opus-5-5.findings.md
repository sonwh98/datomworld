## 3. STOP: units->string with an unpaired surrogate (needs a design decision)

- **What the profile requires.**
  - `units->string`: "The host string of the UTF-16 code units `units` ..., unpaired surrogates included".
  - `code-points`: "an unpaired surrogate is its own".
  - `utf8-encode`: refuses `:unpaired-surrogate`.
  - The oracle relies on all three: `text_test.cljc:125-131,134-140`, `conformance_test.cljc:461-471,501-508`, and the corpus `encode-refusal`/`unpaired-surrogate` cases.
- **What Chez offers.**
  - A string is a sequence of Unicode scalar values.
  - `(integer->char #xD800)` throws "is not a valid unicode scalar value". `(char 55296)` throws "Value out of range for char" (`build/j1-probe/probe1.clj`).
  - jolt's README: "Codepoint strings ... no UTF-16 surrogate pairs".
  - No jolt string can hold a lone surrogate, so the value the profile asks for does not exist on this host.
- **What I did.** The override builds every representable string. For an unpaired surrogate it throws ex-info `{:jolt/unimplemented dao.host.text/units->string :unit u :index i}`, which carries no `:dao.host/refusal`, so every oracle row that depends on it shows as FAIL or ERROR.
- **Options**, for the owner or the host-boundary seat:
  - (a) **Amend the profile for code-point hosts.** On such a host, `units->string` refuses an unpaired surrogate with a profile refusal (for example `:unpaired-surrogate`, entry `units->string`). The refusal moves from encoding to construction. The tests that build ill-formed strings would need a host-specific expectation; that edit belongs to the host-boundary seat.
  - (b) **Declare the rows not applicable on code-point hosts** (an oracle skip list, like the JDK 21 NFC pin). The reason: the encoder's law is vacuously met, because no value of the host can reach it. Combines with (a).
  - (c) **Give jolt an ill-formed-text carrier**: a deftype of UTF-16 units that `units->string` returns only for ill-formed input. It is not a `string?`, so it breaks every entry and consumer that takes a string. Not recommended.
  - (d) **Make jolt strings UTF-16.** That would change jolt's string type everywhere, outside this project's control. Not viable.
  - My recommendation is (a) with (b). Section 4.1 of the host-boundary design, and its Q-list, are the place to decide.
- **Consequence beyond the profile (for the J2/J5 planners).** Python `str` allows lone surrogates (`"\ud800"`). yang.python literals that hold one have no jolt string either, so the same decision reaches the parser/AST path.

## 4. Recorded divergence: carriers are named by value

- **The value model.** jolt types an exact integer as `java.lang.Long` in [-2^63, 2^63) and `clojure.lang.BigInt` outside (`(type 9223372036854775808)` is `clojure.lang.BigInt`; `(type (bigint 5))` is `java.lang.Long`). That is the JVM's canonical-carrier table. So `big-carrier?`, `safe-native?`, `demote` and the conformance `carrier` helper (applied to demoted values) agree with the JVM. The host `:jvm` arm of `conformance_test.cljc:28-29` is what jolt reads, and its expectations hold: 2^53 native, 2^63 big, -2^63 native.
- **The difference.** The JVM's host big integer is a distinct `BigInteger` object even for small values; jolt's is the plain exact integer. Two visible consequences:
  - `(big-carrier? (promote 5))`: JVM true, jolt false. Apart from the STOP, this is the only behavioural difference in the 1502 cases.
  - Non-demoted results carry a different carrier tag: `parse-decimal`, the `fields` fraction, decimal mantissas, ratio fields, and the JVM's `Integer` from `alength`/`code-unit`. These are the 29 differing compare lines, all equal in value.
- **Does it matter.** Every consumer in src applies `big-carrier?` to a value, as `(or (number? x) (big-carrier? x))` (`yin/vm/values.cljc:200`, `data.cljc:421`, `engine.cljc:810`, `vm.cljc:929`) or to canonical results (`integer.cljc:878`, `data.cljc:548`). None depends on a promoted value being "big". I recommend recording this rather than inventing a wrapper type. If the owner wants `(big-carrier? (promote x))` true on every host, that is a law the profile does not state today, and jolt would need a boxed big-integer carrier.

- **Version.** Chez 10.4.1's release notes (`~/.local/share/mise/installs/chezscheme/10.4.1/release_notes/release_notes.stex:131-134`): "Unicode 17.0.0 support (10.4.0) ... character, string, and Unicode-related bytevector operations have now been updated to Unicode 17.0.0." 10.3.0 was 16.0.0, 10.0.0 was 15.1, 9.6.0 was 15.0. jolt's `java.text.Normalizer` shim also routes to Chez's `string-normalize-nfc` (`build/tools/jolt/host/chez/java/text-normalize.ss:104`).

It is ahead of the 16.0 pin: by the normalization stability policy, 17.0 and 16.0 agree on strings of 16.0-assigned code points. They can differ only on code points first assigned in 17.0, which the fixture does not contain; that difference is untested here.
- **Test that cannot run unchanged.** `text_test.cljc:192-206` `jvm-nfc-gap` takes its `:clj` arm on jolt and calls `(Runtime/version)`, for which jolt has no shim ("No matching field or method: Runtime/version").
