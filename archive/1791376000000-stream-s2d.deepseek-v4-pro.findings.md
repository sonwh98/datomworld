## What changed

### `src/cljc/dao/stream/ws.cljc`
- **Bounds config**: `make-attacher` and `make-endpoint` accept `:ws/max-frame-bytes`, `:ws/max-pending-frames`, `:ws/max-pending-bytes`, `:ws/outbound-high-water`, `:ws/max-outbound-bytes`. All default to nil (today's behaviour). Validation is `checked-bounds`: a non-nil value that is not a positive integer throws `ex-info "invalid DaoStream WebSocket bounds" {:bounds ..}`. The spec did not ask for this. It follows the composition-error idiom used everywhere else in S2. The bounds are stored on each handle's state as `:bounds`, and `new-handle` gained a `bounds` argument.
- **`payload-size`** (private): `count` on strings, otherwise `#?(:cljd (.-length ^List payload) :cljs (.-length ^js payload) :clj (alength ^bytes payload))`, with `:cljd` first.
- **`teardown!`** (private): emits the `:ws/error` diagnostic, closes the phase, and calls the host close with a code. `protocol-failure!` now delegates to it, with unchanged behaviour. `frame-too-large!` calls it with 1009 `"dao.stream/frame-too-large"` and `:ws/frame-too-large`.
- **`deliver!`**: the frame bound is checked first, on raw size and before decode. The pending bounds are a fourth action, `:overflow`, inside the existing single `swap!`. The swap also sets `:phase :closed`, so no later frame can queue behind the overflow. Outside the swap the overflow becomes `teardown!` 1013 `"dao.stream/pending-overflow"` / `:ws/pending-overflow`. While a connection is pending its deposit target is the endpoint control medium, so the diagnostic lands there. Queued frames are still stored decoded. A new `:pending-bytes` holds their summed raw sizes, and `drain-pending!` resets it with the queue.
- **`WsHandle.append!`**: encode is separated from send. An encode throw is still `invalid-value`. `send-bounded!` then judges the outbound level:
  - `>= :ws/max-outbound-bytes`: teardown 1008 `"dao.stream/outbound-overflow"` / `:ws/outbound-overflow`, and the append answers `closed` (later appends hit the closed phase).
  - `>= :ws/outbound-high-water`, only when the seam has `:queued-bytes`: answers `full` and sends nothing.
  - The level is `((:queued-bytes socket))` when present. Otherwise it is the cumulative `:sent-bytes`, which grows by the payload size on each `ok` send and only while `:ws/max-outbound-bytes` is set.
  - A throwing `:queued-bytes` answers `transport-error`.
- **`adapter`**: gains `:ws/max-frame-bytes` (so host reassembly knows the bound) and `:too-large!` (the same teardown, for a host that stops reassembling). These are additive keys on the host-only adapter map.

### Host seams
- **`jvm.clj` client** (`client-socket`): `chain!` takes a `size`. The `:queued` counter goes up by that size inside the existing `swap!` under the submission lock, and down in the `whenComplete` observer on both success and failure. Close frames count 0. `:queued-bytes` reads the counter.
- **`jvm.clj` client reassembly** (`connect!` listener): text and binary fragments are bounded by the adapter's `:ws/max-frame-bytes`. On overflow the buffer is cleared, the rest of that message's fragments are discarded until `last?`, and `(:too-large! adapter)` runs, so the stream layer closes 1009 through the chained `sendClose`. **Deviation**: the spec says "abort the socket with 1009". I close with 1009 through the normal chain and do not `.abort`, because an immediate abort would cancel the queued close frame. Memory stays bounded either way, since discarded fragments are never buffered.
- **`jvm.clj` server** (`listen!`): `:ws/max-frame-bytes` is passed as http-kit's `:max-ws` (default 4 MiB, http-kit's own). The seam has no `:queued-bytes`, so it uses the fallback and stays gated.
- **`node.cljs`**: `raw-socket` exposes `:queued-bytes` as `bufferedAmount`. `connect!` passes `maxPayload` from the adapter. `listen!` accepts `:ws/max-frame-bytes` as the server's `maxPayload`. Both fall back to `ws`'s own 100 MiB default, never `undefined`, because `ws` spreads options over its defaults and an undefined `maxPayload` means no limit.
- **`browser.cljs`**: `raw-socket` exposes `:queued-bytes` as `bufferedAmount`.
- **`dart.cljd`**: docstring only (no backlog signal and no inbound limit, so fallback and gated).
- The ns docstrings of node and browser previously said "no outbound high-water, `full` excluded by nature". They are rewritten to match.

## Choices reviewers should check

1. **Threshold semantics**: "at or above" from the spec table is applied to the level *before* this frame. A frame larger than the high-water mark can still send when the backlog is empty, so there is no livelock. The cumulative quota can overshoot by less than one frame, and the append after the quota is reached tears down. For pending bytes the check is on the queue *including* the new frame (`> max`). For pending frames, the frame that would make the queue exceed the count is refused.
2. **Fallback scope**: without `:queued-bytes`, `:ws/outbound-high-water` is ignored. The spec defines the fallback against `:ws/max-outbound-bytes` only. A cumulative quota that answered `full` would never drain.
3. **Reassembly overflow**: close through the chain, not `.abort` (see the JVM client entry above).
4. **The new adapter key `:too-large!`**: it reuses the stream-layer teardown, so the diagnostic and the close code stay owned by `dao.stream.ws`, not the host.
5. **Bounds validation**: this is new. It only fires when a bound key is present.
6. **Known pre-existing race, not widened here**: `accept-slot!` unconditionally sets `:phase :replaying`. A pending connection already closed by any teardown (protocol failure, now also overflow) could in principle be reopened if its ack were consumed in the same tick before `endpoint-step`'s release pass. In practice the release pass runs first in `endpoint-step`, so the overflowed slot is released before its ack is read. The `pending-overflow` tests exercise this ordering.
