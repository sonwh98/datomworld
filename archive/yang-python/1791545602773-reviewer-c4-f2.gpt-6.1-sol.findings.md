# Review Findings: Phase C4 Slice F2 — REPL Catalog Selection

**Status: REJECTED**

## P1 — `yin.repl` still loads the legacy frontend implementations

`yin.repl` requires `yin.repl.frontends` and builds the standard catalog when `:frontends` is omitted. That namespace statically requires `yang.clojure`, `yang.python`, and `yang.php`. Ruling 16 assigns catalog construction to each host's composition and says `yin.repl` should require no frontend. Current host entry points, including `yin.repl.main/boot`, `yin.repl.embed`, and `yin.repl.driver/create-state`, rely on the implicit default. Move default catalog construction to the composition layer and pass the catalog explicitly.

## P1 — Selection does not pin a revision

`select-frontend` selects a qualified id without a revision. If the catalog contains multiple revisions of that id, selection is ambiguous, and `frontend-binding` reports `unavailable-parser`. The API offers no way to select a particular revision or record a `[id revision]` selection in session state, contrary to Ruling 16. Add revision-aware selection and pin the selected revision for the request/session.

## P2 — Tests leave required selection cases uncovered

The tests cover toy selection, a newer immutable catalog, missing-parser behavior, and some legacy compatibility. They do not exercise all-host behavior, ambiguity when multiple revisions share a language alias, or the explicit parser-service case.

## Verified points
- Decouples core compilation pipeline from hardcoded switch/case.
- Pinned catalog snapshot in `create-state` guarantees immutability across session lifecycle.
- Passes clean tri-host execution (JVM, Node, Dart).
