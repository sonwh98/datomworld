## Blocking findings

### 1. P1 — Refused attach probes exceed max-outstanding and can deadlock retries

Location: `src/cljc/dao/stream/remote.cljc:395–429`, particularly the unconditional
pending insertion at lines 426–429; `retry-pending!` at lines 653–657.

`send!` refuses a new probe when outstanding plus pending is at the cap, but
`send-request!` then retains that refused probe in `:pending` anyway. Thus the
configured retained-request bound is not enforced. Every additional attach
retains another request and reflection. This directly contradicts spec §1.3
(max entries in outstanding plus pending), the design documentation, and the
claim that the retry scan is bounded by max-outstanding.

It also prevents recovery, even with a healthy accepting writer. With
max-outstanding 1, attach three reflections using the same `remote/links` value:
there is one outstanding probe and two pending probes. Answer the first probe
and drain repeatedly. Outstanding becomes zero, but both pending probes remain
forever: each retry counts the other pending probe, sees count 1 at cap 1, and
refuses itself. Ordinary new requests on the link are also refused. Closing
reflections can free this state, but normal answering and polling cannot.

Runtime reproduction using existing private test fixtures, loaded without
modifying them, printed:

```text
:after-attach 1 2
:after-answer-and-drains 0 2
```

Requested change: enforce the cap when retaining probes as well as when sending
them, and provide an explicit recovery path for attachments that could not be
admitted. Preserve confirmation retry semantics without keeping an unbounded
queue or allowing pending entries to prevent all progress. Add tests for
multiple attachments sharing a capped link, both an accepting writer and a
writer returning full, and recovery after the first accepted answer.

The report acknowledges pending growth as locally driven. That is not an
exception in the architect contract, and it does not address the retry deadlock.

### 2. P1 — Prefetch eviction can make an ordinary next request permanently blocked

Location: `src/cljc/dao/stream/remote.cljc:524–558` and `:625–628`.

The primary answer is filed with age `[id 0]`, then its prefetched outcomes are
installed with later ages. Eviction consequently discards the primary answer
first. For valid policy `{:dao.stream.remote/max-filed 1
:dao.stream.remote/budget 2}`, a healthy source with at least two readable
values answers `next 0` with the value at 0 plus one prefetched outcome at 1.
Every drain evicts the answer at 0 before the caller can consume it. Re-asking
produces the same two entries and evicts the requested answer again.

Runtime reproduction with `listed-reflection [:a :b :c]`, alternating
`(stream/next r 0)` and `(serve! peer)`, printed:

```text
:poll 0 #:dao.stream{:outcome :dao.stream/blocked}
:poll 1 #:dao.stream{:outcome :dao.stream/blocked}
:poll 2 #:dao.stream{:outcome :dao.stream/blocked}
:poll 3 #:dao.stream{:outcome :dao.stream/blocked}
:retained nil ([n 1])
```

This repeats indefinitely with one consumer, no competing requests, no flood,
and no transport failure. More generally it occurs when retained prefetch fills
the cap and evicts its own primary answer. Thus eviction does not allow clean
re-asking as required. The existing test deliberately expects a primary answer
to disappear when budget 4 and max-filed 2 are combined, but does not check that
the original read can subsequently succeed.

Requested change: reconcile oldest-first eviction with progress for these valid
policy combinations, for example by limiting requested/installed prefetch to
the retention capacity so a fresh request's answer survives its own prefetch.
Add a single-reader regression that actually retrieves the first value with
max-filed 1 and budget 2, then advances normally. Any necessary change to the
architect's stated eviction ordering should be made explicit; merely advising
a larger cap leaves accepted configurations unusable.

## Contract assessment

- Setup validation in `remote/links` correctly rejects non-positive integers
  and invalid types for all three new keys via the specified ex-info data.
- The drain loop bounds successful wire reads, retains the cursor, drops
  unrelated values while counting them, and preserves the existing gap recovery
  behavior. No fabricated end or source gap was introduced.
- For ordinary cursor, next, resolve, and append requests at capacity, local
  refusal follows the required writer-full outcome mappings and sends nothing.
  Attach probe retention is the blocking exception above.
- Filed entries and installed outcomes are counted together, with lowest-id
  eviction and re-asking after eviction. Append answers remain emitted rather
  than filed. The prefetch interaction is the blocking exception above.
- The more clamp uses `budget - 1`, and installs none without a valid stamped
  budget. This agrees with the architect's budget-2/one-installed test and the
  existing mirror chase counting the primary answer as the first outcome. The
  discrepancy with §1.3's prose saying at most budget is justified.
- `ws-project/dial` passes all three link keys through its policy selection.
  Design documentation covers the additions, but its hard retained-request
  bound is not currently true.
- No new global state, application callbacks, ambient clock, stream operation,
  or source-outcome fabrication was found. State remains scoped to the existing
  host-composed link/reflection boundary.
