## Mechanism

**The meeting convention is permitted by the owner’s rulings, but the revised NAT path is not yet mechanically derived from DaoStream alone.** Every peer can run the same serve protocol, and a reachable peer may choose to host meeting streams. That removes a privileged *protocol node kind*. The meeting peer still performs routing, address observation, allocation, and fanout as a composition with costs and policy that must be specified. [revision:42](/Users/sto/workspace/datomworld/collab/1790339700000-architect-dao-stream-serve-invariant-review.claude-fable-5-1.findings.md:42), [revision:55](/Users/sto/workspace/datomworld/collab/1790339700000-architect-dao-stream-serve-invariant-review.claude-fable-5-1.findings.md:55)

Four gaps prevent the claimed mechanical result:

- **Surfaces and provenance.** The serving rule exposes the supplied handle’s declared surface. The meeting interpreter needs private read access to requests and private write access to announcements, while visitors get the opposite surfaces; that requires explicit restricted handles. More seriously, a `:meet/here` value in the request medium does not contain the UDP attachment identity that §3 says M republishes as `:meet/seen`. DaoStream’s attachment correlation is delivered to the composition, not automatically inserted into appended values. [original design:91](/Users/sto/workspace/datomworld/collab/1790335900000-architect-dao-stream-serving-spec.claude-fable-5-1.findings.md:91), [revision:46](/Users/sto/workspace/datomworld/collab/1790339700000-architect-dao-stream-serve-invariant-review.claude-fable-5-1.findings.md:46), [revision:52](/Users/sto/workspace/datomworld/collab/1790339700000-architect-dao-stream-serve-invariant-review.claude-fable-5-1.findings.md:52), [dao.stream.md:272](/Users/sto/workspace/datomworld/docs/design/dao.stream.md:272)
- **UDP punching.** The observed reflexive address must belong to the *same bound UDP socket* used for probes. The original UDP `attach!` binds an ephemeral socket; a fresh attachment to the other peer can use another port. A matching nonce-bearing pong, rather than the first inbound datagram, must establish bidirectional reachability. [original design:192](/Users/sto/workspace/datomworld/collab/1790335900000-architect-dao-stream-serving-spec.claude-fable-5-1.findings.md:192), [revision:160](/Users/sto/workspace/datomworld/collab/1790339700000-architect-dao-stream-serve-invariant-review.claude-fable-5-1.findings.md:160)
- **Nested loss and size.** Two proxied streams can carry inner serve frames, but an outer inbox `gap` is loss of *channel frames*, not a `gap` in the final served stream. The inner driver needs a bounded recovery rule for lost or reordered control frames and append-unknown across sessions. Double framing also reduces the UDP payload budget; the existing design refuses an oversized single value rather than making every stream value transferable. [revision:55](/Users/sto/workspace/datomworld/collab/1790339700000-architect-dao-stream-serve-invariant-review.claude-fable-5-1.findings.md:55), [original design:113](/Users/sto/workspace/datomworld/collab/1790335900000-architect-dao-stream-serving-spec.claude-fable-5-1.findings.md:113), [original design:121](/Users/sto/workspace/datomworld/collab/1790335900000-architect-dao-stream-serving-spec.claude-fable-5-1.findings.md:121), [original design:193](/Users/sto/workspace/datomworld/collab/1790335900000-architect-dao-stream-serving-spec.claude-fable-5-1.findings.md:193)
- **Fairness.** One accepted `:meet/here` can allocate two buffers, while each request can create an announcement read by many peers. Inbox caps alone do not bound request processing, announcement retention, or fanout. A bounded request budget, admission decision, and observable refusal or timeout are needed. A lagging announcement reader can receive `gap` and miss a call. ## Changed questions

- **Q2 — retain the earlier consensus: defer held reads.** Inbox polling adds traffic, but the existing retry interval and attempt budget already prevent a busy loop. Holds trade network traffic for per-session state and repeated polls at M; they are an optional performance choice, not a condition for NAT reachability. If added, bound held demands and work per driver step. A public-key hash without proof of control provides no authenticated peer binding. Discovery’s kickoff-hash rule concerns stream identity and verifies signatures; it is not an existing peer-registration rule. Define duplicate `:meet/here` handling in the meeting convention.
