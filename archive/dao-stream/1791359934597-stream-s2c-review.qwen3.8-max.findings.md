## Detailed analysis

**`remote.cljc` — policy.** `give-up-after` added to the `links` `select-keys` and to positive-integer-or-nil validation (`ex-info "invalid DaoStream remote link policy"`); `new-link` stores it plus `:now nil`. Tested with 0, −1, 1.5. Matches spec §1.2/§1.3.

**`new-deadline`.** `(+ now give-up-after)`, nil when either is missing — clock-less compositions stamp nothing. Arithmetic is portable (int+int and mixed comparison are clean on JVM/CLJS/Dart; epoch-ms magnitudes are far below any precision boundary).

**Stamping discipline**, verified on every path: accepted sends stamp via `register!` (`send-request!`, `refl-append`, `send-named!`); kept probes carry their original deadline because `send-request!` does the **pending lookup first** — never restamped on retry or eventual send (verified in `a-kept-probe-has-a-deadline`); waiting `:probe` entries are unstamped until `admit-probe!`; `count-ask!` touches only `:asks`, never `:deadline`; `absorb!`/`absorb-named!` remove the entry, deadline included. All exactly per spec.

**`link-step!` / `:step`.** Order matches the spec: record `:now`, budgeted `drain!`, then — skipped when `channel-gone?` is already true, so an `end`-loss in the same step doesn't double-report — scan `(concat outstanding pending)` for the least id with `:deadline <= now`, emit `channel-expired` (id, op), run `channel-loss!` (abandons outstanding, `append-unknown` per append, sets gone). Return shape `{:dao.stream.remote/channel-gone? bool :dao.stream.remote/expired id-or-nil}`; nil for unreached channels. Drain-before-scan is the right ordering: an answer arriving in the deadline's own tick clears its entry before the scan. `:step` creating the link on a reached-but-unattached channel via `link-for!` is harmless and pre-records `:now`. Only gaps: findings 1–2.

**Flood immunity.** The scan is independent of drain-budget; `flood-cannot-defer-expiry` (budget 2, 60 junk values) demonstrates the accepted D3 trade-off (possible false loss, never deferred expiry).

**Memory.** No new leak: `:outstanding` cleared on loss; `:filed`/`:filed-cursors` bounded by `max-filed` (S2b); `:pending` retention is pre-existing and bounded by `max-outstanding` when composed (finding 4). Expired entries can't accumulate — expiry is whole-channel loss and all send paths guard on `channel-gone?`.

**Portability.** No reader conditionals needed: `some->`, `concat`, `sort-by key`, numeric `<=` are clj/cljs/cljd-safe. No side effects inside `swap!` in the new paths (`emit!`/`channel-loss!` run outside swaps). The only reachable type hazard is finding 1's `(<= deadline nil)`.

**`ws_project.cljc` — `dial`.** Policy `select-keys` gains `give-up-after`; namespaced-key-only per spec; `dial-propagates-link-options` verifies all four link keys land on the link atom.

**`dial-step!` multi-arity.** 1-arity delegates with nil and preserves existing callers exactly (no `:now`, no link step, nothing expires — `the-one-arity-dial-step-never-expires`). 2-arity: records `:now` on the dial, budgeted projection, link step **between** projection and mirror (correct: freshly deposited answers reach the link before the expiry scan), budgeted mirror once outside any atom update (`dial-mirror-effects-run-once-per-step` still guards this), then closes the ws handle when the step answers gone — `closable?`-checked and idempotent, so repeated post-loss ticks are safe. Nil `stepped` is falsy in the gone-check — no spurious close.

**`establish!`.** Stores `:cd`/`:step!` and, when the dial has a recorded `now`, steps the new link before any probe exists — since `:step` creates the link via `link-for!`, the later `:attach` reuses it with `:now` set, so the immediately-sent attach probe is stamped. This is the one beyond-the-letter behavior; the rationale is sound and the mechanism verified. Residual gap is finding 2.
