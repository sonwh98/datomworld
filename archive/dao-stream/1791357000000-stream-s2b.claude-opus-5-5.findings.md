## Edits

### `src/cljc/dao/stream/remote.cljc`

- **Policy validation (`links`).** The policy `select-keys` now includes `:dao.stream.remote/drain-budget`, `max-outstanding` and `max-filed`. A non-nil value that is not a positive integer throws `ex-info "invalid DaoStream remote link policy" {:policy policy}` when `links` is built. It reuses the existing private `pos-int-or-nil?`. `resend-after` and `budget` keep their lenient reading. The `attacher` docstring names the new keys.
- **`new-link`** stores `:drain-budget`, `:max-outstanding` and `:max-filed`.
- **`drain!`** counts its reads down from `:drain-budget`. At zero it stops, leaving `:cursor` where it was, and the next operation's drain continues from there. A gap already ended the drain, so it counts as its read trivially. The resend scan and `retry-pending!` are unchanged; `max-outstanding` bounds them (spec §1.3).
- **`max-outstanding`.** New private `send!` refuses locally with `{:dao.stream/outcome :dao.stream/full}`, sending nothing, when `count(:outstanding) + count(:pending without this id) >= max-outstanding`. `send-request!`, `send-named!` and `refl-append` all go through it, so each operation answers exactly as it does for a writer `full`:
  - `cursor` and `resolve` answer `retry-read` (`transport-error`, `retry? true`).
  - `next` answers `blocked`.
  - `append!` answers `full`.

  `count-ask!` resends an existing entry, so it is not gated.
- **`install-more!` clamp.**
  - It installs at most `(dec budget)` outcomes, where budget is the link's stamped budget, and none when the link has no valid budget. The answer itself is the first of the k outcomes.
  - This follows the brief's test (budget 2 gives 1 installed) rather than the spec prose "at most `(:budget @link)`". The two differ by one; the test's reading is the one consistent with the mirror's chase.
- **Installed-entry shape.** `:filed-cursors` values are now `{:outcome o :age [answer-id i]}`. `filed-next!` reads `(:outcome o)`. Nothing outside `remote.cljc` reads `:filed-cursors`.
- **`max-filed`.** New `evict-filed!` runs after `absorb!` files an answer, after `install-more!`, and in `absorb-named!`.
  - While `count(:filed) + count(:filed-cursors) > max-filed`, it evicts the minimum age.
  - A filed answer's age is `[id 0]`. The i-th outcome it installed has age `[id i]`.
  - So the lowest id goes first, and within one answer the answer goes before the outcomes installed after it.
  - The scan is O(n) per eviction, with n ≤ max-filed + 1.

## Decisions for review

1. **Kept probes at the cap.** An attach probe refused locally by `max-outstanding` is kept in `:pending` like any writer-refused probe and retried once per drain. `send!` excludes the probe's own id from the count, so a retry is not blocked by itself. `:pending` can therefore grow by one entry per local `attach!` past the cap. That growth is driven by the local caller, not by the peer, and what crosses the wire is still bounded. The alternative was to drop the probe, which would leave the reflection unconfirmed forever.
2. **Eviction cascade.** Eviction is strictly by age, so a re-asked answer that arrives later can evict a newer-id entry that hasn't been consumed yet. That stays correct: the entry is re-asked and no outcome is invented. But `max-filed` should be sized above the number of answers one consumer step expects to hold. The test consumes the kept answers before re-asking the evicted one.
3. **More clamp off-by-one** relative to the spec prose: see above.
