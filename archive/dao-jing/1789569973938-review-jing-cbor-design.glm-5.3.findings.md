# Review: `docs/design/dao.jing.cbor.md` — implementation readiness

All eight evaluation dimensions were traced against the required reading list and the current `src/cljc/dao/jing*.cljc` implementation. Upstream claims were verified against live primary sources (boring README, `doc/COMPATIBILITY.md`, `core.clj`, `data.cljc`, konserve `serializers.cljc`, the IANA CBOR tags registry, Clojars) — the two facts I could not pin down from source are listed under unverified assumptions. Note: boring is **not** in the local dependency cache (`~/.m2` has only `io/replikativ/datalog-parser`), so nothing was verifiable offline.

## Actionable findings

**P2 | docs/design/dao.jing.cbor.md:134-138 | Numeric carriers have no stated equality/ordering contract, and decoded carriers flow into ordered consumers.** The doc adds "portable constructors and accessors" and defers VM arithmetic, but says nothing about `=`, `hash`, and `compare`. Verified upstream: the CLJS carriers are `defrecord`s (`boring.data/Decimal [exponent mantissa]`, `Rational [numerator denominator]`), and floats decode to a carrier on JS/Dart by this doc's own rule (:120-122). Concrete failure: a stored datom value `1.0` in a published covered index, decoded on Node — `dao.data.btree` folds and merges nodes by `compare` on datom components; `compare` on a record that implements no `IComparable` throws or degrades to class-name ordering, corrupting or breaking the index fold; Datalog unification `= carrier 1.0-in-memory` also fails where the JVM host succeeds. **Fix:** one paragraph in *Encoding contract → Numeric identity*: carriers must implement `hash`/`=`/`compare` consistently across hosts, with carrier↔native-number `compare` defined as numeric (not type-disjoint); audit the ordered consumers (btree datom ordering, `dao.space.query` matching) and add a Node/Dart scenario to the test list exercising decoded numerics in ordered/matched positions.

**P2 | docs/design/dao.jing.cbor.md:82 (supported values, "strings") | Ill-formed UTF-16 (unpaired surrogates) diverges across hosts and mutates values silently through storage.** JVM `String.getBytes("UTF-8")` substitutes `?` (0x3F) for an unpaired surrogate; JS `TextEncoder` and Dart `utf8.encode` substitute U+FFFD (EF BF BD). Concrete: `(materialize! h "a\uDC80b")` encodes to different canonical bytes — hence different addresses — on JVM vs JS/Dart; worse, `decode(encode(s))` yields `"a?b"`/`"a\uFFFDb"`, so the read-back value differs from what was stored while the canonicality check still passes. Whether boring pre-validates text strings is unverified; Jing's own contract must not depend on it. **Fix:** the encoding contract rejects strings containing unpaired surrogates before encoding, on every host (noncharacters and normal astral text stay legal); add the fixture to the Unicode scenario.

**P2 | docs/design/dao.jing.cbor.md:211-233 | Completion-criteria gaps — the scenario list and acceptance paragraph would not catch two known defect classes.** Missing: (a) the surrogate case above; (b) host `float32` values on the widening path (:126 — "Widen native float32" has no scenario; only integer/float, signed zero, ∞/NaN, bignum, scale, ratio are listed); (c) empty collections with and without empty metadata (the "omit empty metadata" rule :99 is untested); (d) the carrier equality/ordering smoke from the first finding; (e) identifier fixtures for exactly the pathological class `dao.jing.md` records as a transitional residual — `(symbol "42")` vs `42`, `(keyword "a/b")` (ns=nil, name="a/b") vs `(keyword "a" "b")`, whitespace-bearing names; "ambiguous identifiers" (:215) should name these; (f) acceptance states byte-identity and encode-decode-encode stability but never **injectivity** — distinct supported values → distinct bytes — which is the actual anti-collision guarantee the pathological-symbol residual is about. **Fix:** extend the scenario bullets and add "pairwise-distinct fixtures (including the pathological identifier class) address distinctly" to the acceptance sentence.

**P3 | docs/design/dao.jing.cbor.md:151-153 | The file frame's `[address payload-bytes]` binds the backend to boring's identifier encoding for no benefit.** The frame address is a Jing keyword, so replay/records must decode a keyword — i.e. the byte-oriented backend now depends on boring's (unverified) keyword arm, and the Dart twin must reproduce it just to read frames. **Fix:** carry the raw 32-byte digest byte string instead of the keyword (`[digest-32 payload-bytes]`); the wrapper already owns keyword↔hash conversion, replay validation becomes a byte compare, frames shrink, and the file backend decouples from identifier encoding entirely.

**P3 | docs/design/dao.jing.cbor.md:167-168 | "Existing transport size limits" overstates what exists; the real consequence goes unstated.** Verified: the only app-level limit is the DHT UDP datagram budget (`node.cljc:45-49`, 1200 bytes, refused on send); `ws.cljc`/`rpc.cljc` enforce no byte limit (host WebSocket defaults apply silently). After Base64 (+33%) inside a Transit-JSON envelope, the effective canonical-payload budget per DHT datagram is roughly 700–800 bytes; oversized content already degrades to local-only until DRDS (dao.jing.dht.md, *Operational limits*). **Fix:** name the actual limits (DHT datagram budget; none on WS today), state the effective-budget arithmetic and the local-only degradation, and decide whether the WS path should gain an explicit byte cap now that payloads are arbitrary-length byte strings.

**P3 | docs/design/dao.jing.cbor.md:64-67 | Canonical re-encode on *every* read is redundant work on the hottest path.** The address hash over the retrieved bytes already proves their integrity; one-spelling-per-value (the residual value of the re-encode check) only matters where bytes Jing did not encode can enter: remote/DHT ingest, and file replay acceptance. B-tree hydration reads many payloads per query and would pay double codec cost per node for nothing. **Fix:** scope the rule — hash-verify every read; canonicality-verify once at ingress of foreign bytes. If per-read defense-in-depth is deliberate, say so and accept the cost.

**P3 | docs/design/dao.jing.cbor.md:54-59,176-177 | Byte-store put re-verification is unassigned.** Today every backend validates address↔payload (`mem.cljc:22`, `file.cljc:73`, `remote.cljc:33`); under the byte contract the wrapper derived the address from the very bytes it passes, so backend re-hashing is duplicated for local backends but **load-bearing at trust boundaries** (a remote/DHT server must verify a client's `[address bytes]` claim). **Fix:** one sentence — the wrapper derives and verifies; a backend re-verifies exactly when bytes arrive from an untrusted party.

**P3 | docs/design/dao.jing.cbor.md:164-166,185-191 | Mixed-version peers: name the expected failure mode.** New client → old server: the base64 string is hashed as a string value → address mismatch → throw. Old client → new server: a non-string payload fails Base64 decode → correlated error. Both fail closed (good), but remote/DHT have no version negotiation, so the clean break implies coordinated peer upgrades. **Fix:** one sentence in *Remote and DHT* recording loud validation failure — never silent misinterpretation — as the designed cross-version behavior.

**P3 | docs/design/dao.jing.cbor.md:33-37 | "Supported by Konserve" is accurate but understates its status.** Verified from konserve `serializers.cljc`: boring is serializer byte 3, portable clj+cljs — and marked **"BETA. Not yet recommended for production stores."** boring 0.1.30 itself was released 2026-09-06 (27 releases total). The pin + frozen fixtures already own byte-stability, so nothing structural changes. **Fix:** qualify the precedent ("integrated by Konserve, currently marked beta there") so the maturity claim isn't overstated.

## Verdict

**Ready with corrections.** The architecture is sound and the reuse is genuine, not "an ad hoc format inside CBOR":

- **Boundaries (item 1) — correct.** Codec, addressing, and integrity sit in the Jing wrapper over opaque bytes; durability and concurrency belong to the backend; no global registry or ambient options; handles stay plain data. The effect-stream write path is **not** foreclosed: `put-bytes` is a synchronous function today, but the contract is effect-payload-shaped (address, bytes → verdict), and the doc correctly keeps the write-effect redesign out of scope (:234; dao.jing.md:474-478 deferral stands).
- **Community reuse (item 2) — verified necessary per wrapper.** JVM/JS native-number divergence is documented upstream ("an integral JS number encodes as an integer… a JVM `Double` such as `1.0` encodes as a float, even under `:canonical`") → the `dao.jing/float64` escape is required; boring's reserved tag-27 names have **no list marker** → `dao.jing/list` is required; `clojure/with-meta [metadata value]`, tag 4 scale retention (`1.50M` ≠ `1.5M`), tag 30 `Rational`/`Decimal` CLJS carriers, `:stringref false`, opt-in shapes, opt-in offset index, and bignum-narrowing-to-int ("host integer width is not identity") all check out. Tag 27 is IANA-registered (generic object), as are 2/3, 4, 30, 258 — the named extensions ride a registered mechanism, not a squat.
- **Feasibility (item 4) — yes.** Named frames are boring's public registry mechanism ("a caller's registry takes precedence over built-in markers"); no private API needed on JVM/JS. The Dart codec is in-repo work bounded by frozen fixtures; it must reproduce only the Jing profile subset (floats are always the 8-byte tag-27 escape, so shortest-float rules never apply).
- **Storage correctness (item 5) — carried over and strengthened.** Snapshot copying, CAS insert-if-absent, `:present` byte read-back, fsync-before-ack, torn-tail recovery all descend from the current verified backends; verification improves (byte hash vs re-print). Old-store rejection is achievable: complete old EDN frames never look torn (framing is shared), and EDN text fails CBOR frame decode loudly before any truncation — the required nondestructive-rejection test is already listed. PostgreSQL/S3 reasoning stays at the right altitude.
- **Migration (item 6) — clean break is consistent** with dao.jing.md ("every minted address changes together", "no version header is owed") and ADR 0001's open question 3; the address-bearing consumers are real and located (`yin/vm/v2.cljc`, `dao/space/index.cljc`, `dao/data/btree/storage.cljc` + tests). The migration also retires three recorded dao.jing.md open items (canonical encoding + its deferred residuals, byte-array identity hashing, metadata-carrying backends/transports) — worth saying in the doc since it's the payoff.
- The two cross-document tension points (symbol metadata now address-significant; lists/seqs unified but vector-distinct) are intentional supersessions, and the doc already orders dao.jing.md updated — no silent contradictions found.

**Unresolved decisions**

1. Carrier `=`/`hash`/`compare` semantics and their acceptance by ordered consumers (finding 1) — must be decided before step 1 of the implementation sequence.
2. Whether to adopt boring's native identifier encoding wholesale or escape all identifiers into `dao.jing/keyword`/`symbol` frames — the doc's "where they round-trip exactly" rule presupposes knowing the exact native arm, which is unverified (below).
3. Per-read canonicality re-check vs ingress-only (finding 6) — a cost decision to make explicitly.

**Unverified upstream assumptions**

1. **Boring's exact keyword/symbol encoding** (tag number, payload shape — slash-joined string vs `[ns name]`): the arm lives in the Java writer hot path, not in the fetched Clojure sources, and `COMPATIBILITY.md`'s table lists no dedicated identifier tag. It becomes part of Jing's frozen byte contract (values, and the file frame as currently specified) and must be replicated in Dart — verify against boring source or its goldens before freezing fixtures.
2. **Whether boring itself rejects ill-formed UTF-16 text strings** on JVM/JS rather than relying on host encoder substitution — determines whether finding 2 needs a Jing-side guard in addition to (or instead of) boring's validation. Jing should state its own rule regardless.

Everything else cited above (coordinates `org.replikativ/boring`, version 0.1.30 as latest, the compatibility policy's "does not require… byte-identical output", `:canonical` = RFC 8949 bytewise key order, signed-zero retention, NaN `f9 7e00` handling bypassed by the float64 escape, konserve's beta-marked boring serializer) was verified against primary sources.
