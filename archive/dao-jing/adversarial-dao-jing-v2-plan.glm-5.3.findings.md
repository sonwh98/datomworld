# Adversarial review — dao.jing.v2 migration plan (collab/architect-dao-jing-v2-plan.claude-fable-5-1.findings.md)

Reviewed as an argument, not a diff. Every claim below was checked against the tree. Citations: `plan:<n>` = findings.md line; `rpc.cljc` = src/cljc/dao/stream/rpc.cljc; `log.cljc` = src/cljc/dao/stream/log.cljc; `log_test` = test/dao/stream/log_test.cljc.

## Findings

**P1 | plan:269–280, 452–454 (Decision 3) | The `busy`/`step` protocol is self-contradictory: an unsent envelope can never be retried or cleared through the specified surface.** The plan bars the only retry path and then specifies a `step` that cannot retry either. `rpc/request!` is the sole caller of the private `attempt-unsent` (rpc.cljc:193–256, :unsent branch at 243–244), and its own docstring says a call while unsent "retries the exact already-allocated envelope and ignores op/args" — which is why the plan's `busy` guard exists (plan:274–276). But `poll!` only reads the response medium (rpc.cljc:421–445 → `poll-read` → `stream/next`); it never touches the writer. So under the plan's own spec: request #1 → `full` → `pending-request`; request #2 → `busy`; `step` → poll only, `unsent` unchanged; request #2' → `busy` again — forever. Request #1 is never re-attempted, and the driver is permanently unable to submit work. The plan's J3a test betrays the contradiction: "a scripted writer answering `full` once: `pending-request`, then `busy` on a second request, then **`requested` after a step**" (plan:452–454) is unachievable if `step` only polls, and the bullet "the envelope is retained and re-attempted on the next request **or step**" (plan:272–273) is false on both halves — the next request returns `busy` without calling `rpc/request!`, and step doesn't attempt. This is exactly the "phase will decide" the architect brief forbade. **Fix:** specify that `step` first re-attempts the unsent envelope via `rpc/request!` (whose unsent branch ignores op/args — re-invoking with the retained op/args is equivalent), fold that attempt's outcome (`requested`/`pending-request`/`request-undeliverable`, the last arriving as a `:lost` completion) into `step`'s result, and state explicitly that a driver that only re-calls `request-*` cannot clear a `busy`.

**P1 | plan:471–474 + rpc.cljc:267–283, 308–315, 465–476 (Decision 3 / J3b) | A pending (unsent) request is silently swallowed on detach, and `rebind` preserves the stale envelope — the plan never mentions `abandon-unsent`, which exists for precisely this.** On `/detached`, `handle-event` calls `lose-outstanding`, which reduces over `:outstanding` only (rpc.cljc:308–315) — the unsent envelope is not in `:outstanding` (it moves there only on a successful append, rpc.cljc:185–190). So a request that returned `pending-request` produces **no completion at all**: not `:lost`, not served, id retired from the caller's view never. `rebind` (rpc.cljc:465–476) then keeps `:unsent` across the new writer, and `rpc.ws/rebind` rebuilds only the decoder (src/cljc/dao/stream/rpc/ws.cljc:152–167). The plan's J3b claim "killing the connection completes the outstanding request as `:lost`" (plan:471–472) is true only for *accepted* requests. `rpc/abandon-unsent` (rpc.cljc:267–283) is documented as the composition's tool for "an operator disconnect, a rebind onto a fresh attachment"; the plan never names it, and its client surface exposes no equivalent — combined with the first finding, a caller holding a `pending-request` id has no operation that ever retires it. **Fix:** on observing a terminal `/detached` (and before any rebind), the client completes the unsent request as `:lost` via `rpc/abandon-unsent`; add an unsent-at-detach case to J3a/J3b.

**P1 | plan:392–398, 354–359 (Decision 2 / Phase J1) | The truncate-incomplete-tail path — the riskiest code being copied — loses its only test coverage when v1 dies; the golden-byte test does not cover it.** The prompt's suspicion is confirmed. The golden-byte compatibility test writes "a golden byte sequence for **one known record**" (plan:392–394) — the clean-replay path only. The ported `file_test` cases (handle-shape, count-records, corrupt-record, raw-duplicate, plan:395–398) all write **complete** frames through `append-frame!`. The only test of truncation anywhere is `log_test.cljc:100–135` (`torn-tail-test`, hand-written overlong length prefix + short payload, all three hosts), which lives in `dao.stream.log`'s suite, is never mentioned in the plan's "v1-only tests deliberately not mirrored" list (plan:354–359), and is deleted with v1 — while the truncation loops being copied (log.cljc:203–210 clj, 222–230 cljs, 237–248 cljd: the `(< (- end offset) 4)`, negative-length, and overlong-length branches) survive in `dao.jing.file` with zero coverage on any host. Decision 2's own cost statement calls this path out by name ("truncate an incomplete tail exactly as `dao.stream.log/make-log-stream` does", plan:214–215), then J1 fails to test it. **Fix:** port `torn-tail-test` into `file_test` on all three hosts (torn frame hand-written as raw bytes, assert `create-content-file` truncates, replays the surviving records, and a subsequent put lands clean), plus a sub-4-byte-tail variant.

**P2 | plan:266–267 vs 278–280 (Decision 3) | `step`'s return shape has no field for the diagnostics it "takes exactly once."** The specified result is `{:state s' :completions [...]}` (plan:266–267), yet step "takes completions **and diagnostics** exactly once" (plan:278–280). Either the diagnostics are dropped — losing `decode-error`, `unsolicited-response`, `event-after-terminal`, and transport diagnostics, which are the only signal a noisy or mis-decoded response medium ever produces — or `take-diagnostics` isn't called, and `take-diagnostics`' own docstring warns the vector then "would grow … for the session's lifetime" (rpc.cljc:456–462). **Fix:** add `:diagnostics [...]` to `step`'s result (or name their destination explicitly).

**P2 | plan:283–288, 269–274 (Decision 3) | The completion vocabulary is not total over what `rpc/poll!` and `request!` can actually produce.** The enumerated `:lost` reasons — "gap, /detached, /ended, /not-found, /transport-error, or an append that could not be delivered" (plan:283–288) — omit `:dao.stream/cursor-mismatch` and `:dao.stream/invalid-cursor`, which `poll-read` produces as terminal loss reasons from the response read (rpc.cljc:408–413), and `:dao.stream.rpc/abandoned` if the second finding's fix is adopted. Likewise `request-*`'s outcome set ("requested, pending-request, request-undeliverable, or terminal", plan:270–272) omits `:dao.stream.rpc/allocator-error`, which is what the first allocation failure actually returns (`terminal` only on subsequent calls; rpc.cljc:155–161, 240–241). A decode implemented from the plan's enumeration literally would fall through on these. **Fix:** specify the `:lost` decode as total over any reason keyword (pass-through), and add `allocator-error` to the `request-*` outcomes (or map it onto `terminal`).

**P3 | plan:589–591 (End condition) | "No namespace under `dao.jing.v2*` requires `dao.stream`" is true only of direct requires.** `dao.jing.v2` requires `dao.jing` for `materialize!` (plan:66–68), and `dao.jing` requires `dao.stream` for the v1 observer (jing.cljc:19) until J5. This is inherent to the fold-back strategy and not a defect, but the end-condition bullet reads like an isolation claim and could mislead someone into loading `dao.jing.v2` without v1. **Fix:** one clarifying sentence ("transitively, until J5 removes the v1 observer from `dao.jing`").

## Reviewed and sound (with caveats noted)

- **Decision 2 (option b) — sound.** I attacked it on Axiom 1 and lost. `datom.world.md`'s "side effects must appear as stream emissions" reads against the plan at first, but the plan's answer — the intake pool is DaoJing's stream boundary, and the write behind `:put-content-fn` is the backend effect at the far side of interpretation, exactly like `dao.jing.mem`'s atom (jing/mem.cljc requires only `dao.jing`) — is the position `dao.jing.md` §Materialization rule already commits to ("backend effects are explicit functions"). The public-transport exposure was real but latent: grep shows zero consumers of `{:dao.stream/type :append-log}` outside `dao.jing.file` and tests, so removal breaks nothing, and `dao.stream.log` dies with v1, bounding the copy-not-require duplication window (its hazard — bugfixes double-applied during that window — is real but small, and requiring it would keep v1 alive past its own deletion, which is worse). Caveats: the torn-tail coverage gap above; and note the mild tension that "the framing is private" (plan:190–191) coexists with byte-for-byte compatibility enforced by a golden test — privacy is now aspirational, as it already was under v1.
- **Decision 3's core claim — sound.** A synchronous handle genuinely is unimplementable over the polling RPC: nothing in `dao.stream.rpc` waits, `take!!` is gone by construction, and on cljs/cljd waiting deadlocks (dao.stream.md IO Model). A JVM spin-poll inside `:get-content-fn` would be host-divergent `take!!`. Removing the handle and returning a caller-stepped state machine is the honest shape; the widening to three hosts is a real gain (v1's client was JVM-only, remote_test.cljc:234–235). The defects are in the specified protocol details (findings 1, 2, 4, 5), not in the architecture.
- **Decision 1 — sound.** Composition-minted cursors, retain-exactly-the-successor-after-materialize, and `adopt-cursor` restricted to stream-handed-out values all match the contract (dao.stream.md, Cursors: "minted by `cursor`, received as a successor from `next`, or recovered from a gap outcome"). The seven-outcome totality with a declaration-driven test, defects-as-data with `:member`/`:result`, and the construction-time throw for missing cursor/reader surface sit correctly inside the contract's exception rule. The J2 port list covers every observer case in jing_test.cljc:322–560.
- **Decision 4 / in-place rewrite of `dao.jing.file` — sound on the evidence.** No code outside `file_test` reads `:log` or `:stream` from a file handle (grep over src/, test/dao/space, test/dao/data); `btree_durability_test` uses only `create-content-file` + the handle API (btree_durability_test.cljc:211–227), and `dao.space.index` reaches the file backend only through `jing-coordinate/open!` (index.cljc:382 `ds/defopen :dao.space.index/published`). The "avoid two address-minting paths" rationale is correct — a wholesale `dao.jing.v2` would duplicate `segment-key`, and content identity is the one thing that must stay single-sourced. J1's requirement to run the `dao.space` and btree suites rather than inspect is the right gate.
- **Phase boundaries — sound.** Every phase has fail-able completion criteria (requires-absence, named Node test output, specific scripted outcomes, named prose sections). Nothing is left as a phase that "will decide" — the J5 naming decision is deferred *with a settled recommendation* (fold back), mirroring the stream plan's own end-condition language ("a single decision is taken explicitly"), and the `:dao.jing/remote` coordinate deferral names its home (`dao.space`'s plan) rather than deferring into a void. Ordering is right: J1 precedes J2 because `observer-convergence-test` needs both; the plan already moves it.
- **End condition / deletion gate — acceptable coexistence, not a fork.** The stream plan's "defect of the migration" language condemns *undecided* coexistence (dao.stream.implementation-plan.md:656–659); this plan decides (deletion gated on `dao.space`, fold-back recommended, duplication of `default-handlers` explicitly ends at J5). The one thing worth saying out loud: Decision 3 makes `dao.space`'s plan strictly harder — query-side remote reads now require designing async B-tree hydration and a new coordinate story — so the J5 gate's critical path runs through the largest unpaid design debt in the system. Named deferral, not a defect.
- **Invariants and portability — no violations found.** No atoms/globals/registries in the new namespaces (per-handle state matches `dao.jing.mem`'s precedent); nothing self-schedules; the cljd `#?(:cljd nil :clj …)`-first discipline is stated correctly and no new host branch is proposed for the pure `.cljc` namespaces; the three J1 host branches mirror `dao.stream.log` code that already runs green on clj, Node, and cljd (log_test.cljc's own three-host ns form), so achievability is proven by the v1 existence proof.

## Summary

Six actionable findings (3×P1, 2×P2, 1×P3), all concentrated where the prompt aimed the budget: Decision 3's client protocol has two specification holes an implementer would hit inside J3 (the un-clearable `busy` state and the swallowed pending request at detach), and Decision 2's on-disk compatibility claim rests on a test matrix that drops the torn-tail recovery path — the one piece of the copied code with a history of being subtle. The plan's four architectural decisions themselves survive adversarial reading; the defects are in the seams between the plan's specified surface and what `dao.stream.rpc` actually provides.
