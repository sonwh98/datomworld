## Findings

1. **Float `**` guard boundary: CPython raises one half-ulp-band earlier than the implemented ≥ 2^1024.** `prelude.cljc:1206-1217` fires OverflowError when `|e| >> 1024 > 0`, i.e. |e| ≥ 2^1024. CPython 3.9.6 converts the exponent through double first, and int→double conversion overflows at the round-to-nearest threshold, not at 2^1024: measured `1.0 ** (2**1024 - 1)` → **OverflowError "int too large to convert to float"**, and the exact cutover is `1.0 ** (2**1024 - 2**970)` → OverflowError vs `1.0 ** (2**1024 - 2**970 - 1)` → 1.0 (DBL_MAX = 2^1024−2^971; values ≥ 2^1024−2^970 round to inf). So for |e| ∈ [2^1024−2^970, 2^1024) this profile computes (1.0 for ±1 bases; ±inf for |base|>1, consistent with the accepted inf posture) — and for negative e in the band `0.0 ** -(2**1024-1)` answers ZeroDivisionError where CPython raises OverflowError (conversion precedes the zero-base check there too). The brief itself (item 4b) specified ">= 2^1024", so the engineer implemented the binding faithfully; this is a brief-level simplification, and the two pins at 2^1024/2^1023 (`int_ops_test.cljc:570-589`) are each CPython-correct on their side of the line. Severity: **low** (needs |e| ≈ 1.797·10^308, reachable only via a computed big exponent). Exact fix, still constant-free: replace the quotient test with `(|e| >> 970) + 1) >> 55 > 0` — since `T = 2^1024 − 2^970` satisfies `T >> 970 = 2^55 − 1`, this fires exactly at T and above (T−1 gives `2^55−1 >> 55` = 0), uses only literals 970/55/1, and keeps the small-profile safety the engineer's shift form was after. Alternatively get an architect note logging the band with the other ruling-10 S4 amendments — but then disclose it in the findings the way the v2 exclusions are disclosed.
2. **Non-floaty negative exponent with |e| ≥ 2^1024 stays unguarded (pre-existing, out of this brief's scope).** `prelude.cljc:1218-1226`: `0 ** -(2**1024)` here → ZeroDivisionError "0.0 cannot be raised to a negative power" and `2 ** -(2**1024)` → 0.0 via the ruling-10 reciprocal path; CPython 3.9.6 converts the operands to double and raises OverflowError "int too large to convert to float" for both (measured). This is the S3-B-era float-path posture (same family as the accepted underflow delta), the brief scoped item 4b to "both floaty arms" only, and nothing in this diff changed it — but it is now the third manifestation of the same conversion rule, so it should ride explicitly with finding 1's fix or the S4 ruling-10 amendment list rather than being rediscovered. Severity: **low**. Exact fix if taken with finding 1: drop the `floaty` condition from the same guard (the corrected threshold test is exact for the int arm too; CPython converts in both arms).
3. **NIT (record; no action): CPython's huge-left-shift class past allocation scale is not MemoryError.** Measured: `1 << 2**64` → MemoryError but `1 << 2**100` → OverflowError "too many digits in integer" (newsize overflows Py_ssize_t). This profile answers MemoryError at every magnitude, which is what the architect's S3 table rules for the bit-limit and what the fast pins assert (`int_ops_test.cljc:561-568`, small-profile `1 << 60` and `1 << 2^59`). The corpus honestly excludes huge-count nonzero left rows and no pin claims CPython's class at those magnitudes — correct handling, just worth one sentence in the S4/S6 parity ledger.
4. **NIT (optional): augmented bitwise on a bool LHS is unpinned.** `x = True; x &= False` returns False (bool) through the same `py/bitand`, correct by construction, but the augmented pin (`int_ops_parser_test.clj:171-180`) uses a big int cell and the corpus covers only the non-augmented bool grid.
