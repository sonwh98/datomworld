### A.1 Findings

**P1-1. Dropping the sender's admission at restore breaks fenced recovery and the relift law for every real pack with an install child.**
The lift copies the install record's `response` whole into the `:install` row (`install-node`, `rows.cljc:1643`). The linker's interpreter puts `:yin.admit/id`, `:yin.admit/decision`, `:yin.admit/asserters` and `:yin.admit/address` on every successful DHT-admitted response (`interpreter.cljc:416-421`), so a real pack's `:install` row carries them. The new restore-side `dissoc` (`rows.cljc:2236-2237`) then produces a machine whose `:installs` response lacks the four keys. Consequences:
- `rehydrate-fenced` re-prepares and re-encodes the restored machine and demands byte equality with the published pack (`export.cljc:548-556`); the relift's install row now differs from the carried one, so every fenced recovery of such a pack answers `:yin.k/undecodable :recovery-inconsistent`.
- The harness law "the relift equals the lift by root" (`safepoint_harness_test.cljc:10`, asserted at `:629` via `canonical-under`) fails for the same packs.
The current tests pass only because every fixture response (`rows_support/module-response`, `blocking-body`) carries no `:yin.admit/*` keys. This is a correctness defect, not a test gap.
Required fix (revert-not-fix does not apply, this is the slice's own line): strip the four `:yin.admit/*` keys **at lift**, in `install-node`, so the pack never carries S's decision ("the carrier narrows, never widens", §4.1), and make the lower **refuse** a carried response that still carries any `:yin.admit/*` key as `:yin.k/undecodable :install-response` (one clause in `check-install!`'s existing `and`; hand-crafted packs only). Delete the restore-side `dissoc`. Then the restored response equals the carried one, fenced reproduction and the relift law hold by construction, and `link-install` sees no sender record. New pin for the mutant: a source whose install response carries the record lifts to an `:install` row without the keys (assert on the decoded row's slot 3), and a pack with the keys spliced back in is refused before attach with zero attaches. Keep the existing "installed entry has no `:admission`" assertion.

**P2-1. The holder driver has no seam to supply `:yin.k/admitted`, so the composition's real lower path refuses every pack with an install child.**
`driver/lowered` is called with `{:exclusive true}` (`driver.cljc:2294`) and with the grant map (`driver.cljc:1588-1600`); the fenced recovery at `driver.cljc:2455-2457` passes only `:address` and `:attach`. None forwards an admitted map. This is fail-closed (safe) but it means R4 as written makes carried install children unreachable through the holder, with no driver test noticing (`driver_test.cljc` has no install-child handoff; `:2726` fakes one for gate-mode only). Required for round 2, not for landing R4 alone: a config entry `(:yin.k/admitted-modules (:config state))` forwarded by `lowered` and by the fenced recovery call (two lines), plus one driver test that lowers a parked-installer checkpoint with and without the config. Until then, a known-gaps row "holder driver passes no admitted-modules map; install-child handoff through the driver refuses" (P2) must land with R4.

**P2-2. `:yin.k/admitted` already means two other things in the same vocabulary.**
It is a ledger fact kind, "one effect's dedup record with its result" (`ledger.cljc:22, 115, 553`), and the driver's not-holder answer field for the admitted variant set (`driver.cljc:743, 1655`). The threat model (§4.4, my text) chose the word carelessly. Rename the lower option to `:yin.k/admitted-modules` in `rows.cljc`, `export.cljc`, the five test files and the five doc amendments. Cheap now, a permanent vocabulary defect after commit.

## Part B: ruling on host-module ("nil") pins

### B.0 Facts the ruling rests on

- A host-registered entry has `:address nil` and lists its exports as `:yin.module/primitives {sym profile-address}` (`register-host-module`, `module.cljc:223-263`). `module/host-export-profile` answers exactly that profile address for a qualified symbol (`module.cljc:266-281`): a **keyword** `:yin.k.pp/blake3-…` minted by `vm/primitive-profile` over `{name class arities effects host-state}` (`vm.cljc:338-356`). Plain data, no functions, no host objects. The core `stream` and `cell` modules are host modules with literal cljc profiles and `:none` host-state (`module.cljc:350-363, 405-410`), so their addresses are identical on JVM, Node and Dart.
- The linker already defines "satisfied by equal profile" for exactly this case: `declared-discharge` discharges a primitive obligation by `(= profile (module/host-export-profile modules name))` (`linker.cljc:1014-1018`), and a module obligation by equal manifest address (`:1022-1027`). UCF §7.6.5 already carries `:yin.k/primitives {name <expected profile>}` in the outcome.
- The lift's `discharge!` answers a qualified free name by registry presence (`rows.cljc:1611-1616`) and nothing of the entry travels. The task row's `requires` slot is a plain map (`rows.cljc:1687-1689`), so two more keys cost no slot change.

### B.1 Ruling

1. **Host modules participate in this slice.** Not deferred. Reason: `stream` and `cell`, the most common modules in any pack, are host modules; deferring leaves R6 (silent skew) open for the common case while closing it only for DHT-linked modules. The data is already pure, the comparison already exists in the linker, and the lift already resolves the entry. The risk of implementing is one more `requires` key and a fixture re-mint, both owed anyway for `:yin.k/modules`. The risk of deferring is a second re-mint later and a documented hole in the fetch-loop contract.

2. **What the lift records.** Only what the live code uses: for every live free name `ns/f` that `discharge!` answered through the registry (`rows.cljc:1614-1616`, after `E`, store, primitives and installing names, which stay as they are):
   - `:yin.k/modules` gets `{ns <manifest address>}` when the entry is linked (`(:address entry)` non-nil), `{ns nil}` when it is host-registered;
   - `:yin.k/host-exports` gets `{ns/f <profile address>}` when the entry is host-registered, the value being `(module/host-export-profile (:modules m) 'ns/f)`.
   Not all exports. Recording all exports would refuse a receiver whose host module gained or changed an export the code never touches, and it would persist what the free-name scan already derives. A lift where `host-export-profile` answers nil for a name the registry claims to hold (an entry with a malformed `:yin.module/primitives`) is `:yin.k/non-portable :host-export-profile {:yin.k/name ns/f}`.

3. **Canonical encoding.** Two maps in the task row's `requires` beside `:yin.k/segments`, `:yin.k/trees` and `:yin.k/cursor-profiles`: `:yin.k/modules {symbol -> string-or-nil}` and `:yin.k/host-exports {qualified-symbol -> keyword}`. Keys sorted by the carrier's existing rules for symbol keys; the `keyed`/`built` host-collapse discipline applies (module names contain dots, no slash; a qualified export has one slash, so the known P3 `keyed` gap does not reach these maps, but add the count guard anyway as the `built` precedent). Absent maps are not emitted when empty (same as `:yin.k/trees` with no segments is still emitted; follow whatever the existing `requires` does for empties, byte-stable). No richer value in `:yin.k/modules`: a tagged vector `[:host profiles]` beside address strings mixes value kinds in one slot and duplicates the primitives precedent for no gain.

4. **How the lower compares** (new `check-modules!`, one pass over the whole tree, after `check-custody!`, before `attach-streams!`, absorbing today's `check-install-admission!`):
   - `:yin.k/modules {ns address}`: receiver's `module/resolve-module` entry exists with `(= address (:address entry))` → satisfied. Entry exists with another address (including a host entry, nil, where a linked one was pinned, or vice versa) → **terminal** `{:yin.k/status :yin.k/unsatisfied :yin.k/kind :module-pin-mismatch :yin.k/name ns :yin.k/pinned address :yin.k/linked (:address entry)}`, the `:dependency-pin-mismatch` words (`engine.cljc:1388-1393`). Entry absent → collected into `:yin.k/missing {:yin.k/modules {ns address}}`.
   - `:yin.k/host-exports {ns/f profile}`: `(= profile (module/host-export-profile (:modules recv) 'ns/f))` → satisfied. Receiver answers another profile → **terminal** `{:yin.k/status :yin.k/unsatisfied :yin.k/kind :host-export-mismatch :yin.k/name ns/f :yin.k/pinned profile :yin.k/held <receiver's>}`. Receiver answers nil (no such export, or the module is absent, or it is linked rather than host) → collected into `:yin.k/missing {:yin.k/host-exports {ns/f profile}}` (the `:yin.k/modules {ns nil}` entry will be in the same map when the module is absent).
   - Receiver's host module exporting **more** than the pin names: satisfied (subset by construction, since only used exports are pinned). Equality is of profile addresses, never of normalised profile maps: the address already covers name, class, arities, effects and host-state.
   - Carried install children: `:yin.k/admitted-modules {ns address}` equality as today; unlisted → collected into `:yin.k/missing {:yin.k/modules {ns carried-address}}`.
   - Order: terminal mismatches are thrown first (nothing the composition can fetch repairs them), then one collected refusal `{:yin.k/status :yin.k/unsatisfied :yin.k/discovery :complete :yin.k/missing {…}}` with keys present only where something is missing. Zero attaches in every case.
   - The fetch loop (composition, not this slice) requires only keys of `:yin.k/missing :yin.k/modules` whose pin is non-nil; a nil pin and every `:yin.k/host-exports` entry are composition prerequisites and are not fetched.

5. **Determinism across hosts.** Profile addresses are BLAKE3 content hashes over plain data computed identically on all three hosts (the same mechanism Stage E already pins for primitives); manifest addresses are segment keys. The refusal maps are plain data. Pin T8 in `stage_e_rows_test.cljc`: a `requires` with both maps re-encodes byte-identically and the two terminal refusals and the collected refusal are `=` across JVM, Node and Dart.

6. **Threat-model text amended by this ruling.** §4.2's shape gains `:yin.k/host-exports`; "whose export profiles equal those the lift recorded" becomes "whose profile address for each used export equals the pinned one"; §4.4's option is renamed `:yin.k/admitted-modules` and its refusal is folded into the collected shape with `:yin.k/discovery :complete`. T4 reads: a nil pin plus `:yin.k/host-exports` is satisfied by a host module answering equal profile addresses for the pinned exports; another profile for a pinned export refuses `:host-export-mismatch`; a missing export is collected as missing; extra exports are ignored.

### B.2 Alternative considered and rejected

"Refuse nothing for nil pins, document, defer": `:yin.k/modules {ns nil}` would then only assert "a host module of this name must exist", which `resolve-var` already enforces at run time, and skew in `stream`/`cell` profiles between two compositions would still run under R's authority (R6, R8 for the common case). The saving is one map and one lift line; not worth a second re-mint. Rejected.
