Rule R is a sound direction for making definitions unshadowable, but Fable’s enforcement plan is not yet complete. This was a read-only review; no suites were rerun.

Factual claims:

- **PARTLY — `def` is already a special form.** The Yang frontend recognizes `def` before ordinary variable lookup, but lowers it to an ordinary application of `yin/def`; the VM does not yet preserve its special-form meaning (`src/cljc/yang/clojure.cljc:132-160`).
- **TRUE — `yin/def` is an ordinary primitive today.** Its registry entry returns a `:vm/store-put` effect (`src/cljc/yin/vm.cljc:194-197`).
- **TRUE, narrowly — all four engines use the shared variable resolver.** The walker, semantic, stack, and register engines call `engine/resolve-var`, whose order is environment → store → primitives → modules (`src/cljc/yin/vm/ast_walker.cljc:379`, `src/cljc/yin/vm/semantic.cljc:263-267`, `src/cljc/yin/vm/debruijn/stack.cljc:386-390`, `src/cljc/yin/vm/debruijn/register.cljc:390-395`, `src/cljc/yin/vm/engine.cljc:54-73`). Direct store instructions do not use it.
- **FALSE as stated — only primitives raise effects, and all other store keys are syntactically visible.** Built-in store instructions write directly, and a composition-supplied host function can return an effect with a computed key; effect dispatch accepts it (`src/cljc/yin/vm/ast_walker.cljc:419-438`, `src/cljc/yin/vm.cljc:143-150`, `src/cljc/yin/vm/module.cljc:77-80`, `src/cljc/yin/vm/engine.cljc:510-516`). The literal-key claim holds for the portable built-in store instructions, not every executable path.

P2 | `collab/1790341000000-architect-yin-def-unshadowable.claude-fable-5-1.findings.md:19` | “The symbol `yin/def` may occur only as operator” conflates a variable occurrence with quoted data. “Sound and complete for constant keys” is achievable **for admitted images under a single revised execution contract**: a valid `yin/def` application would always define its literal key, while the existing invocation position correctly places the write after its value operand (`src/cljc/yin/vm/linker.cljc:427-468`). It is not established by the present proposal across macro ingress, direct execution, and old-contract or foreign engines.

A dedicated `:vm/define` node is not inherently contrary to “derive, don’t persist”: it would encode a distinct operation once, but would migrate the row grammar and content hashes (`src/cljc/yin/vm.cljc:795-807`). Keeping the current application shape is reasonable if one shared recognizer governs validation and lowering and the walker has matching transition tests. Fable is right to reject primitives-first lookup: it would leave `yin/def` first-class and aliasable. Once Rule R is fully enforced, the round-3/4 shadow filters and `:yin-def?` bookkeeping can go (`src/cljc/yin/vm/linker.cljc:401-424`, `src/cljc/yin/vm/linker.cljc:474-478`); constant-key recognition, invocation positioning, dominance, and the earlier fetch-bound fixes must stay (`src/cljc/yin/vm/linker.cljc:301-319`, `src/cljc/yin/vm/linker.cljc:427-468`).

Land a complete, independently gated Rule R change before M2 if two commits can each remain coherent. Do **not** use Fable’s validator-only M2 fallback: direct execution and dynamic host effects remain outside that proof (`collab/1790341000000-architect-yin-def-unshadowable.claude-fable-5-1.findings.md:69-75`). Update the contradictions Fable identified in UCF and the linker, and also the macro contract’s stored-macro lookup, the semantic/stack/register instruction contracts, and code-as-tuples’ assertion that the `yin/def` operator is free (`docs/design/yin.vm.macro.md:373-396`, `docs/design/yin.vm.semantic.md:231-257`, `docs/design/yin.vm.debruijn.stack.md:325-340`, `docs/design/yin.vm.debruijn.register.md:369-385`, `docs/design/yin.vm.code-as-tuples.md:1828-1832`). Store-update discovery may remain deferred; the admission, macro, and contract gaps above cannot.
