# Cursor-cell numbering by discovery order (companion to the row carrier)

Status: **Adopted by the owner 2026-10-12 (replaces carrier §6's
refinement and search); not yet implemented.** Written 2026-10-12
(Architect, claude-fable-5-1) for the owner's observation that "the
problem is not that the cursor cell has identity, but that the identity
is local", and the orchestrator's proposal to number cursor cells by
**discovery order** in a canonical traversal. Revised twice the same day
after independent reviews (gpt-6.1-sol,
`collab/1792140000000-…findings.md` and `collab/1792170000000-…findings.md`).
Round 2 repaired the orbit lemma (`#{[X X] [Y Z]}`) and nested tie groups
(`#{#{X Y} #{Z W}}`). Round 3 (this text) fixes what the second review
found: which local conflicts refuse (§2 D5, witness
`[#{#{[A B] [B A]}} A]`), the install-child refusal escaping decode, the
work bound (now an explicit budget, with body labels spelled by rank so
key bytes no longer grow with a stream descriptor), the A2 wording, the
size estimate, and the coverage regression against 6a (2-cycles and
3-cycles), for which §2 D6 specifies and §6 measures the repair. §8 lists
what an implementation deletes, rewrites and keeps in 6a. Subordinate to
[`yin.vm.ucf-transport-tuples.md`](./yin.vm.ucf-transport-tuples.md)
(the carrier, body version 3) and
[`yin.vm.semantic-register-vm.continuation.md`](./yin.vm.semantic-register-vm.continuation.md);
vocabulary is UCF §7.5.3 ("Terminology: cursor, cursor cell, cursor-ref,
cell") exactly. Evidence is the carrier draft §5/§6 tables, slice 6a's
`src/cljc/yin/vm/ucf/rows.cljc` and `test/yin/vm/ucf/rows_test.cljc`
(branch `srvm-phase6a` at `d77da9f0`), and a prototype run against that
code (§6). Nothing here is implemented.

**In one line:** number cursor cells in the order a canonical traversal
meets them (D1–D2); order the elements of a guest set or map by a key
that is the spelling of a speculative local run over the element (so
alias patterns such as `[X X]` versus `[Y Z]` are part of the key);
defer equal keys and re-examine them to a fixpoint (D3); at a fixpoint,
link tied elements that share an unnumbered cursor cell into components
and enter the component of least complete encoding (D4); a component
holding two equal-keyed elements of one container is the one case this
cannot certify: refuse it (D5), or resolve it by a bounded residue search
over that component alone (D6, recommended). Proof in §3, budget in §2
"Work", results in §6, the cut against 6a in §8.

## 0. Vocabulary used below

- **Canonical traversal order** is the order D1 defines: a function of
  the abstract task alone. **Host enumeration order** (also "listed
  order") is the order in which a host happens to list the elements of a
  guest set or the entries of a guest map, or the census; it is an
  accident of the host. The procedure reads it in exactly one place, D4's
  entry of components of equal encoding, where lemma C shows it cannot
  change the result.
- An **element** is a `:set` element or a `:map` entry `[key value]`
  (the key is a guest value and may be a cursor cell).
- A **numbering** `N` is a partial map from the task's cursor cells to
  positive integers, injective, assigned in increasing order; `|N|` is
  its size. The emitted id of a cell numbered `k` is `:yin.k/cc-k`.
- A **run** is one execution of the traversal-and-resolution procedure
  over one item (a row or a value) from a starting numbering. The **root
  run** is the run over the `:task` row from the empty numbering; its
  numbers are the output. A **local run** is a run over one item from
  the enclosing run's current numbering. There are three kinds of local
  run, and the distinction decides what refuses (D5):
  - a **key run** is a local run over one element, made to compute the
    element's sort key; it is *speculative*: it never refuses, and
    whatever it cannot resolve (a tie, a conflict) is spelled in its
    key as `[:tie …]`;
  - a **component run** is a local run over a component's synthetic
    `[:component …]` row (D4); it must be *complete*, else D5;
  - a **trial** (D6 only) is a component run that enters one chosen
    element before its siblings.
- A **body label** is `[:body [:stream identity descriptor] position]`,
  a cursor cell's census body as plain data; its **rank** is its index
  among the census's distinct body labels in bytewise order.

## 1. Findings

**F1. Every non-guest position is ordered.** From the carrier §5 tables
(and `rows/row-table`, `rows.cljc:37-57`), the positions that can hold a
cursor-ref (`[:cursor-cell C]`) or a bare `C` slot, and their order:

| Position | Order | Canonical index |
|---|---|---|
| `:task` slots 5 `free-env`, 6 `store`, 8 `parked`, 15 `result`; `:wait` state, pending; `:act` env, window, k; `:tail` k; `:kframe` env, window; `:reified` act; `:env` and `:closure` bindings; `:module-store` store; `:pending` `cursor-cell-C`, `response-cursor-cell-C`, `value-V`, `envelope-V` | fixed slot | slot index |
| `:task` 7 `module-stores`, 12 `installs` | keyed by `M`, by module name | Jing bytes of the key; the child is a task boundary |
| `:task` 13 `frames`; `:k`; `:vec`, `:list` elements | ordered vector | position `i` |
| `:window` | keyed by register `N` | `N` ascending, numerically (carrier §5.2) |
| `:bindings` (environments, closures, the free environment) | keyed by symbol `S` | Jing canonical bytes of `S` (§5 preamble: "sorted") |
| `:store`, `:parked-table` | keyed by `D`, by `P` | bytes of the key; a parked-table value is a structural `:act`/`:tail` reference, entered like any row |
| `:set` elements | **unordered** | none |
| `:map` entries | **unordered** (keys are `V`) | none |
| `:cursor-cells` census | not a position (carrier §6 step 2, §8 step 3) | — |

So the only unordered positions are guest `:set` elements and guest
`:map` entries. Both reviews confirmed the inventory complete. The
example state in `collab/example-suspended-state.clj` holds its one
cursor cell (`:cursor-1`) in three ordered positions: the act's
environment under `c`, the window under register 2, and the `:next`
pending's `cursor-cell-C` slot.

**F2. Discovery order subsumes the positions step.** The carrier's §6
step 3 (positions) exists to let a cursor cell's number depend on where
it occurs. A canonical traversal (D1) visits every ordered position in a
fixed order, so "the n-th cursor cell met" already encodes the first
position of each cursor cell; later positions cannot change an assigned
number and need not be collected. Refinement (step 4) and search (step 5)
existed only to turn position multisets into a total order; discovery
order is a total order by construction.

**F3. Unordered containers are ordered by a content encoding that
carries the alias pattern.** The first draft spelled an unnumbered cursor
cell by its body alone, so `[X X]` and `[Y Z]` encoded alike. The
repaired encoding (§2 "Spelling") numbers the cursor cells *inside* an
element provisionally, in the element's own discovery order, relative to
the enclosing numbering: `[X X]` spells `[(u0) (u0)]`, `[Y Z]` spells
`[(u0) (u1)]`, so alias topology inside an element is part of its sort
key, as a de Bruijn index is part of a term. The key of an element is the
spelling produced by a *key run* over it, which applies the same rules
recursively (nested containers sorted, nested ties deferred and
re-examined, D4 inside) and spells what it cannot resolve as `[:tie …]`.
Equal keys form a **tie group**, deferred to the run's worklist and
re-examined to a fixpoint (D3) as other positions assign numbers. A
provisional cell is spelled with its body *rank*, not its body label, so
a key's size depends on the element's structure and not on the length
of a stream descriptor (§2 "Work").

**F4. What refuses, and what is lost against 6a.** What survives a run's
fixpoint is a worklist of tie groups whose unnumbered cursor cells occur
only inside tied elements. Link two tied elements when they share an
unnumbered cursor cell; a connected set of tied elements is a
**component**. Two cases:
- *Certified*: no component holds two elements of one group. Every
  component is then encoded by a component run over its elements in
  group order (so a component spanning two groups, `[#{X Y} #{X Y}]`,
  spells its shared cell once with one index), components are sorted by
  that encoding, and the least run of equal encodings is entered in host
  order. Equal encodings here mean *isomorphic* components (§3, lemma C).
  `#{X Y}`, `#{[X X] [Y Y]}`, `{X 1, Y 1}`, `#{#{X Y} #{Z W}}` and
  `[#{X Y} #{X Y}]` are this case.
- *Conflict*: some component holds two elements of one tie group. Then
  entering either element first is a choice D1–D4 cannot show to be
  harmless. **Which runs refuse.** Only the *root run* and *component
  runs* refuse on a conflict (D5). A *key run* never refuses: it is a
  speculation made to sort, its unresolved residue is spelled `[:tie …]`
  in the key, and the enclosing run may resolve the same elements later.
  The second review's witness is exactly this: in `[#{#{[A B] [B A]}} A]`
  the key run over the inner set reaches a conflict (`[A B]` and `[B A]`
  tie and share both cells), the outer set has one element and is
  entered, the inner tie is deferred to the root worklist, index 1 meets
  `A = cc-1`, and the root fixpoint separates `[A B]` (`[(n 1) (u0)]`)
  from `[B A]` (`[(u0) (n 1)]`), so `B = cc-2`; the lift numbers and the
  receiver recomputes the same root (`9600fe01…`, the review's digest).
  The earlier text's "at any fixpoint of any run" was wrong and is
  replaced in D5, lemma D and A1.
  The predicate, in one sentence: *a state is refused under D5 iff the
  root run, or a component run it requires, reaches a fixpoint at which
  two elements of one guest set or map have equal keys and are connected
  by a chain of shared unnumbered cursor cells through tied elements.*

  **Exactly which structures that is.** A D5 state needs two or more
  cursor cells with *equal bodies* (same stream identity and descriptor,
  same position) that are held *only* through guest sets or maps, in
  elements that each mention more than one of them, with equal keys. The
  smallest are the directed 2-cycle `#{[A B] [B A]}` and the directed
  3-cycle `#{[A B] [B C] [C A]}` (both interchangeable: the swap and the
  rotation are automorphisms, so any entering order gives the same rows,
  and 6a numbers them); the path `#{[A B] [B C]}` and the seven-cell
  triangle plus square (`rows_test.cljc:392-404`) are refused and
  genuinely need a tie-break (§6: two and four distinct roots under
  host-order entry); the loop plus 2-cycle `#{[L L] [A B] [B A]}`
  (`rows_test.cljc:312-329`) numbers `L = cc-1` by its key and conflicts
  on `{A, B}`. One register, environment binding, pending slot or vector
  position holding any one of the cells breaks the tie for the whole
  component (`[#{X Y} X]`, the witness above). **Are they common in
  realistic suspended tasks?** Unmeasured: the repository has no
  version-3 task corpus (the Stage E scenarios and the v2 handoff census
  tests hold cursor cells but no v3 lift exists before 6b). The structural
  argument is that a cursor cell is created into a register
  (`:stream/cursor` delivers to `rd`, engine `:2595-2602`) and reaches a
  guest set only by guest code that builds a set of tuples of cursors on
  one stream at one position and then drops every other reference; of
  the repository's own fixtures only the two built for the purpose hit
  D5, and under a tie-biased generator the rate is 35 of 2300 (§6).
  Because the rate is unmeasured and 6a numbers the 2-cycle and 3-cycle,
  this note does not leave the regression as a documented limitation:
  **D6** (§2) is the minimum extra rule that repairs it, a search over
  the conflicting component only (two trials for a 2-cycle, three for a
  3-cycle, eleven for the seven-cell state), prototyped and measured in
  §6: with D6 every one of the 2300 generated states numbers, the 2-cycle
  and 3-cycle reach 6a's exact roots, and no D1–D4 numbering changes.
  The owner's choice between D5 (refuse, no search anywhere) and D6
  (bounded residue search) is §10 question 1; this note recommends D6.

**F5. The scheme is canonical.** Proved in §3: the output (rows or

## 2. The rule (replaces carrier §6 "The procedure")

Input: the abstract task of carrier §6 (the §5 structure with cursor
cells as identities, before numbering). Output: a bijection from the
task's reached cursor cells to `:yin.k/cc-1 … :yin.k/cc-n`, or a
refusal. Install children are numbered as their own tasks by the same
rule (task boundary, unchanged), in any order, since scopes are disjoint.

**Spelling (the content encoding `CE`).** A run spells the item it has
traversed under its final numbering. The root run spells a cursor cell
numbered `k` as `[:cursor-cell [:n k]]`, `k` an exact integer; a local
run spells a cursor cell it numbered itself (index `j`, counted from the
enclosing run's local counter) as `[:cursor-cell [:u j r]]`, `r` the
cell's body rank (an exact integer; rank order equals body-label order,
so no comparison and no numbering changes against spelling the label,
and the key's size no longer depends on the descriptor), and a cursor
cell numbered by an enclosing run as that run spelled it. Nothing else
changes from carrier §6 step 2: `[:lit d]` as itself, `[:row B]`
expanded in place, structural data as itself, the census as
`[:cursor-cells]`, an install child as `[:child]` (replacing step 2's
`[:child <child root id>]`: a child sits only under a name-keyed install
entry, never inside an unordered container, so its content never decides
an order, and the encoding stays hash-free). Keyed structural rows are
spelled in their canonical key order, `:window` in numeric register
order; a `:set` or `:map` is spelled as the bytewise sorted vector of its
elements' spellings (an entry as `[:entry K V]`), duplicates retained,
where a tie group the run could not resolve is spelled in place as
`[:tie K … K]` (its common key, once per element). All comparisons are
bytewise on canonical CBOR of these synthetic vectors. `CE` is hash-free.

**D1. Traversal.** Depth-first, pre-order, from the run's root item. A
row's slots are visited in table order. Ordered repeated slots
(`frames`, `:vec`, `:list`, `:k`) in order. Keyed rows with structural
keys (`:bindings`, `:store`, `:parked-table`, the root's `installs` and
`module-stores`) in the Jing canonical byte order of the key, the order
§5 emits; `:window` in ascending numeric register order as the carrier
specifies. The census is not entered; an install child's `:task` row is
not entered. A `:set`'s elements and a `:map`'s entries are each given a
**key**: the spelling of a key run over the element under the numbering
at the moment the container is entered (every element keyed from that
one numbering). Elements are then taken in bytewise key order: a run of
equal keys is a **tie group**, appended to the run's worklist (deferral
order is canonical: containers in traversal order, groups within one
container in key order); every other element is entered in key order,
an entry's key before its value.

**D2. Meeting.** When the traversal reaches an identity position (a
`[:cursor-cell C]` value or a `C` slot of a `:pending` row) whose cursor
cell has no number, the cursor cell receives `|N| + 1` (the root run
counts from 1; a local run counts its own cells from the enclosing run's
local counter, so a nested local run never reuses an index of its
enclosing run). An already numbered cursor cell is passed over. There is
no first-occurrence spelling: every occurrence emits
`[:cursor-cell :yin.k/cc-n]` and the census row (carrier §3) stays the
contents table.

**D3. Fixpoint.** After the traversal, the worklist's groups are
re-examined in deferral order: each group's elements are re-keyed under
the current numbering and taken as in D1 (singletons entered, equal runs
re-deferred in order). Repeat while a round numbers at least one cursor
cell and groups remain. Entering an element inside a group runs D1 on
it, so a group discovered *inside* an entered element (`#{#{X Y} #{Z W}}`)
joins the same worklist and is re-examined in the next round; there is
one worklist per run, and the root run's worklist collects deferred
groups from every depth.

**D4. Components.** When a fixpoint is reached with groups remaining,
link two tied elements (of any groups) that share an unnumbered cursor
cell; a connected set of tied elements is a **component**. (At a
fixpoint every unnumbered cursor cell occurs only inside tied elements,
so all of its occurrences lie in one component.) Encode each component
by a component run over the synthetic ordered row
`[:component g₁ i₁ g₂ i₂ …]` in group order, `gᵢ` the group's deferral
sequence number (a datum) and `iᵢ` the component's one element of that
group, or, when the component holds several elements of group `gᵢ`, a
synthetic `:set` of them (the D5/D6 case). A component run must be
complete (no `[:tie]` in its spelling); it is incomplete only when it
reaches a conflict of its own, which D5 or D6 decides. Sort the
components by their encodings and **enter the run of least encoding**:
each of its components has its component run's cursor cells numbered,
in that run's local-index order, continuing the enclosing run's
numbering; components of equal encoding are entered in host order (§3,
lemma C: equal encodings are isomorphic and the result is the same).
Remove the entered elements from their groups and return to D3. A group
whose elements mention no unnumbered cursor cell holds equal values (the
carrier refuses the duplicate at §8 step 5); its elements are entered in
host order, which numbers nothing and emits identical rows.

**D5. Conflict, and refusal without D6.** A component **conflicts** when
it holds two elements of one group. Without D6, a conflict reached by the
root run, or by a component run (directly, or through a nested component
run of its own), refuses the lift: `:yin.k/non-portable` kind
`:unresolved-cursor-cells`, `:yin.k/path` the row path of the container
holding the least conflicting group (for an install child, prefixed
`[12 <install name> …]`), and `:yin.k/cursor-cells` the sorted unnumbered
cursor cells of every conflicting component at that fixpoint (so the
diagnostic, like the verdict, does not depend on host order). A key run
never refuses (§0; F4). A receiver that reaches D5 while recomputing
refuses `:yin.k/undecodable` kind `:unresolved-cursor-cells`. Neither is
a resource refusal and neither is `:noncanonical-cursor-cells`.

**D6. Residue search (recommended; the repair of F4's regression).** A
conflict is resolved instead of refused: let `g` be the least conflicting
group of the component and `E` the component's elements of `g`. For each
`e ∈ E` run a **trial**: a component run over the same `[:component …]`
row in which `e` is entered first when its container is keyed, before
its siblings are keyed (so `e`'s cursor cells take the first local
indices and its siblings are keyed against them), and which runs to
completion by D1–D6. Each trial charges `:search` one unit. The
component's encoding is the least trial spelling, and entering the
component adopts that trial's numbering (D4). Equal least spellings are
isomorphic and either may be adopted (§3, lemma E). With D6 no
structural refusal remains: the only refusals of the procedure are the
resource refusals of "Work" below, and `:unresolved-cursor-cells` is not
defined. With D6 in force, 6a's `:search` budget key stays and counts
trials; without it, the key is deleted.

**Totality.** The root run ends with an empty worklist or a refusal.
Before emission the implementation asserts that the numbering is a
bijection from the census's cursor cells onto `1 … n`; a violation is a
defect (an exception naming the missing or extra cursor cells), never a
refusal, and never a partially numbered carrier.

**Memoization (implementation note, not part of the definition).** A
local run's result is a function of its item, of the enclosing numbering
restricted to the item's cursor cells, of the enclosing local counter and
(D6) of the forced element; an implementation may memoize on that key and
must return the numbering restricted to the item's own cursor cells (the
prototype's one bug during round 2 was returning the whole numbering of
another element's context, which the decode round trip caught). The memo
holds only spellings that were paid for under `:work`, so it adds no
unaccounted bytes. No bound on the number of distinct memo contexts is
claimed; the memo is an optimization and the budget is the bound.

**Validation and decode.** Unchanged in form: the receiver decodes, runs
the root run, re-emits and compares root ids (`:noncanonical-cursor-cells`
on mismatch). In 6a's `decode*` the recomputation is `emit` itself
(`rows.cljc:570-575`), which numbers the root *and every install child*
(`emit-node`, `:185-189`); the **whole** of that call is wrapped so that
only a lift-side `:yin.k/non-portable` of kind `:unresolved-cursor-cells`
(D5, from the root or from a child) is translated to `:yin.k/undecodable`
kind `:unresolved-cursor-cells` with `:yin.k/path` prefixed by the
carried root id (a child's path then reads `[<root id> 12 <name> …]`);
a resource refusal (`:yin.k/unsupported :resource-limit`) propagates as
itself; no other non-portable kind can arise there, because step 5 has
already checked literals and markers. The second review's escape (an
install child's D5 leaving `decode*` as `:yin.k/non-portable` with path
`[:child 15]`) came from translating only the root's numbering; the
prototype now wraps the whole recomputation and the case is in §6. The
validator order stays: step 6 (numbering) after step 5 and before
`validate-frames` (`rows.cljc:576-578`; test
`numbering-precedes-frame-defect`, `rows_test.cljc:206`). With D6 the
translation has nothing to translate and is omitted.

**Work.** No polynomial bound is claimed. The second review showed the
round-2 bound counted positions but not bytes (a 65536-character stream
descriptor multiplied key bytes by 170 at fixed `P`, `d`, `n`, `m`) and
that memoization's benefit across differing local contexts is unproved.
The procedure is instead *accounted*, as 6a already accounts refinement:
the `:work` budget is charged one unit per position visited (D1, D3,
every local run) and one unit per position spelled plus one unit per
byte of literal or structural datum copied into a spelling, before the
copy; `:search` (D6) is charged one unit per trial; `:depth` bounds the
structural depth as today, `:cursor-cells` bounds `n`, `:rows` the
carried rows and `:bytes` the carried bytes. Exceeding any budget is the
resource refusal of carrier §10.10 (`:yin.k/unsupported :resource-limit
[<key>]`), never a canonicality verdict, exactly as 6a's `:label-bytes`
was. The budget charges every allocated spelling byte before allocation,
so the bytes materialized at any time are bounded by `:work` plus the
carried bytes. What the rank spelling guarantees is narrower and exact:
a key's bytes are a function of the element's expanded structure and of
the number of distinct bodies, not of the bodies' sizes (§6: 1396 key
bytes at both 128 and 65536 descriptor characters). The crude bound
without memoization is `O(P · (n + 1)^(d + 1) · log m)` positions and
`O(B)` bytes per spelling (`P` expanded positions counted per reference,
`B` expanded bytes, `d` the unordered-container nesting depth, `n` cursor
cells, `m` the largest container), which the budget enforces rather than
the analysis. Measured: every fixture of §6 charges under 1000 `:work`
units, the 2300 generated states at most 1470, against 6a's default
200000; the seven-cell state charges 488 and 11 trials under D6. The
`:label-bytes` budget disappears with the growing labels.

## 3. Proof of canonicality

Call two configurations (abstract task, partial numbering, worklist)
**isomorphic** when a bijection `π` of cursor cells carries one to the
other: the structures agree up to renaming by `π` and up to the host
order of every unordered container and of the census, numbers agree
(`N'(π(c)) = N(c)`), and worklists correspond group by group in order.
The proof is a simultaneous induction over runs, ordered by (number of
unnumbered cursor cells of the run's item, nesting depth of the item):
a key run, a component run or a trial is over an item with no more
unnumbered cells than its enclosing run and strictly fewer nested
unordered containers, or (a trial) strictly fewer unnumbered cells; so
the lemmas below may assume themselves for every local run a run spawns.

**Lemma A (keys are canonical).** The key of an element is the spelling
of a key run over it, and a key run reads only structure, body ranks
(the rank of a body is a function of the census up to isomorphism) and
numbers; its own listed-order inputs are (i) element order inside nested
containers, which it never uses except through keys, by the induction,
(ii) the host order of components of equal encoding in its D4 step,
covered by lemma C, and (iii) nothing else: a key run that reaches a
conflict does not choose, it spells the residue `[:tie K … K]`, which is
a function of the group's common key and size. So isomorphic items under
corresponding numberings have byte-identical keys, and the sorted order
of a container's elements is a function of the configuration up to
isomorphism.

**Lemma B (ties are exactly what keys cannot separate).** By
construction: elements are deferred iff their keys are equal bytes.

**Lemma C (components).** At a fixpoint let `C₁ … Cₘ` be the components
of one run of equal encodings, each encoding complete, and let
`U₁ … Uₘ` be their unnumbered cursor cells. The `Uᵢ` are pairwise
disjoint and each `Uᵢ` is confined to `Cᵢ` (every occurrence of an
unnumbered cell lies in a tied element, hence in its own component).
Equal, complete encodings of `[:component g₁ i₁ …]` rows are a faithful
spelling (literals as themselves, rows expanded, every cursor cell by
index and body rank, groups by sequence number, a group's several
elements as a sorted set), so they exhibit, for each pair `Cᵢ, Cⱼ`, a
bijection `Uᵢ → Uⱼ` under which the components are the same structure
group by group. Entering the run in host order `σ` gives the cells of
`C_{σ(t)}` the numbers `b + (t−1)·|U| + 1 …` by local index; in order
`σ'` the cells of `C_{σ'(t)}` receive the same numbers. The block-swap
bijection composed from the pairwise bijections is an isomorphism of the
two resulting configurations: numbers agree by construction, structures
agree because the swapped components are isomorphic and nothing outside
them mentions their cells, and the worklists agree because the same
groups remain, with the same elements removed. ∎

**Lemma D (the D5 verdict is invariant).** Whether the root run, or a
component run it requires, reaches a fixpoint with a conflicting
component depends only on which tied elements share unnumbered cursor
cells at that fixpoint, which is a function of the configuration up to
isomorphism (lemma A gives the ties, the sharing relation is structural);
and whether a component run is complete is the same question one level
down, by the induction. Key runs do not enter the verdict: their
conflicts are spelled, not refused, and the spelling is canonical (lemma
A iii).

**Lemma E (D6 trials).** At a conflicting component the set `E` of
elements of its least conflicting group is a function of the
configuration up to isomorphism (lemma D names the component and its
groups canonically). Each trial is a deterministic function of (the
configuration up to isomorphism, the chosen element), by the induction
on the trial run, which has strictly fewer unnumbered cells than the
enclosing run (its forced element holds at least one, being linked into
the component by a shared unnumbered cell). So the multiset of trial
spellings is canonical and its least member is canonical. Two trials
with equal least spellings have produced isomorphic numberings of the
component (faithful spelling, as in lemma C), so adopting either yields
isomorphic configurations. ∎

**Theorem.** The procedure's output on isomorphic configurations is the
same: both refuse at corresponding points, or both emit byte-identical
rows. *Proof.* By the induction above. D1 and D2 decisions are functions
of the configuration up to isomorphism (lemma A); D3 only repeats D1 on
deferred groups in a canonical order; D4's choice of the least run is
canonical (lemma A on component encodings, which are complete by D5/D6)
and its only listed-order input is harmless (lemma C); D5 is invariant
(lemma D); D6 is invariant (lemma E). Emission spells cursor cells by
number only and sorts every emitted unordered slot by canonical bytes
under the final numbering (carrier §5), so isomorphic final
configurations emit the same rows. ∎

Consequences:

1. *Function of structure, renaming-invariant, enumeration-invariant*:
   the theorem with `π` a renaming, a permutation of the containers, or
   both. No decision reads a source id or a host order except at the
   point lemma C covers.
2. *Terminating.* The structural edge family is acyclic (carrier §8 step
   3), so every traversal is finite. In any run each D3 round that is not
   the last numbers a cursor cell; each D4 step numbers at least one
   cursor cell or removes a duplicate group; each local run is over an
   item with fewer unordered containers nested below it than its
   spawning run's item, or (a trial) with fewer unnumbered cells, so the
   induction measure of §3 decreases and there are finitely many local
   runs. The budget of §2 "Work" is what bounds the count.
3. *Deterministic*, hence two lifts of one state are byte-identical and
   the receiver's recomputation is well defined.
4. *Sharing survives*: the numbering is a bijection on reached cursor
   cells (D2 never renumbers; totality is asserted), every occurrence of
   one cursor cell spells one number, and two cursor cells at one
   position get two numbers.
5. *Cross-engine law*: two engines lifting one canonical frame produce
   abstract tasks equal up to renaming (the frame is engine-independent,
   continuation §2.1) and therefore, by the theorem, equal rows.
6. *D6 moves no D1–D4 id.* Trials run only where D4 found a conflict,
   which without D6 is a refusal; every numbering D1–D4 assign is
   identical with and without D6 (§6 checks the pins both ways).

## 5. The alternative: portable ids minted in the VM

The owner asked whether a cursor cell could carry a portable id from
creation so the carrier sends it as is. To work across engines the id
must be computable by every engine from shared inputs. The candidates
(branch `srvm-phase6a`, `src/cljc/yin/vm/engine.cljc`) are: the task's id
counter (`gen-id`, `:227-230`; `gensym`, `:2312-2318`, which lower adopts
as `max(local, carried)`), the creation sequence of `:stream/cursor`
executions (`handle-cursor-unminted`'s `seq-n`, `:557-568`, minted at the
`:stream/cursor` effect, `:2595-2602`, with the id from `gensym` and the
sealed reference from `issue-ref`, `:311-323`), a hash of (occurrence,
counter), or a random id. Every one of them names *history*, not
structure:

- *Same structure, same hash fails.* Hold every carried field equal:
  task A executes `:stream/cursor` three times (ids `cursor-0`,
  `cursor-1`, `cursor-2`; counter 3) and drops the second; task B executes
  `:stream/cursor` twice and then consumes one unrelated fresh name
  (`gensym` for a non-cursor id; counter 3) and keeps both. The two
  snapshots are structurally equal (two cursor cells with equal bodies at
  equal positions, the same id counter, the same everything else), yet A
  carries `{cursor-0, cursor-2}` and B `{cursor-0, cursor-1}`, so the root
  ids differ. Any id recomputed from the snapshot's *structure* instead
  is the canonicalization problem of §2 again, not an alternative to it.
- *The cross-engine harness law* would hold only if both engines agree
  on the minting history, which makes an execution trace part of the
  frame's identity; a random or occurrence-bound id breaks it outright
  (a fork halt has no occurrence; a child has none of its own).
- *The VM grows a second name.* Lower mints a fresh private resource
  entry per cursor cell (carrier §8 step 12) and must keep the carried
  id beside it; a relift after further execution must mint ids that
  cannot collide with carried ones, which needs an (origin, counter)
  pair: a global naming scheme for a thing that only needs a name
  relative to its state.

Discovery order answers the owner's observation differently: the
identity stays local and the carrier gives it a *structural* name, the
n-th cursor cell met, exactly as a de Bruijn index names a binder by
position rather than by a global symbol. Recommend against portable
ids for immutable creation-history ids carried unchanged; that is the
only kind proposed.

## 7. Recommendation and cost

**Adopt discovery order with D6** (owner decision: adopt; D6 is this
note's recommendation within it). 6b has not started and 6a is
unmerged, so the cost is one implementation slice of `rows.cljc` and its
tests (§8) plus the amendments of §4. Size, from the prototype and the
second review's count rather than the round-2 guess: the prototype's
schema-to-procedure region is about 330 nonblank lines, of which about
30 are D6, the diagnostic mode, tracing and measurement; in place it
reuses 6a's `descriptors`, `bytes-key`, `compare-bytes`, `spend!`,
`refuse!` and `emit-node`, so expect **250–300 added or replacement
lines and 135–150 deleted** (`check-label-bytes!`, labels, `ce`,
`positions`, `classes`, `refine`, `search`), **about 100–160 net**,
excluding tests; the second review's independent estimate was 100–195
net. Review cost: one implementation round and one review round; the
review reads §3 (five lemmas, one induction) and §8's cut list rather
than re-deriving the design, and the generator of §9 item 18 runs in CI.
What the owner gains over 6a: a definition that can be stated and proved
(the n-th cell met, with one bounded tie-break), no growing labels, a
search confined to the residue (two trials for a 2-cycle; 6a's search
over the seven-cell state exceeded a megabyte of labels, D6 numbers it in
11 trials), and 6a's own roots on the 2-cycle and 3-cycle. Risk: a
canonicality bug, mitigated by §9 item 18's generator in CI (it caught
the prototype's memo bug), by the decode round trip in that generator,
and by the proof; and the unproved cost bound, which the `:work` and
`:search` budgets enforce as 6a's budgets did.

**D5 variant (no search at all).** Same slice minus D6 (about 25 lines),
plus the `:unresolved-cursor-cells` kind, its decode translation and the
documented refusal class of F4; refuses 2-cycles and 3-cycles that 6a
numbers. Acceptable if the owner wants no search in the codec; the
refusal can be replaced by D6 later without changing any id numbered
under D1–D4 (§3 consequence 6).

**Keep 6a.** Zero rounds now, but 6b, the cross-engine harness and every
reviewer of a pinned id inherit an exhaustive search over the whole
state, labels that grow until the seven-cell state exceeds a megabyte,
and a definition that is "whatever the procedure outputs". Not
recommended; the owner has decided against it.

**Portable ids.** Changes the VM, the census, the laws and the harness
(§5); three or more rounds across two designs. Against.
