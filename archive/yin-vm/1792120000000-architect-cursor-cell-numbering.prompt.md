## Context and owner rulings

- The row carrier (`docs/design/yin.vm.ucf-transport-tuples.md`, body version 3) serializes a continuation as tuples with Merkle ids. Cursor cells are the one identity-bearing thing in the state; their VM ids (`:cursor-1`, creation order) are LOCAL, so the carrier renames them `:yin.k/cc-<n>` by "canonical cursor-cell numbering" (carrier section 6): label refinement plus exhaustive search. Slice 6a implements it (`src/cljc/yin/vm/ucf/rows.cljc`, `canonical-numbering`).
- Owner rulings that bind you: sharing MUST survive transport (two references to one cursor cell stay one cell; two cells at one position stay two); the root id must depend only on structure (same structure, same hash; the cross-engine harness law compares canonical frames lifted from different engines); the cursor inside a cursor cell is plain data and a stream travels as a portable descriptor; no legacy, no version bumps; the AST is retrievable; BLAKE3 for new identities.
- The owner observed (quoted): "the problem is not that the cursor cell has identity, but that the identity is local". Orchestrator proposal to evaluate: NUMBER CURSOR CELLS BY DISCOVERY ORDER in a canonical traversal (de Bruijn style: the n-th cell met), because every place a suspended state can hold a cursor-ref is ordered (environment keyed by name, window keyed by register number, return frames in a vector, the wait entry's slots), so a canonical traversal has a well-defined "first"; label refinement is then needed only as a fallback for cursor cells reachable solely through UNORDERED guest collections (sets, map keys) whose elements have identical contents.
