## Findings

### F6 — Medium: discharge checks code that cannot run from the carried context

`src/cljc/yin/vm/ucf/rows.cljc:1420–1426`

The context records its resume PC, but discharge uses that PC only to select a body. It then checks every free occurrence in that body and every enclosed body, including occurrences that are behind the resume PC and cannot be reached again. This can reject a valid continuation.

Independent evaluator-produced reproduction:

```clojure
{:type :if
 :test (s/lit false)
 :consequent (s/v 'ghost)
 :alternate (s/next-of (s/cursor-of {:type :stream/make :buffer 4}))}
```

Run this to block, then add `:module-stores {'unrelated {'ghost 42}}` to compare with the old union rule. The actual vector is:

```clojure
[[:const 1 false] [:branch-false 1 4] [:var 0 ghost] [:jump 7]
 [:stream-make 3 4] [:stream-cursor 2 3] [:stream-next 0 2] [:halt 0]]
```

The carried wait is an `:act` at PC 7, with empty E, window and K. Nothing can return to PC 2; no carried closure retains a route to it. Current lift nevertheless refuses with `:yin.k/unsatisfied`, discovery `:incomplete`, obligations `#{ghost}`. Feeding the source stream makes the original machine complete with **73**.

With only the union-discharge mutant enabled, the same state lifts and lowers, carries **zero module stores**, attaches one stream, and both source and receiver complete with **73**. Thus this is a valid state accepted by the old rule and falsely refused by the new context rule; the unrelated store is not needed by execution or transport. The fix report's context-precision concern is reproduced, not hypothetical.

Required change: determine obligations from code reachable from each context's PC, including nested closures that can still be constructed. Use control-flow reachability rather than merely filtering occurrence PCs numerically: backward jumps can make earlier code live. Keep the new per-E/per-active-store answering rule. Add a resumed-PC regression that proves successful transport and completion, and retain negative coverage for genuinely reachable missing names.

### F7 — High: lower accepts a missing module store named by a carried closure

`src/cljc/yin/vm/ucf/rows.cljc:1621–1640`

Lower checks code/tree coverage, closure origin/binders and primitives, but never checks that each closure or frame `store-of` names a module-store row in its own task. This violates continuation design §2.6: “every `store-of` resolves to a carried module store.” This is a remaining validation gap, rather than a newly introduced line of code.

Independent reproduction:

1. Run `(fn [] ghost)` to obtain a real closure.
2. Route its E to `scoped`, with `:module-stores {'scoped {'ghost 42}}`.
3. Put an authentic stream reference in the root store, so successful attachment is observable.
4. Lift normally, decode, remove the task's module-store rows with `(assoc-in task [:slots 7] [])`, and **re-emit** with `rows/emit`.
5. Lower into a fresh receiver, store its result as `f`, and run `(f)`.

The original carrier attaches once and `(f)` returns **42**. The edited carrier also **accepts and attaches once**, but `(f)` throws `Unable to resolve symbol: ghost in this context`, ex-data `{:symbol ghost}`. Row hashes, canonical numbering, code and tree associations are valid; the omitted store is the defect.

Required change: before composition/attachment, validate every non-nil `store-of` against the module-store census of that task, including closures nested in values, acts, return frames, parked/reified states, and install children. A child cannot use a sibling's or parent's store merely because it has the same key. Add zero-attachment regressions for missing stores, with positive coverage for present empty stores and valid scoped stores.

## Staging, attachment preflight and install review

`decode` retains gate → structure/graph → hashes → canonical form → numbering → frames. Lower then runs stores, pendings/install records, dependencies and custody **one stage at a time across the whole task tree**, before `attach-streams!`. Root custody cannot mask a child's dependency failure, and a root dependency failure cannot mask a child's pending/install failure. The original store/closure/install refusals now have named transport outcomes before stream attachment. F7 shows that this does not yet establish complete carrier validation.

`attaches?` calls `module/attach-module` and discards the returned VM. On this semantic-register implementation it is pure: `attach-image` validates/analyses the vector and builds persistent code/alias maps; it runs no evaluator, creates no stream handle, calls no composition attacher or secret source, and changes no mutable receiver field. I independently lowered row 10 into a receiver already holding its carried vectors; it accepted and the original receiver value remained equal to its saved value. I found no valid-vector false refusal in that case.

The vector is validated/analysed in preflight and again during restoration. This duplicates CPU work, but does not duplicate stream attachment or observable execution. Install response images are likewise preflighted and loaded later in a fresh child. No side-effect or double-counting defect was established in these paths. Stream-attachment counts deliberately measure the composition's `attach!`, not pure code-map construction.

Install validation accepts the existing blocked-child records, including the corpus's phase-`:running` synthetic case and tail-delivery case. Phase, response status/name, export shape, image admissibility and child kind are checked before composition. I did not establish an additional valid install state refused by these checks. The blocked-child restriction matches the current engine's `advance-install`: blocked children are retained, halted children proceed to linking in that sweep. The documented executable parked-child scenario remains an architectural follow-up from the previous review.

## Per-context discharge assessment

Contexts are collected for closures, acts and return frames, including values reached transitively through E and module stores. Tail states contribute their K contexts and deliberately contribute no running context for their own dead segment. Nested bodies are associated by the owner chain. The answering order now short-circuits E → the one active store → primitive → installing export → registry. Root-store keys no longer answer a routed closure when its module store lacks the name.

Independent extra probes show a freely used host-class primitive refuses with `:host-state-primitive`, while the same name shadowed by the closure's E or by its active store lifts successfully. This confirms the new ordering rather than the previous unconditional host-profile check. Existing tests exercise closure-only, transitive E/store, and routed-store obligations; corpus transport exercises act, return-frame and tail contexts. The remaining context reachability problem is F6. Missing store-census validation is F7. Receiver registry prerequisites remain the previously accepted composition prerequisite; this review does not reclassify them as a new carrier slot or require registry transport.
