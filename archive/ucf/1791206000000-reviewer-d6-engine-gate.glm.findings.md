## Findings

1. **`apply-next` will advance an unminted cursor cell (advisory, one-line guard).** `engine.cljc:1919-1926` — `advance` writes `:dao.stream/cursor` onto `[:resources cursor-id]` without checking `:yin.k/unminted`. The D5 cursor ruling makes "the driver may not observe a read on a cell until that cell is minted" a driver obligation, and `apply-mint` refuses non-unminted cells in the other direction (`:581-582`), but a mis-ordered driver applying `apply-next` with `ok`/`gap` on an unminted cell silently produces a hybrid cell (both `:yin.k/unminted` and `:cursor`) that later reads would treat as minted at the driver-supplied position. Unreachable through any current caller; a `(when (:yin.k/unminted cell) (fail …))` in the ok?/body would make the fence symmetric. Recommend for D11/D12's hardening round, not this slice.

2. **Child-creation stamping and the gated settle branch lack portable coverage (disclosed; acceptable, recommend closing at land time).** `created-install-child-carries-the-mode-test` exists only under `#?(:cljd nil :clj …)` (`engine_gate_test.cljc:827-842`, because of `(var engine/start-install)`), so no CLJS/CLJD run pins `spawn-child`'s stamp; and no gated test drives `apply-link-read`'s own-`:ok` settle branch (`start-install`, module install) — the round-2/3 reports say so. A portable test exists in principle: gated miss → `apply-link-cursor` → `apply-link-sent` → `apply-link-read` with the entry's own id and an `:ok` response, asserting the install child carries the mode — which would cover both gaps on every lane. Not blocking; the machinery itself is kernel-independent and correct (`stamp-gate` at creation `engine.cljc:1285` and before each run `:1403`).

3. **A gated entry's `:cursor` is a portable position while an ungated entry's is a host cursor (recorded, no action).** `apply-link-cursor` stores `position` directly (`engine.cljc:1605-1609`); the ungated `require-handler` stores `(:dao.stream/cursor minted)` (`module.cljc:571-575`). This is consistent with the ruling in substance — `apply-mint` also stores the position via `vm/cursor-entry`, which wraps without seeding (`vm.cljc:594-598`), and `apply-link-read`'s outcomes overwrite `:cursor` with the driver's successor positions anyway — and the gated form is the one D9/D13 lift needs. The two forms never mix on one task. Noted so D13's "carries its kept cursor from the body" knows both shapes exist.

4. **Report/commit wording could mislead a later auditor (nit).** The claim "nothing outside tests sets `:yin.k/gate`" is true only for *turning custody on*: `stamp-gate` sets it on children (`engine.cljc:1245-1250`), exactly as ruled. Likewise the 2-arity retention's justification cites a `yin.vm.ucf.remote` dependency that is a docstring mention, not a call (`ucf/remote.cljc:561`). Substance right, wording loose.

5. **`apply-ffi-read` re-inlines `ffi-response-entry?` as `reader?` (nit).** `engine.cljc:1990-1991` duplicates the private predicate at `:1713-1717` character-for-character; same namespace, so the named fn could be used directly. Drift risk only.

6. **Wait-set ordering differs between sweep and applies (recorded, no defect).** The ungated rebuilds append still-waiting engine-polled entries after swept ones (`engine.cljc:1566-1568`, `:1855-1857`, `:2086-2090`); the new applies preserve positions (`:1638-1646`, `:2010-2014`). Both are contract-legal — each apply addresses one entry and selection among equal sources falls to wait-set order within one arrangement — but D12's selection rule should not assume either layout.
