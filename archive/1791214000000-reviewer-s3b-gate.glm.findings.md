## Findings

1. **Stale prelude docstring now misstates the `//`/`%`/`**` contract.** `src/cljc/yang/python/antlr/prelude.cljc:101-104` still says integer `//`, `%`, `**` "are exact algorithms here over + - * < … valid within 2^53." Anyone reading the prelude's own contract block would believe `7 // -(2**64)` or `3 ** 40` still refuse. Severity: **low**. Exact fix: drop `//`, `%`, `**` from that sentence and keep it for the bitwise/S3-C helpers only, e.g. "Bitwise operators (pending S3-C) and their bounded helpers below are exact algorithms here over + - * < … valid within 2^53; division, power and true division go through the integer module." Ride with the S3-C prelude edit (which re-mints goldens anyway) or land now — either is fine.
2. **Float `**` with an int exponent ≥ 2^1024: computes where CPython 3.9.6 raises.** In `py/pow` (`prelude.cljc:1270-1279`), a floaty base with a huge non-negative int exponent goes straight to `fpow`. CPython converts the exponent to double first: `1.0 ** (2**2000)` → `OverflowError: int too large to convert to float` (measured on 3.9.6); this profile answers `1.0` — and for |base| > 1 answers ±inf where CPython raises "(34, Result too large". The inf case is pre-existing (the old bounded path did the same for e < 2^53), but for ±1/±1.0 bases the old 2^53 bound raised OverflowError, which *matched* CPython's class at ≥ 2^1024 by accident; this slice fixed the 2^53…2^1024 band (where CPython really computes, now pinned by the corpus at 2^64 scale) and simultaneously broke the ≥ 2^1024 corner. Related: `fpow`'s recursion is now once per exponent bit with no bound below the profile's max-bits — I probed `1.0 ** 2**2000` and `1.0 ** 2**20000` on all four JVM VMs (all returned 1.0, no stack failure), but the Node/Dart lanes have not seen exponents beyond 2^64, and the findings disclose only "bounded integral float exponent admission," not this. Severity: **low** (the corner needs an exponent ≈ 4.5·10^307). Exact fix, three lines inside S3-B's own scope: in both floaty arms of `py/pow`, guard `(if (> (integer/compare e <2^1024-lit>) 0) (py/raise-new py.b/OverflowError {:py/str "int too large to convert to float"}) …)` — this mirrors CPython's exponent conversion, restores the class at ≥ 2^1024, and caps fpow depth at ~1024. Alternatively get an architect ruling to defer it with the other ruling-10 S4 amendments — but then disclose it in the findings the way the parity exclusions are disclosed.
3. **Nits (recorded; pre-existing posture, no action required to land).** (a) `py/division-check` raises "integer division or modulo by zero" for every float zero divisor; CPython 3.9.6 says "float floor division by zero" / "float modulo" / "float divmod()" (measured), and "float division by zero" for `/`.
