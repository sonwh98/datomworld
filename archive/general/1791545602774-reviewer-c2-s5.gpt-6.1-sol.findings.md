# Adversarial Review: Phase C2 Slice S5

**Verdict: REJECTED**

## P1 — `yield from` treats user iterator method returns as generator outcomes

`py/user-forward` wraps the result of `send` and `throw` in `py/guarded`, whose success case is `[:yield result]`. In `py/user-delegate-step`, that outcome is returned to `py/delegate`, which interprets `:yield` as a value to yield outward. That part is consistent for normal results. But StopIteration from a forwarded method becomes `[:return value]`, and this is used to complete delegation; ordinary results work as `[:yield value]`.

The specific failure is the `:throw` path: `py/user-delegate-step` returns `[:raise exception]` only when no `throw` exists, while an exception raised by the delegate's `throw` is not normalized according to PEP 380. `py/guarded` propagates every non-StopIteration exception by raising it in the surrounding outer generator, which bypasses the `py/delegate` outcome protocol and risks unwinding in the wrong context. Likewise, a StopIteration raised by `send` is converted to `:return`, which is correct only if it is the delegate's completion; this needs outcome-boundary handling and focused tests.

More immediately, the acceptance test does not prove the forwarding contract: its `send` and `throw` methods return strings and the expected strings are printed as the outer generator's yielded values, but it does not test exception normalization, StopIteration values from those methods, or missing methods under the relevant message paths. Add cases that assert the delegated yielded result, completion value, and propagation of a non-StopIteration exception from each forwarded method.

## P1 — Heap test does not cover the ruling 7 acceptance shape

`dropped-generators-are-collected-test` compares heap size and deep size after 5 versus 60 temporary generators, while retaining one generator suspended after a single yield. The ruling requires the complete reachable continuation and heap graph across many yields, changing callers, nested delegation, and forced collections; top-level continuation length alone is insufficient. The separate `reachable-heap-is-stable-under-delegation-test` covers changing callers and delegation, but this new dropped-generator test does not stress repeated suspensions of the dropped generators or capture references to their yielded locals across resumed calls. A leak specific to successive suspensions can therefore escape these two samples. Expand the scenario to repeatedly suspend/resume then drop many generators, and compare the complete reachable graph after collection.

## P2 — Iterator object diagnostic rendering needs direct coverage

The renderer adds deterministic forms for `:py/generator` and `:py/iterator`, and the generator snapshot test covers generator output. There is no direct or guest-level assertion for `{:py/iterator "iterator"}` rendering as `<iterator object>`. The implementation appears consistent with the specification; add a small renderer assertion so this new diagnostic form is protected.

## Verified points

- `__iter__` and `__next__` are obtained through `py/class-lookup` on `py/type-of`, so instance attributes with those names do not shadow the implicit special-method lookup.
- `py/user-adv` catches `StopIteration` only around the one `__next__` call. Exceptions from the loop body are outside that guard; other advancement errors are re-raised.
- Invalid `__iter__` results are rejected, and generators/sequence iterators qualify as iterator results.
- The renderer's generator spelling and iterator spelling are deterministic and avoid host addresses.
- The five changed prelude address goldens are a plausible consequence of adding prelude functions, and the reported new prelude root is consistent with the expected profile bump. The other bundled-unit roots are expected to move because they include the prelude subtree.
